
# **FineDev 방법론**

## FineDev 방법론 종합 정리 목차(안)

### 0. Executive Summary

* FineDev가 해결하려는 문제
* 한 문장 정의: Micro Orchestration + Output Fine Tuning
* 핵심 결론 5가지(모델 vs 공정, 함수 단위, 결정론적 게이트, 재작업/승격, 로그/DB)

---

## 1부. 배경과 문제 정의

### 1. FineDev가 등장한 배경

* “모델이 커져도 단순 실수는 남는다”
* 로컬 SLM의 실용화 필요(비용/보안/온프렘)
* ‘API 단발 호출’의 한계와 실패 비용

### 2. 가설과 목표

* 가설: 성공률은 모델보다 공정(오케스트레이션)이 좌우한다
* 목표: SLM으로도 “반복 생산 가능한 개발”을 만든다(전기세 공장)

### 3. 용어 정의

* Micro Orchestration(작게 나누고 조립하는 공정)
* Output Fine Tuning(마지막 1% 오류를 잡는 수렴 루프)
* 계약/스펙, 게이트, 재작업, 승격, Audit(옵션), 경험치 DB

---

## 2부. 실험 설계(공통 프레임)

### 4. 실험 프레임워크 개요

* task/spec 중심 설계(YAML 등)
* 생성→검증→수정→승격 구조
* 로그/재현성 원칙

### 5. 결정론적 게이트 설계

* syntax/compile/ast
* import/packaging 제약
* examples(스펙 테스트) vs pytest(프로젝트 테스트)
* 실패 원인 분해 표준(형식/문법/import/test)

### 6. 프롬프트 설계 원칙

* “최소·명료 + 예시/테스트”
* 과도한 출력제약의 역효과(특히 4b)
* 스키마/포맷 안정화 전략(raw vs schema 등)

---

## 3부. 실험 결과(이전 세션 포함 종합)

### 7. 모델 크기/계열별 관찰(4b ↔ 12b ↔ 대형 LLM)

* 4b: 형식/문법/제약 준수 불안정
* 12b: 함수 단위에서는 실용권 진입
* 대형 모델도 “사소하지만 치명적” 실수는 존재(근원 동일)

### 8. 길이 축(200라인 vs 500~1000라인)과 난이도 분리

* 긴 파일 1회 생성의 실패 패턴
* context/num_predict 확장 시 추론시간/실패율/서빙 리스크

### 9. 시스템/서빙 이슈가 성능을 오판하게 만드는 사례

* PAD_END, HTTP 500, schema 전달 오류
* “에러 바디 로깅”의 결정적 효과

---

## 4부. FineDev 핵심 방법론

### 10. FineDev 아키텍처(전체 구조)

* Spec layer / Generator layer / Deterministic gates / Repair loop / Promotion
* 패키징/모듈 구조(함수=파일, 카탈로그 주입, topo build)

### 11. Micro Orchestration: 함수 단위 개발 전략

* function = file
* dependency catalog / selective injection
* topo 순서 생성/검증/통합
* 템플릿(설계) 중심 접근

### 12. Output Fine Tuning: “99%→100% 실행 가능” 수렴 기술

* 실패 시그니처 분류
* 재작업(1차/2차) 전략
* 결정론적 리라이터(반복되는 단순 오류 자동 교정)
* Planner/Fixer 역할 분리

### 13. Audit AI(옵션): 휴리스틱 분리 원칙

* “계약/게이트는 결정론”
* 휴리스틱(코드 품질/보안/스타일/리팩터)은 옵션 레이어
* 사람 리뷰와 유사한 “불안정성 탐지” 위치

# 1장. FineDev가 등장한 배경

이 장은 “왜 FineDev 같은 방법론이 필요해졌는가”를 독자가 납득하도록 만드는 장입니다. 핵심은 단순합니다. **모델을 더 크게/좋게 쓰는 것만으로는 ‘업무용 소프트웨어 개발’이 안정화되지 않는다**는 점, 그리고 그 이유가 “모델이 약해서”가 아니라 **개발이라는 행위가 갖는 구조적 특성**과 **운영/검증/패키징** 같은 시스템 요인에 있다는 점을 실험으로 확인했다는 것입니다.

---

## 1.1 기존 접근의 전제: “좋은 모델이면 된다”는 믿음

많은 팀이 AI 코딩을 도입할 때 암묵적으로 갖는 전제가 있습니다.

* 더 큰 모델(또는 더 최신 모델)을 쓰면
* 더 긴 프롬프트(더 많은 규칙, 더 자세한 지시)를 주면
* 자연스럽게 “실행 가능한 코드”가 산출될 것이다

이 전제는 **부분적으로는 맞습니다.** 모델이 커지고 성능이 좋아질수록 평균적인 결과가 좋아지고, 잘못된 추론/누락이 줄어드는 경향은 분명 존재합니다.

그러나 소프트웨어 개발에서는 “평균 성능”보다 더 중요한 것이 있습니다.

* **재현 가능성(reproducibility)**: 같은 조건에서 다시 돌려도 결과가 비슷해야 함
* **실행 가능성(executability)**: 문법/빌드/테스트를 통과해야 함
* **정책 준수(compliance)**: import 금지 같은 규칙을 반드시 지켜야 함
* **운영 안정성(operability)**: 실패해도 원인을 추적하고 수리 루프로 수렴해야 함

즉, “대부분 맞는다”는 것보다 “항상 돌아간다”에 가까운 안정성이 더 중요합니다. 업무용 개발은 **99% 정답이 아니라 100% 실행 가능**을 요구하는 경우가 많고, 그 1%가 실제로 비용을 폭발시킵니다.

---

## 1.2 실험이 드러낸 현실: 모델 크기와 무관한 ‘단순 실수’의 반복

이전 세션과 이번 세션 실험에서 반복해서 관찰된 사실은 다음과 같습니다.

* gemma3:4b(소형), gemma3:12b(중형), qwen3-coder:480b-cloud(대형) 등 **서로 다른 규모/계열**의 모델에서도

  * 문법/형식 오류
  * 사소한 오타
  * 요구 미충족(규칙 누락, 엣지 케이스 누락)
  * 출력 형식 불안정(JSON/스키마 등)
    같은 “작은데 치명적인 실수”가 나타났습니다.

여기서 중요한 건 “큰 모델이 더 못했다”가 아니라, **실수의 종류가 유사했다**는 점입니다. 즉, 실수의 근원은 단순히 지능/파라미터 규모의 문제가 아니라는 뜻입니다.

이 세션에서 slugify 같은 작은 함수 과제를 돌리면서도, “짧으면 100% 될 것”이라는 기대가 무너졌습니다. 오히려 짧은 과제일수록 실수가 더 선명하게 보였습니다.

* 하이픈이 하나 빠지거나
* 구두점(콤마, 느낌표) 처리가 누락되거나
* 비ASCII(한글) 제거 규칙을 빠뜨리거나
* 제약(import 금지)을 어기거나

이런 실수는 코드가 5줄이어도 발생합니다. 따라서 “짧은 코드니까 모델이 완벽해야 한다”라는 가정은 실험적으로 성립하지 않았습니다.

---

## 1.3 왜 이런 일이 생기는가: 개발은 ‘정답 생성’이 아니라 ‘정답 수렴’ 문제

FineDev가 필요해진 배경을 이해하려면, 소프트웨어 개발의 본질을 다시 봐야 합니다.

개발은 사실상 아래의 두 과정을 포함합니다.

1. **생성(Generation)**

   * 기능 구현 아이디어, 코드 작성, 구조 설계
2. **수렴(Convergence)**

   * 문법/빌드/테스트/정책 준수
   * 엣지 케이스 보완
   * 환경(패키징, import 경로, 파일 구조) 정합
   * 품질/보안/성능 요구 만족

사람 개발자는 “수렴 과정”을 너무 당연하게 해왔습니다.

* IDE가 문법 오류를 잡아주고
* 린터가 스타일과 일부 버그를 잡아주고
* 테스트가 요구를 강제하고
* CI가 환경 차이를 빨리 발견해주고
* PR 리뷰가 불안정한 부분을 걸러줍니다

그런데 모델을 “단발 호출”로 쓰면, 이 수렴 과정이 통째로 빠집니다. 그러면 모델은 “그럴듯한 코드”는 내지만, **실행 가능한 코드로 수렴시키는 장치**가 없어서, 작은 실수가 그대로 남습니다.

실험적으로도 확인된 결론은 다음과 같습니다.

* 모델은 “코드를 만들 수 있다”
* 그러나 “업무용으로 통과시키는 마지막 1%”는 **모델 단독으로는 불안정**
* 결국 개발 자동화는 “생성”보다 “수렴”이 핵심이다

이 문제 설정이 FineDev의 출발점입니다.

---

## 1.4 로컬 SLM이라는 현실적 제약이 방법론을 더 ‘공정 중심’으로 만들었다

FineDev가 단순히 “모델을 잘 쓰는 법”이 아니라 “공정을 설계하는 법”으로 발전한 데는 로컬 SLM의 제약이 결정적으로 작용했습니다.

로컬 SLM 환경은 장점도 있지만 제약도 분명합니다.

* 장점

  * 비용 절감, 데이터 통제, 온프렘 운영, 반복 실행(전기세 구조)
* 제약

  * 작은 모델은 프롬프트 길이에 민감
  * 출력 형식/문법 안정성이 떨어질 수 있음
  * 긴 파일 1회 생성(500~1000라인)은 실패 확률/시간이 급증

이 제약은 오히려 방향을 선명하게 만들었습니다.

* “큰 파일 한 번에”가 아니라 **함수 단위로 쪼개야 한다**
* “규칙을 많이 나열”이 아니라 **최소 지시 + 테스트 기반**이 낫다
* “모델이 알아서”가 아니라 **결정론적 검증 게이트**가 있어야 한다

즉, 로컬 SLM 환경에서 실용성을 확보하려면, 모델을 “똑똑하게 만드는 것”보다 **실패를 관리하는 공정**이 필수라는 결론으로 수렴했습니다.

---

## 1.5 모델 문제와 시스템 문제를 구분하지 못하면 ‘모델을 오판’하게 된다

이번 방법론이 등장한 또 하나의 직접적 계기는, 초기에 반복된 오판 위험입니다.

실험 초반에는 실패가 나면 흔히 이렇게 해석하기 쉽습니다.

* “4b라서 안 된다”
* “모델이 멍청하다”
* “LLM/SLM로 개발은 어렵다”

그런데 실제로는 많은 실패가 모델 자체가 아니라 아래에서 발생했습니다.

* format/schema 전달 방식 오류 → HTTP 500 (서버가 죽은 게 아니라 요청이 잘못된 것)
* import 경로/패키징 문제 → 코드가 맞아도 실행이 안 됨
* 에러 바디/단계별 실패 로그가 없어서 원인 파악 불가 → 모델 탓으로 귀결

이 경험 때문에 FineDev는 초기에 반드시 다음을 요구합니다.

* 요청/응답(최소한 에러 바디) 로깅
* 단계별 실패 원인 분리(형식/문법/import/test)
* 결정론적 게이트로 “어디서 실패했는지” 즉시 확정

이것이 없으면 모델을 바꾸거나 키워도, 실패의 원인이 계속 “모델 탓”으로 잘못 귀속됩니다.

---

## 1.6 FineDev의 문제 정의(요약)

이 장의 결론은 아래 한 문장으로 요약됩니다.

> **FineDev는 “코드를 생성하는 기술”이 아니라, 모델이 만드는 99% 정상 출력에서 남는 1% 오류를 결정론적으로 잡아내고, 재작업/승격/보정으로 실행 가능한 산출물로 수렴시키는 개발 공정 방법론이다.**

그래서 FineDev의 출발점은 “모델 선택”이 아니라 다음 질문입니다.

* 어떤 단위로 쪼개면 모델이 흔들리지 않는가? (Micro Orchestration)
* 어떤 결정론적 게이트를 두면 실패 원인을 오판하지 않는가?
* 어떤 수리 루프를 두면 고정점을 깨고 수렴하는가? (Output Fine Tuning)
* 어떤 부분을 계약으로 박고, 어떤 부분은 Audit 옵션으로 분리할 것인가?

---

다음 2장에서는 위 배경을 바탕으로,

* FineDev가 세운 핵심 가설(모델 vs 공정)
* 실험 목표(함수 단위에서 pass@k로 수렴시키기)
* 로컬 SLM을 전제로 한 현실적인 성공 기준

을 명확히 정의합니다.

# 2장. 가설과 목표

이 장은 FineDev가 “무엇을 증명/확인하려는 방법론인지”를 실험 가능한 형태로 정의합니다. 즉 **이 방법론이 성공/실패했다고 말할 수 있는 기준**을 세우는 장입니다. FineDev는 ‘좋은 모델을 고르는 법’이 아니라 ‘개발을 수렴시키는 공정’을 다루기 때문에, 가설과 목표도 **모델 성능 지표**가 아니라 **공정 성능 지표**로 정의됩니다.

---

## 2.1 문제를 다시 정의하기: “모델이 코드를 쓰는가?”가 아니라 “결과가 수렴하는가?”

일반적인 AI 코딩 논의는 다음 질문으로 시작합니다.

* 어떤 모델이 더 코딩을 잘하나?
* pass@1이 더 높은가?
* 더 큰 모델이 더 낫나?

FineDev는 질문을 바꿉니다.

* 작은 모델도 포함해, **전체 시스템이 실행 가능한 코드로 수렴하는가?**
* 실패가 났을 때 **원인을 정확히 분해하고**, **재작업이 효과적으로 작동하는가?**
* 비용/시간을 통제하면서 **안정적인 성공률**을 만들 수 있는가?

이 관점 전환이 필요했던 이유는, 이전/이번 실험에서 다음을 확인했기 때문입니다.

* 4b든 480b든 “단순 실수”는 남는다.
* 실무에서 치명적인 것은 “큰 논리 오류”보다 “작은 실행 불능 오류(문법/규약/패키징)”다.
* 그러므로 모델을 키우는 것만으로는 “업무용 개발 안정성”을 보장하지 못한다.

따라서 FineDev의 가설은 “모델이 더 똑똑해진다”가 아니라, **공정이 성공률을 만든다**에 맞춰진다.

---

## 2.2 FineDev의 핵심 가설(Hypotheses)

### 가설 H1: 성공률의 주된 병목은 ‘모델 지능’보다 ‘공정 결함’에서 발생한다

이 가설은 이번 세션의 경험(HTTP 500 원인, import 경로 문제, 로그 부족으로 오판)에서 매우 직접적으로 도출됩니다.

* 실패가 났을 때,

  * 모델이 진짜로 못한 것인지
  * 시스템이 요청을 잘못 보냈는지
  * 실행/테스트 환경이 잘못되었는지
    를 분해하지 못하면,
* “모델이 못해서 실패했다”는 오판이 매우 쉽게 발생한다.

따라서 FineDev는 “모델 바꾸기” 이전에,

* **결정론적 게이트 + 단계별 로깅**을 갖추면
* 같은 모델이라도 성공률이 유의미하게 올라갈 것이라고 가정합니다.

---

### 가설 H2: 큰 파일 1회 생성보다 “함수 단위 + 조립”이 pass@k를 비약적으로 올린다

이전 실험에서 관측된 바:

* 500~1000라인급 단일 파일은 12b에서도 “완성 자체”가 흔들렸음.
* 반면 experiment6/7에서 “function = file” 방식은 다수 함수에서 빠르게 통과가 나왔음.

FineDev는 이를 일반화합니다.

* 개발 단위를 작게 하면

  * 프롬프트 길이가 줄고
  * 모델이 다뤄야 할 상태 공간이 줄고
  * 검증/수정 루프가 짧아져
  * 전체 성공률이 오른다.

즉, FineDev는 “한 번에 크게 생성”을 버리고, **Micro Orchestration(분해·조립)**을 기본 전략으로 둔다.

---

### 가설 H3: “Output Fine Tuning(수렴 루프)”이 pass@1보다 pass@k를 안정적으로 만든다

FineDev는 pass@1을 지나치게 목표로 삼지 않습니다. 이유는 간단합니다.

* 모델은 단발 생성에서 작은 실수를 한다(그리고 그건 완전히 없어지지 않는다).
* 대신, 실패를 정확히 진단하고 재작업을 시키면,

  * 2~5회 이내(pass@k)로 성공하는 비율은 크게 끌어올릴 수 있다.

즉 FineDev는 다음을 가정합니다.

* “한 번에 완벽”은 비현실적일 수 있지만,
* “짧은 루프로 수렴”은 현실적이며,
* 실무에서는 이 수렴 구조가 더 중요하다.

이번 세션의 slugify가 대표적입니다. 동일 모델(4b)이어도,

* 실패가 “제약 위반”에서 “정제 규칙 누락”으로 이동하는 것 자체가 수렴의 조짐이었고,
* 이를 더 빠르게/확실하게 만드는 것이 FineDev의 목적입니다.

---

### 가설 H4: 제약 준수는 프롬프트 강화보다 “시스템 강제”가 더 안정적이다

이번 세션에서 “import 하지 마라”를 모델이 어기는 상황이 발생했습니다. 이때 중요한 결론이 나왔습니다.

* 모델이 지침을 지키게 “설득”하는 건 불안정하다.
* 특히 작은 모델에서는 금지 규칙 준수가 더 흔들린다.
* 따라서 제약은 말로 강제하기보다,

  * 결정론적으로 검사하고
  * 필요한 경우 실행 환경/리라이터/라우팅으로 강제하는 게 낫다.

이 가설은 이후 FineDev의 설계 원칙(계약=결정론, 휴리스틱=옵션 분리)로 이어집니다.

---

### 가설 H5: “경험치 DB(실패→수정)” 축적은 작은 모델을 더 ‘결정론적으로’ 만든다

FineDev는 결과적으로 **학습 없는 튜닝**을 하게 됩니다.

* 같은 실패(시그니처)가 반복될 때
* 어떤 수정 지시/수정 코드가 성공했는지 축적하면
* 다음에는 모델이 실수해도

  * 시스템이 빠르게 올바른 방향으로 수렴시킬 수 있음

이것이 사용자가 말한 “Output Fine Tuning”의 실체 중 하나입니다.

* 모델을 재학습시키지 않아도,
* 공정+DB만으로 성능이 개선되는 영역이 존재합니다.

---

## 2.3 목표(Goals): 무엇을 “성공”이라고 부를 것인가?

FineDev의 목표는 3층으로 나눠 정의하는 것이 좋습니다.

### 목표 G0: 오판 방지(관측 가능성 확보)

가장 먼저 성립해야 하는 목표입니다.

* 모든 실패는

  * 어느 게이트에서 실패했는지
  * 실패 메시지가 무엇인지
  * 어떤 프롬프트/출력으로부터 나왔는지
    가 재현 가능해야 함.

이번 세션에서 “프롬프트 전문 로깅”을 넣은 이유가 바로 이것입니다.

**성공 기준(G0):**

* runs.jsonl만으로 “왜 실패했는지”를 추적 가능
* 프롬프트/출력/게이트 결과가 모두 남음

---

### 목표 G1: 함수 단위 과제에서 pass@k 수렴 구조 성립

MVP1~MVP2 수준의 실용 목표입니다.

* 입력: 함수 스펙(시그니처/예시/제약/노트)
* 출력: 테스트 통과하는 구현 파일
* 과정: 1~k회의 재작업 루프로 수렴

**성공 기준(G1):**

* “함수 1개”는 k(예: 3~5) 시도 내에서 높은 확률로 통과
* 실패하더라도 실패 원인이 명확히 분해됨
* 고정점이 감지되면(동일 시그니처 반복) 다른 전략이 자동 적용됨

---

### 목표 G2: 비용 최적화(저가 모델 우선 + 필요한 경우만 승격)

FineDev의 실용 가치가 여기서 나옵니다.

* 가능한 한 4b/저가 모델로 처리
* 고정점/난이도 상승 시에만 12b/상위 모델로 승격

**성공 기준(G2):**

* 전체 비용(시간/추론량)이 일정 수준 이하로 유지되면서도
* pass@k 성능이 안정화됨
* 승격은 “정책적으로” 일어나고, 로그로 설명 가능

---

### 목표 G3: 대규모 확장(함수 1000개~10000개)에서도 공정이 붕괴하지 않음

사용자가 말한 “전기세만 늘어나는 체계”가 이 목표입니다.

**성공 기준(G3):**

* 함수 1000개 프로젝트에서도

  * 의존성 topo 순서로 자동 생성/검증/조립
  * 실패는 격리되고(한 함수가 깨져도 전체가 멈추지 않음)
  * 경험치 DB가 누적되어 재시도 비용이 감소

이 목표는 MVP5(함수 1000개) 단계로 이어집니다.

---

## 2.4 실험 질문(Research Questions): 이번 세션에서 실제로 확인한 것

FineDev의 가설/목표를 실험 질문으로 바꾸면 다음과 같습니다.

* RQ1: 실패는 어느 단계에서 주로 발생하는가? (문법/제약/예시/테스트/환경)
* RQ2: 재작업은 언제 효과가 있고, 언제 고정점에 빠지는가?
* RQ3: Planner(옵션)나 교차 모델이 고정점 탈출에 유의미한가?
* RQ4: 제약(import 금지 같은)이 모델의 품질을 올리는가, 오히려 실패를 늘리는가?
* RQ5: 프롬프트 길이/복잡도가 성공률에 어떤 영향을 주는가?

이번 세션에서 slugify는 최소한 RQ1~RQ4의 “초기 형태”를 확인했습니다.

* import 금지 위반이 나타났고(제약 준수 문제)
* 하이픈 관련 고정점이 나타났고(재작업 진동)
* planner를 붙여도 같은 4b이면 탈출이 제한적임을 확인했으며(역할 분리의 한계)
* 프롬프트 로깅으로 원인 분석 기반을 만들었습니다(관측 가능성)

## 2.5 이 장의 결론(요약)

FineDev의 가설과 목표는 모델 성능 자체를 목표로 삼지 않습니다. 대신:

* **작은 단위로 분해(Micro Orchestration)**
* **결정론적 게이트로 실패를 분해**
* **수리 루프로 1%를 제거(Output Fine Tuning)**
* **필요할 때만 승격**
* **경험치 DB로 반복 실패를 줄임**

이 과정이 “현실적 비용” 안에서 **pass@k 수렴**을 만들어내는지 확인하는 것이 FineDev의 핵심 목표입니다.

# 3장. 용어 정의

이 장은 FineDev 문서 전체에서 반복되는 핵심 용어들을 **같은 의미로** 쓰기 위해 만든 “사전”입니다. FineDev는 특히 **결정론적(Deterministic)** 요소와 **휴리스틱/추정(Heuristic)** 요소를 엄격히 분리하려고 하기 때문에, 용어 정의가 흐려지면 설계가 바로 흔들립니다. 그래서 이 장은 설명형으로 충분히 풀고, 일부는 개조식(규칙/기준)으로 고정합니다.

---

## 3.1 FineDev (방법론 전체)

**FineDev**는 “AI가 코드를 잘 쓰게 하는 팁”이 아니라, 다음 두 축을 결합한 **개발 공정 방법론**입니다.

* **Micro Orchestration**: 개발을 작은 단위(주로 함수)로 쪼개고, 단계적으로 조립하는 운영 방식
* **Output Fine Tuning**: 산출물의 마지막 1% 오류를 결정론적 검증/수정 루프로 제거하여 “실행 가능한 코드”로 수렴시키는 기술

FineDev의 핵심 메시지는 한 문장으로 이렇게 고정됩니다.

> FineDev = “작게 나누고(Micro), 결정론적으로 검증하고(Gates), 반복 수리로 수렴시켜(Output Fine Tuning), 실행 가능한 산출물로 만든다.”

---

## 3.2 Micro Orchestration (분해·조립 중심의 공정)

**Micro Orchestration**은 “오케스트레이션을 한다”가 아니라, 작업 단위를 **미세하게** 고정해서 모델 부담을 줄이는 방식입니다.

### 정의

* 개발 작업을 **함수/작은 모듈** 단위로 분해하고,
* 각 단위를 독립적으로 생성·검증·수리한 뒤,
* 의존성을 기준으로 **조립(topological assembly)** 하는 공정.

### 핵심 특성(개조식)

* 단위: 보통 **function = file**
* 입력: spec(시그니처, 예시, 제약, 노트, 의존 카탈로그)
* 출력: 통과된 구현 조각 + public export 연결
* 조립: topo 순서로 빌드(선행 함수가 먼저 통과해야 후행이 생성/검증 가능)

### 왜 “Micro”가 중요한가

* 큰 파일 1회 생성은 실패 축이 폭발함(완성도/문법/일관성/시간)
* 작은 단위는:

  * 프롬프트 짧아짐
  * 검증 빨라짐
  * 실패 원인이 분해됨
  * 재작업 비용이 작아짐

Micro Orchestration은 FineDev의 “생산성”을 책임지고, Output Fine Tuning은 FineDev의 “품질/수렴”을 책임집니다.

---

## 3.3 Output Fine Tuning (마지막 1% 오류 제거)

**Output Fine Tuning**은 흔히 말하는 모델 파인튜닝(학습)과 다릅니다. FineDev에서 Output Fine Tuning은 먼저 **시스템 레벨의 미세 교정 공정**을 뜻합니다.

### 정의

* 모델 출력(코드)을 결정론적 검사로 평가하고,
* 실패 원인을 가능한 한 정확하게 분해하여,
* 재작업(수정/재생성/승격/리라이트)을 통해
* **테스트 통과**라는 결정론적 목표로 수렴시키는 방법.

### Output Fine Tuning의 구성요소

1. **검증(Validation)**: compile/tests/examples 같은 결정론적 평가
2. **진단(Diagnosis)**: 실패 메시지/시그니처로 원인 분류
3. **수정(Repair)**: 재작업 프롬프트, 패치 모델, 리라이터
4. **수렴(Convergence)**: pass@k를 올리고 고정점을 깨는 전략
5. **축적(Experience DB)**: 반복 실패를 룰/데이터로 저장하여 다음에 더 빨리 수렴

### “Fine”가 의미하는 것

* 출력의 99%가 정상일 때
* 남은 1% (하이픈 하나, import 한 줄, 구두점 처리 누락)를 잡아내는 것이 실제 비용을 좌우하므로
* “미세 조정”이라는 단어가 실무 체감과 잘 맞습니다.

---

## 3.4 Spec / Contract (스펙 / 계약)

FineDev에서 **스펙(spec)**은 “모델에게 주는 요구사항 묶음”이고, **계약(contract)**은 “게이트가 강제하는 규칙”입니다. 둘을 구분하는 이유는:

* 스펙은 사람이 쓰는 요구사항일 수 있고,
* 계약은 반드시 **기계적으로 판정 가능한 규칙**이어야 하기 때문입니다.

### Spec(스펙) 정의

* 함수 시그니처, 목적, 예시, 제약, 노트, 의존성 정보를 포함하는 입력 문서(YAML 등)

### Contract(계약) 정의

* spec 중에서도 **결정론적으로 true/false 판정 가능한** 부분만을 말함
* 예:

  * “import 금지” → 코드에서 import 문이 있으면 실패
  * “함수 이름/시그니처 고정” → AST로 검사 가능
  * “출력은 [a-z0-9-]만” → 정규식/검사로 판정 가능

### 계약 설계 원칙(중요)

* 계약은 **휴리스틱이면 안 됨**
* 애매한 요구(“깔끔하게”, “좋은 코드”)는 계약이 아니라 **Audit(옵션)** 영역으로 밀어냄

---

## 3.5 Deterministic Gate (결정론적 게이트)

**게이트(gate)**는 FineDev의 심장입니다. 게이트는 “AI가 아니라 기계적으로” 결과를 판정합니다.

### 정의

* 입력: 후보 코드(또는 산출물)
* 출력: 통과/실패 + 실패 이유(정확한 메시지)

### 게이트의 예(개조식)

* **extract gate**: 코드 블록만 추출(형식 안정화)
* **syntax gate**: `compile()` / `ast.parse()` 통과 여부
* **constraint gate**: import 금지, 금지 API 사용 금지 등
* **examples gate**: 예시 입력→출력 비교
* **pytest gate**: 테스트 러너 통과 여부
* (확장) lint/type/security gate: flake8/mypy/bandit 등

### 게이트 설계 원칙

* “통과/실패”가 **항상 동일**해야 함(결정론)
* 실패 메시지는 다음 재작업에 곧바로 투입할 수 있어야 함
* 게이트는 가능한 한 **빨리, 싸게** 실패시킬수록 좋음(초기 단계에서 컷)

---

## 3.6 Repair (재작업) / Retry (재시도) / Rebuild (재생성)

FineDev는 “그냥 다시 해봐” 같은 재시도를 최소화하고, “왜 실패했는지”를 반영한 재작업을 선호합니다.

### Retry(재시도)

* 같은 프롬프트/조건으로 다시 생성하는 것
* 장점: 비용이 싸고 운 좋으면 통과
* 단점: 고정점이면 의미 없음(같은 실수 반복)

### Repair(재작업)

* 실패 메시지와 수정 지시(edit directives)를 포함하여 다시 생성/수정하는 것
* 장점: pass@k를 체계적으로 올림
* 단점: 지시가 길어지면 모델이 흔들릴 수 있음 → “최소 지시” 원칙 필요

### Rebuild(재생성)

* 기존 코드를 버리고 새로 생성(큰 구조가 잘못됐을 때)
* 보통 2차 repair 실패 후 선택

FineDev는 기본적으로

* 1차: retry/repair(짧게)
* 2차: 실패 원인 명시 repair(조금 더 구체적)
* 그럼에도 실패: 승격/역할 분리/리라이트
  순서를 취합니다.

---

## 3.7 Promotion / Escalation (승격)

**승격(escalation/promotion)**은 “더 큰 모델로 바꿔서 한 번에 해결”이 아니라, FineDev 공정의 일부로 정의됩니다.

### 정의

* 특정 실패 패턴(고정점/시간 초과/반복 위반)이 나타날 때,
* 더 강한 모델 또는 다른 역할 모델(planner/fixer)을 투입하는 정책.

### 왜 정책이어야 하나

* 무작정 큰 모델 호출은 비용을 망가뜨리고,
* 승격 기준이 없으면 운영이 불투명해져 실험/개선이 어려움

### 승격 트리거 예시(개조식)

* 동일 failure signature 2회 이상 반복
* attempt 3 이상에서 같은 유형 실패 지속
* 특정 스테이지에서만 연속 실패(예: constraints 고착)
* timeout/서빙 불안정 감지

---

## 3.8 Planner / Producer / Fixer (역할 분리)

FineDev는 한 모델에게 “모든 걸 다 하라”를 시키기보다, 역할을 분리할 수 있습니다.

### Producer

* 실제 코드 생성 담당(대개 저가/로컬 SLM)

### Planner

* 실패를 보고 “수정 지시(EDIT DIRECTIVES)”만 생성
* 목적: 프롬프트를 짧게 유지하면서도 수정 방향을 정확히 주입

### Fixer

* 기존 코드를 최소 변경으로 고치는 역할(패치 중심)
* Producer가 고정점에 빠졌을 때 탈출에 도움

이번 세션에서는 Planner를 옵션으로 도입했지만, planner도 4b인 환경에서는 효과가 제한적일 수 있음을 확인했습니다. (역할 분리의 개념은 유효하되, “역할 모델의 힘”이 필요)

---

## 3.9 Failure Signature (실패 시그니처)

**실패 시그니처**는 FineDev 운영에서 매우 중요한 개념입니다.

### 정의

* 실패 로그를 사람이 읽기 좋은 형태로 요약한 “실패 유형 코드”
* 예: `syntax_error`, `constraint_no_imports`, `missing_separators`, `too_many_hyphens` 등

### 목적

* “같은 실패 반복”을 기계적으로 감지
* 고정점(stuck loop) 판단
* 다음 조치(Planner 호출/승격/리라이트/룰 적용)를 정책적으로 결정

---

## 3.10 Experience DB (경험치 DB)

FineDev에서 경험치 DB는 “학습 데이터”라기보다 **운영 데이터**입니다.

### 정의

* 실패 시그니처 + 상황(spec/테스트/환경) + 성공한 수정 전략을 기록한 데이터베이스

### 활용

* 동일 실패에 대한 빠른 처방(룰/리라이트/지시문)
* 장기적으로는:

  * patch 전용 모델 학습(진짜 fine-tuning)
  * 조직/프로젝트 규칙 내재화

---

## 3.11 Audit AI (옵션 레이어)

Audit은 FineDev에서 의도적으로 “옵션”입니다.

### 정의

* 결정론적으로 판정할 수 없는 품질 요소를 점검하는 단계

  * 가독성, 스타일, 보안 취약점 가능성, 성능, 리팩터링 제안 등

### 분리 원칙(중요)

* Audit 결과로 빌드를 실패시키면 휴리스틱이 계약을 오염시킴
* 따라서 Audit은:

  * 경고/추천을 주고,
  * 필요하면 인간 또는 별도 정책이 반영하도록 한다

---

## 3.12 용어 간 관계(요약 맵)

개념 관계를 한 줄로 정리하면:

* **Micro Orchestration**이 작업 단위를 줄여 “생성 가능성”을 올리고
* **Deterministic Gates**가 실패를 정확히 분해하고
* **Output Fine Tuning(Repair/Promotion/Rewrite)**이 마지막 1%를 수렴시키며
* **Failure Signatures + Experience DB**가 반복 실패를 점점 자동화하고
* **Audit AI**는 휴리스틱 품질 점검을 옵션으로 제공한다.

# 4장. 실험 프레임워크 개요

이 장은 FineDev 실험(그리고 실제 운영)의 “기본 프레임”을 설명합니다. FineDev는 단순히 프롬프트를 잘 쓰는 방법이 아니라, **스펙 기반으로 생성→검증→수정→승격을 반복하면서 결과를 수렴시키는 시스템**입니다. 따라서 프레임워크는 (1) 입력 형식, (2) 실행 파이프라인, (3) 로깅/재현성, (4) 실패 분해 방식이 핵심 구성요소입니다.

---

## 4.1 프레임워크의 목적: “모델 평가”가 아니라 “공정 수렴”을 측정한다

일반적인 벤치마크는 모델의 pass@1 같은 성능만 봅니다. FineDev 프레임워크는 그보다 아래를 봅니다.

* 어떤 단계에서 실패했는가?
* 실패는 모델의 문제인가, 시스템/환경의 문제인가?
* 같은 실패를 반복하는가(고정점)?
* 수정 루프가 수렴을 만드는가?
* 비용(시간/시도 횟수/승격률)은 어떤가?

즉, FineDev 프레임워크는 **코딩 에이전트**라기보다 **개발 공정 엔진**에 가깝습니다.

---

## 4.2 입력: Spec 중심 설계(스펙이 곧 작업 단위)

FineDev의 실행 단위는 “프롬프트”가 아니라 “스펙(spec)”입니다. 스펙은 사람이 읽어도 되고 기계가 읽어도 되는 형태로 유지합니다(보통 YAML).

### 스펙에 포함되는 정보(권장 스키마)

* `name`: 함수/유닛 이름
* `signature`: 고정 시그니처(예: `def slugify(text: str) -> str:`)
* `purpose`: 간단한 목적
* `examples`: 입력→출력 예시(결정론적 검증용)
* `constraints`: 계약(금지/허용 규칙)
* `notes`: 추가 힌트(가능하면 짧게)
* (확장) `deps`: 의존 함수/모듈 카탈로그, 선택적 주입 목록

여기서 핵심은 **examples/constraints가 곧 게이트로 연결**된다는 점입니다.

* examples는 “스펙 테스트”가 되고,
* constraints는 “정책 검사”가 됩니다.

즉 스펙을 쓰는 순간, 검증이 자동으로 생성됩니다.

---

## 4.3 실행 파이프라인: 생성→게이트→수리 루프의 기본 흐름

FineDev는 다음의 고정된 흐름을 갖습니다. (이 순서가 중요합니다. “싼 것부터 먼저” 실패시키기 때문입니다.)

### Step 0) 준비(프로젝트 스캐폴딩/환경)

* 패키징 구조, import 경로, 테스트 러너, logs 디렉토리 등
* 이 단계가 흔들리면 모델을 오판하기 쉬움

### Step 1) Generate (Producer)

* 입력: 스펙
* 출력: 후보 코드(raw output)
* 특징: 모델은 “완벽”이 아니라 “후보”를 낸다

### Step 2) Extract (형식 안정화)

* raw output에서 **코드만 추출**
* 이유: 작은 모델은 JSON/마크다운 등 형식을 쉽게 흔들고, 그게 실패 원인이 되기 때문

### Step 3) Fixup (안전 후처리)

* 들여쓰기/코드블록/불필요 텍스트 제거 등 “안전한 정규화”
* 원칙: 로직을 바꾸지 않고, 실행 가능성만 높이는 정리

### Step 4) Syntax/Compile Gate (결정론적)

* `compile()` 및 `ast.parse()`로 문법/파싱 검사
* **AI 없이 100% 확정** 가능한 단계
* 실패하면 바로 repair로 (테스트까지 갈 필요 없음)

### Step 5) Constraint Gate (결정론적)

* 예: import 금지, 특정 API 금지, 시그니처 고정 등
* “정책 위반”은 여기서 조기 차단
* 이 단계에서 실패하면, 이후 테스트를 돌려봐야 의미가 없음(정책 위반은 통과해도 불합격)

### Step 6) Examples Gate (결정론적 스펙 테스트)

* 예시 입력을 실제로 함수에 적용해 output 비교
* 장점:

  * pytest보다 빠르고
  * 실패 메시지를 “구체적인 미스매치”로 만들기 쉬움
* 이번 세션 slugify에서 가장 중요한 수렴 축이 되었음

### Step 7) Write/Export (산출물 반영)

* 구현 파일 저장(`function=file`)
* public API에 export 라인 추가
* 이 단계는 “통과 후보”만 반영하는 것을 권장(중간 실패 코드는 격리)

### Step 8) Pytest Gate (통합 테스트)

* 프로젝트 테스트 전체 실행
* 여기서 통과하면 “완성”
* 실패하면 pytest 로그를 기반으로 repair

---

## 4.4 수리 루프(Repair Loop): pass@k를 올리는 장치

FineDev의 핵심은 “한 번에 성공”이 아니라 “몇 번 안에 수렴”입니다.

### 기본 루프

* Attempt 1: 생성(gen prompt)
* Attempt 2..k: 수리(repair prompt)

repair prompt에는 보통 다음이 들어갑니다.

* 실패 메시지(게이트가 반환한 정확한 오류)
* edit directives(짧은 수정 지시)
* 이전 코드(가능하면 코드 전체 또는 diff)
* 동일 스펙(시그니처/예시/제약/노트)

### 고정점 대응

실험에서 확인했듯, 같은 실수가 반복될 수 있습니다. 이를 위해 FineDev는:

* 실패 시그니처를 계산하고
* 동일 시그니처 반복 시

  * Planner 호출
  * 모델 교체(승격/교차)
  * 결정론적 리라이트 적용
    같은 “다른 조치”를 트리거합니다.

---

## 4.5 Planner(옵션): “수정 지시만” 분리하는 이유

Planner는 코드가 아니라 **수정 지시(EDIT DIRECTIVES)**만 만드는 모델/단계입니다.

### Planner를 쓰는 이유

* Producer(특히 4b)가 긴 repair prompt를 받으면 더 흔들릴 수 있음
* Planner가 실패 로그를 읽고 “수정 요약”을 만들어 주면,

  * repair prompt를 더 짧고 명확하게 만들 수 있음

### 운영 원칙

* 항상 Planner를 쓰면 비용이 늘고, 오히려 혼란이 생길 수 있음
* 따라서 “동일 시그니처 반복” 같은 조건에서만 켠다(라우팅)

이번 세션에서 Planner도 4b였기 때문에 효과는 제한적이었지만,
“라우팅으로 필요한 순간에만 호출”하는 구조는 검증되었습니다.

---

## 4.6 로깅과 재현성: FineDev 실험의 최소 조건

FineDev는 “잘 되더라”가 아니라, “왜 됐는지/왜 안 됐는지”를 남깁니다.

### 최소 로그(권장)

* spec_path, attempt 번호
* 사용 모델명/프로바이더
* 사용된 프롬프트 전문(gen/repair/planner)
* raw output
* extracted code
* fixup 적용 내역
* 단계별 게이트 결과(compile_ok, constraints_ok, examples_ok, pytest_ok)
* 실패 메시지(에러 바디 포함)
* failure_signature

이번 세션에서 “프롬프트 전문 로깅”을 붙인 이유가 바로 이것입니다.
이제 프롬프트를 직접 튜닝할 수 있고, 어떤 변경이 성공률을 올렸는지 추적할 수 있습니다.

---

## 4.7 실패 분해(Failure Taxonomy): 모델 탓을 막는 분류 체계

FineDev는 실패를 다음 범주로 분해합니다.

1. **형식 실패**: 코드 추출 불가, JSON 파싱 실패, 스키마 미준수
2. **문법 실패**: compile/ast 실패
3. **제약/정책 실패**: import 금지 위반 등
4. **스펙 실패**: examples mismatch(요구 불일치)
5. **통합 실패**: pytest 실패, import 경로 문제, 패키징 문제
6. **시스템 실패**: HTTP 500, 타임아웃, OOM, 서빙 오류

이 분류를 하면,

* “모델이 못해서 실패”인지
* “시스템이 깨져서 실패”인지
* “요구가 애매해서 실패”인지
  가 분리됩니다.

---

## 4.8 프레임워크가 지키는 핵심 원칙(정리)

* **스펙이 곧 테스트/계약으로 이어지게 한다** (스펙-검증 일체화)
* **싼 게이트부터 먼저** 실패시켜 비용을 줄인다
* **결정론적 요소와 휴리스틱 요소를 분리**한다
* **재작업은 짧고 명확하게**, 필요할 때만 확장(Planner/승격)
* **로그가 없으면 실험이 아니다** (재현성/오판 방지)

---

## 4.9 이 장이 다음 장으로 연결되는 지점

4장은 “전체 프레임”을 보여줬습니다. 다음 5장에서는 이 프레임 안에서 가장 핵심인 **결정론적 게이트 설계(어떤 게이트를 어떤 순서로 배치하고, 실패 메시지를 어떻게 표준화하는지)**를 더 깊게 다룹니다.

# 5장. 결정론적 게이트 설계

FineDev에서 “결정론적 게이트(Deterministic Gates)”는 단순한 검증 장치가 아니라 **모델을 오판하지 않게 하는 안전장치**이자, **Output Fine Tuning(수렴)**을 가능하게 만드는 핵심 메커니즘입니다. 이 장에서는 게이트를 어떤 철학으로 설계하고, 어떤 순서로 배치하며, 실패 메시지를 어떻게 표준화해야 공정이 안정적으로 수렴하는지를 정리합니다.

---

## 5.1 게이트의 목적: “정답 판정”이 아니라 “실패를 쪼개서 수리 가능하게 만들기”

게이트를 단순히 “검사 단계”로 이해하면, 설계가 불필요하게 복잡해지거나(모든 걸 다 검사하려 함) 반대로 너무 약해질 수 있습니다.

FineDev에서 게이트의 목적은 3가지입니다.

1. **실패를 조기에(cheap) 잡아서 비용을 줄인다**

   * 실패할 코드는 빨리 떨어뜨릴수록 좋다.

2. **실패 원인을 ‘모델 문제 vs 시스템 문제’로 분리한다**

   * “모델이 못했다”는 결론을 내리기 전에,

     * 요청이 잘못되었는지
     * 실행환경이 잘못되었는지
     * 테스트가 잘못되었는지
       를 분해한다.

3. **수리 루프에 넣을 수 있는 형태의 피드백을 만든다**

   * 게이트가 “틀렸음”만 말하면 수렴이 안 된다.
   * 무엇을 어떻게 고치면 되는지, 모델이 행동할 수 있는 정보를 제공해야 한다.

---

## 5.2 게이트 설계의 1원칙: “결정론적”이어야 한다

결정론적이라는 것은:

* 동일한 입력(코드/산출물)에 대해
* 언제 실행해도
* 같은 결과(통과/실패)와 같은 실패 메시지를 내야 한다

### 결정론적이지 않은 것의 예

* “코드가 깔끔한가?” (주관)
* “성능이 좋은가?” (환경/데이터에 따라 달라짐)
* “보안이 안전해 보이는가?” (휴리스틱)

이런 것은 Audit 단계로 빼고, 게이트는 아래처럼 명확해야 합니다.

* `compile()` 통과? (예/아니오)
* 특정 import 존재? (예/아니오)
* 예시 입력 결과가 기대 출력과 동일? (예/아니오)
* pytest 통과? (예/아니오)

---

## 5.3 게이트 설계의 2원칙: “싼 것부터” 배치한다

게이트는 **계층형 파이프라인**으로 구성합니다. 앞단은 빠르고 싸게, 뒷단은 느리지만 포괄적으로.

권장 순서는 다음과 같습니다.

1. **Extract gate** (형식 안정화)
2. **Syntax/Parse gate** (compile/ast)
3. **Contract/Constraint gate** (정책 위반)
4. **Examples gate** (스펙 단위 빠른 검증)
5. **Import/Packaging gate** (모듈 구조/경로 확인)
6. **Pytest gate** (통합 검증)
7. (확장) Lint/Type/Security gate (선택)

### 왜 이 순서인가?

* 문법이 깨진 코드는 테스트 의미가 없음
* 정책 위반 코드는 통과해도 불합격이므로 빨리 자른다
* 예시 검증은 pytest보다 빠르고, 실패 피드백이 직접적이다
* pytest는 가장 비싸지만 최종 판정이므로 맨 뒤

---

## 5.4 각 게이트 상세 설계

아래는 FineDev에서 실무적으로 가장 효과가 큰 게이트들을 설명합니다.

---

### 5.4.1 Extract Gate: “코드만 추출”

#### 목적

* 모델 출력에는 종종 설명, 마크다운, JSON, 잡텍스트가 섞임
* 실행 시스템은 “코드만” 필요
* 따라서 먼저 코드만 안정적으로 추출해야 한다

#### 통과 기준

* 지정된 코드 블록(예: `python … `) 또는 전체 출력에서 파이썬 코드 형태를 추출
* 추출 실패 시: `ExtractError`로 즉시 실패

#### 실패 메시지 설계

* 단순히 “추출 실패”가 아니라:

  * “코드 블록이 없었다”
  * “여러 블록이 충돌했다”
    같은 구체적 사유가 좋다

#### 시사점

* 이 게이트가 없으면, JSON/스키마 파싱 실패 등 “형식 실패”가 모델 탓으로 오해되기 쉽다.

---

### 5.4.2 Syntax/Parse Gate: “문법은 AI가 아니라 컴파일러가 판정”

#### 목적

* 문법 오류는 100% 결정론적으로 잡을 수 있음
* AI에게 문법 검사를 맡기는 건 비용 낭비

#### 구현(개조식)

* `compile(code, ...)` 실행
* `ast.parse(code)` 실행

#### 실패 메시지 설계

* Python이 주는 메시지를 그대로 보존:

  * `SyntaxError: unexpected EOF while parsing (line N)`
  * `IndentationError: ...`
* line 번호는 수리 루프에서 매우 유용함

#### 시사점

* 문법 게이트를 앞에 두면,

  * “코드 생성 성공률”은 실제로 크게 오른다(다음 단계로 진행 가능한 후보가 늘기 때문)

---

### 5.4.3 Contract/Constraint Gate: “정책은 규정 준수 검사로 강제”

#### 목적

* import 금지, 금지 API, 시그니처 고정 같은 규칙을 강제
* 정책 위반은 통과해도 불합격이므로 조기에 컷

#### 설계 원칙

* 계약은 **판정 가능해야 한다**
* 계약이 휴리스틱이면 Audit로 빼야 한다

#### 구현 예: import 금지

* 코드에서 `import ` 또는 `from ` 라인을 탐지
* 발견 시 즉시 실패:

  * `ConstraintViolation: import not allowed (line i): ...`

#### 중요한 추가 논의(세션 시사점)

* 단순히 import 라인을 “지워서 진행”하면,

  * 해당 import에 의존한 코드 전체가 무의미해질 수 있음
* 따라서 권장 전략은:

  * **의존 여부 탐지 → 라우팅(재구현 요구)**
    즉, import 발견 자체가 아니라 “그 import가 실제로 사용되는지”까지 판단해서
  * 미사용이면 안전하게 제거
  * 사용 중이면 즉시 실패 + “재구현” 지시
    로 가는 것이 안정적이다

---

### 5.4.4 Examples Gate: “pytest 전에 스펙을 빠르게 확정”

#### 목적

* pytest는 느리고 실패 메시지가 때로 과잉 정보
* examples는 빠르고, 실패가 “input/expected/got”로 직관적

#### 통과 기준

* 코드 실행(`exec`) 후 함수 로드
* examples 입력을 순서대로 넣어 기대 출력과 동일한지 비교

#### 실패 메시지 설계(권장)

* mismatch를 1~N개까지만 출력(너무 길면 모델이 흔들림)
* 예:

  * `ExampleMismatch #1: input='Hello, World!' expected='hello-world' got='hello,-world!'`
* 추가 힌트는 “결정론적으로”만 붙인다

  * 예: expected에 '-'가 있는데 got에 '-'가 없다 → `missing separators` 힌트 가능
  * got에 '-'가 과도하게 많음 → `char-by-char join` 의심 힌트 가능

#### 시사점

* 이번 세션에서 slugify는 examples gate에서 수렴/발산 패턴이 아주 잘 드러났다.
* 즉 “작은 과제”일수록 examples gate가 강력한 레버가 된다.

---

### 5.4.5 Packaging/Import Gate: “코드가 맞아도 실행환경이 틀리면 실패”

#### 목적

* 코드가 맞는데도 import 경로/패키지 구조 때문에 테스트가 깨질 수 있음
* 이 경우 모델을 탓하면 오판

#### 구현 아이디어

* 최소한:

  * `python -c "from mypkg import slugify"` 같은 import check
* 프로젝트가 커지면:

  * `__init__.py` 존재, export 라인 존재 여부 확인

#### 시사점

* 이번 세션에서도 초기에 `mypkg` 모듈을 못 찾는 오류가 있었고,
  이는 모델과 무관한 “환경/설치” 문제였다.

---

### 5.4.6 Pytest Gate: “최종 판정”

#### 목적

* 단위 예시를 넘어선 통합 테스트 통과 여부 확정

#### 설계 원칙

* pytest는 가장 비싸므로 마지막에 배치
* 실패 로그는 너무 길게 주지 않는다

  * tail 30~50줄 정도가 적당(모델이 읽을 수 있어야 함)

---

## 5.5 Failure Signature: 게이트 결과를 “수리 가능한 코드”로 요약

게이트가 반환하는 원문 오류 메시지는 그대로 중요합니다. 하지만 운영/라우팅을 위해서는 “요약 코드”가 필요합니다. 그게 **Failure Signature**입니다.

### 시그니처의 목적

* 같은 실패 반복(고정점) 탐지
* 특정 실패에만 Planner 호출
* 특정 실패에만 승격/모델 교체
* 경험치 DB 키로 사용

### 시그니처 설계 규칙

* 결정론적으로 생성 가능해야 함(규칙 기반)
* 너무 세분화하지 말고 운영 가능한 수준으로

예시(개조식)

* `syntax_error`
* `constraint_no_imports`
* `missing_separators`
* `too_many_hyphens`
* `punctuation_not_removed`
* `non_ascii_not_removed`
* `pytest_fail`

---

## 5.6 게이트와 프롬프트의 관계: “게이트가 프롬프트를 짧게 만든다”

FineDev는 프롬프트에 모든 규칙을 넣지 않으려 합니다. 대신:

* 규칙 일부는 게이트가 강제하고
* 실패하면 그때 필요한 정보만 repair prompt에 주입합니다.

이 방식이 중요한 이유:

* 작은 모델은 긴 프롬프트에서 흔들림
* “사전에 장황하게 설명”하는 것보다
  “실패 후 딱 필요한 수정 지시”가 더 잘 먹힘

즉, 게이트는 단순 검증기가 아니라 **프롬프트 최소화 장치**입니다.

---

## 5.7 게이트 설계 체크리스트(실무용)

개조식으로 고정해두면 유용합니다.

* [ ] 각 게이트는 결정론적인가?
* [ ] 게이트 순서는 “싼 것부터”인가?
* [ ] 실패 메시지가 모델이 행동 가능한 정보인가?
* [ ] 실패 메시지가 너무 길지 않은가?
* [ ] 정책 위반은 테스트 전에 컷되는가?
* [ ] 환경/패키징 실패를 모델 실패로 오판하지 않게 분리했는가?
* [ ] failure signature가 라우팅/DB에 쓰일 만큼 안정적인가?
* [ ] 프롬프트에 과도한 규칙을 넣지 않고, 게이트/수리로 분배했는가?

---

## 5.8 이 장의 결론

FineDev에서 게이트 설계는 단순한 “검사 단계”가 아니라:

* 실패 원인을 분해하여 모델 오판을 막고,
* 프롬프트를 최소화하며,
* 수리 루프가 수렴하도록 피드백을 구조화하는

**핵심 설계 영역**입니다.

다음 6장에서는 “프롬프트 최소·명료” 원칙을 구체화합니다. 즉, 어떤 정보를 스펙/프롬프트에 넣고, 어떤 정보를 게이트/수리 단계로 미뤄야 하는지, 그리고 작은 모델(4b)이 흔들리지 않도록 프롬프트를 어떻게 설계해야 하는지를 다룹니다.

-----
-----

# 6장. 프롬프트 설계 원칙

FineDev에서 프롬프트는 “모델에게 모든 규칙을 주입하는 계약서”가 아니라, **최소한의 정보로 후보를 만들게 하고**, 나머지는 **결정론적 게이트 + 수리 루프**가 수렴시키도록 설계합니다. 이 장은 그 이유와 원칙, 그리고 이번/이전 실험에서 실제로 효과가 있었던 패턴을 정리합니다.

---

## 6.1 FineDev 프롬프트 철학: “설명은 줄이고, 판정은 늘린다”

일반적인 프롬프트 접근은 이렇게 흐르기 쉽습니다.

* 실패가 나면 → 규칙을 더 붙인다
* 또 실패하면 → 예외 규칙을 더 붙인다
* 또 실패하면 → 형식/스키마/출력 제약을 더 붙인다

그 결과:

* 프롬프트가 길어지고
* 사람이 보기에도 복잡해지고
* 작은 모델(4b)은 더 흔들리고
* 모델이 “규칙을 지키는 척”하면서 엉뚱한 출력을 내기 쉽습니다.

FineDev는 반대로 갑니다.

* 프롬프트는 **짧고 명료하게**
* 애매한 규칙은 **게이트로 판정**
* 필요할 때만 **수리 프롬프트에 딱 필요한 만큼** 주입

즉, FineDev의 프롬프트는 “한 번에 완성”이 아니라 “수렴 루프의 입력”으로 설계됩니다.

---

## 6.2 프롬프트는 3종으로 나뉜다: Gen / Repair / Plan

FineDev는 역할에 따라 프롬프트를 분리합니다. (이 분리가 모델 부담을 크게 줄입니다.)

### 1) Gen Prompt (첫 생성)

* 목적: “정상 후보를 빠르게 생성”
* 포함: 시그니처, 핵심 목적, examples 몇 개, 최소 제약
* 배제: 장황한 규칙, 장기 품질 요구, 스타일 강제

### 2) Repair Prompt (수리/재작업)

* 목적: “실패 원인에 딱 맞춰 최소 변경”
* 포함: 실패 메시지, edit directives, 이전 코드, 동일 examples/제약
* 원칙: **지시가 늘어날수록 흔들리므로**, 지시문은 짧고 구체적으로

### 3) Plan Prompt (옵션: 수정 지시 생성)

* 목적: “고정점에서 탈출하기 위한 수정 전략 요약”
* 출력: 코드가 아니라 **수정 지시(불릿)**만
* 장점: Producer에 들어가는 텍스트를 줄이고 명확화

이번 세션에서도 “프롬프트 전문 로깅”을 붙인 이유가,
이 3종 프롬프트를 각각 개선하기 위함입니다.

---

## 6.3 ‘최소·명료’ 원칙: 무엇을 넣고, 무엇을 빼야 하나

### 반드시 넣는 것(우선순위 높음)

1. **시그니처(정확히)**
2. **입출력 예시(examples) 2~6개**
3. **목적 한 줄(purpose)**
4. **치명적 제약 1~3개(가능하면 결정론적 판정 가능한 것)**

### 가급적 빼는 것(또는 notes로 약하게)

* 코드 스타일/클린코드/리팩터링 요구
* 장황한 “금지 목록” (특히 4b에 불리)
* 복잡한 출력 포맷(JSON, 스키마) 강제 (코딩 과제에서는 오히려 실패 유발)
* “반드시/절대/항상” 같은 문장 남발 (모델이 과잉 보정하기 쉬움)

**실험에서 관측된 패턴**

* slugify 같은 과제에서 “규칙을 너무 많이” 주면,

  * 4b는 흔들려서 아예 다른 구현으로 튀거나,
  * 규칙을 지키는 척하며 `h-e-l-l-o-...` 같은 과잉 보정을 하기도 했습니다.
* 반대로 examples 중심으로 주면,

  * “정답 모양”에 더 빨리 수렴했습니다.

---

## 6.4 예시(Examples)는 프롬프트의 핵심이자 ‘가장 강한 레버’

FineDev에서 examples는 단순 힌트가 아니라:

* 모델에게는 “학습 샘플”
* 시스템에게는 “결정론적 검사”
  로 동시에 작동합니다.

### examples 설계 요령

* 2개는 너무 약하고, 10개는 길어집니다.
* 보통 4~8개 정도가 “정보량 대비 안정성”이 좋습니다.
* 엣지 케이스는 examples로 주면 제일 강하게 잡힙니다.

  * 빈 문자열, 공백만, 유니코드/특수문자, 연속 구분자 등

### 이 세션 사례(의미)

* 하이픈 누락(helloworld) → examples에서 바로 적발
* 과잉 하이픈(h-e-l-l-o…) → examples에서 바로 적발
* 구두점/비ASCII 처리 누락 → examples에서 바로 적발

즉, examples는 “프롬프트를 길게 쓰지 않고도” 규칙을 강제하는 장치입니다.

---

## 6.5 제약(Constraints)은 “많이”가 아니라 “판정 가능한 것만”

당신이 강조한 포인트가 여기서 중요합니다.

* 제약을 계약처럼 넣기 시작하면 끝이 없다.
* 휴리스틱/애매한 것은 Audit로 분리해야 한다.
* 계약은 결정론적으로 판정 가능해야 한다.

따라서 constraints는 다음처럼 설계합니다.

### 좋은 constraints 예(결정론적)

* import 사용 금지
* 특정 함수 호출 금지
* 출력은 `[a-z0-9-]`만 허용
* 공백 연속은 `-` 하나로 축약

### 나쁜 constraints 예(휴리스틱)

* “깨끗하게 구현하라”
* “효율적으로 구현하라”
* “가독성 좋게”
* “최적의 방법으로”

이런 건 프롬프트에 넣으면 모델을 흔들고, 게이트로도 판정이 애매합니다.
→ Audit(옵션) 단계가 맞습니다.

---

## 6.6 Repair 프롬프트의 핵심: “실패 메시지 + 최소 수정 지시”

Repair에서 가장 흔한 실패는 두 가지입니다.

1. 지시가 너무 길어져 모델이 오해/환각을 일으킴
2. 지시가 너무 약해 같은 실패를 반복(고정점)

FineDev는 이 균형을 다음 방식으로 맞춥니다.

### (A) 실패 메시지는 ‘원문 그대로’ 전달

* compile 에러, mismatch, pytest 실패 로그는 원문을 최대한 보존
* 단, 길이는 tail로 제한

### (B) edit directives는 “짧고 행동 가능한 문장”으로

좋은 지시 예:

* “문자 사이에 하이픈을 넣지 말고, 토큰 사이에만 넣어라.”
* “구두점은 제거하고, 영숫자만 유지하라.”
* “입력이 공백뿐이면 빈 문자열을 반환하라.”

나쁜 지시 예:

* “더 잘 구현해라”
* “정확하게”
* “규칙을 모두 지켜라”

### (C) 최소 변경(minimal diff) 요구

Repair에서는 다음 문장이 효과가 큽니다.

* “가능하면 기존 코드 구조를 유지하고 필요한 부분만 수정하라.”

특히 작은 모델에서 “전체를 다시 쓰기”는 더 흔들립니다.

---

## 6.7 프롬프트가 길어질 때의 ‘수렴 붕괴’ 패턴과 대응

### 붕괴 패턴 1: 규칙을 문자 단위로 해석(과잉 보정)

* 예: `h-e-l-l-o- -w-o-r-l-d`
* 원인: “하이픈을 넣어라”를 가장 단순 단위(문자)로 만족시켜버림

대응:

* “하이픈은 토큰 사이에만” 같은 **반례 지시**를 짧게 추가
* examples로 “문자 사이 하이픈”을 명확히 실패하게 만들기

### 붕괴 패턴 2: 규칙을 무시하고 습관적 해결로 회귀(import re)

* 원인: 모델의 고정된 레시피(regular expression)로 돌아감

대응:

* 제약은 프롬프트가 아니라 **시스템 게이트로 강제**
* “의존 탐지” 후 재구현 라우팅(말로 설득하지 않음)

### 붕괴 패턴 3: 프롬프트가 너무 길어 핵심을 놓침

* 긴 계약서/옵션/예외가 들어가면 4b가 특히 흔들림

대응:

* 프롬프트를 짧게 유지하고
* Audit/옵션을 분리
* 필요 시 Planner로 “지시 요약”만 주입

---

## 6.8 출력 형식(Structured Output)은 ‘코딩’에선 신중히 써야 한다

이전 실험에서:

* `--format raw`에서 JSON parse 실패가 다수
* `--format schema`도 문법/구조 안정성이 모델 크기에 민감

이 경험이 말해주는 건,
코딩 과제에서 “구조화된 출력”은 양날의 검이라는 점입니다.

* 구조화 출력은 시스템 연결엔 좋지만
* 작은 모델에겐 부담이 커지고
* 결국 “코드 생성 성공률”을 떨어뜨릴 수 있습니다.

FineDev의 기본 권장:

* 코딩 결과물은 **코드만** 받는다(extract gate)
* 구조화된 메타 정보(설명/요약/계획)는 **옵션 플로우**로 분리(Planner)

---

## 6.9 프롬프트 개선을 위한 실험 운영: “프롬프트를 로그로 남겨야 한다”

이번 세션에서 “프롬프트 전문 로깅”을 붙인 건, FineDev 프롬프트 설계의 핵심 원칙을 반영합니다.

* 프롬프트는 감으로 튜닝하면 끝이 없음
* 실패 유형별로 어떤 문장이 효과가 있었는지 데이터로 남겨야 함
* 결국 경험치 DB(실패 시그니처 → 성공한 지시/패치)로 이어짐

즉, FineDev에서 프롬프트는 “한 번 쓰고 끝”이 아니라,
**측정→개선→축적 대상**입니다.

---

## 6.10 이 장의 결론(요약)

FineDev의 프롬프트 원칙은 다음으로 요약됩니다.

* **Gen은 최소**: 시그니처 + examples + 핵심 제약만
* **Repair는 정밀**: 실패 메시지 + 짧은 수정 지시 + 이전 코드
* **제약은 게이트로 강제**: 프롬프트 설득에 의존하지 않음
* **고정점은 라우팅**: Planner/승격/리라이트로 탈출
* **프롬프트는 로그로 튜닝**: 경험치 DB로 축적

# 7장. 모델 크기/계열별 관찰 (4b ↔ 12b ↔ 대형 LLM)

이 장은 “어떤 모델이 더 좋다”를 말하려는 장이 아닙니다. FineDev 관점에서 중요한 것은 **모델의 평균 성능**이 아니라, **실험 공정 안에서 어떤 종류의 실패가 어떤 빈도로 발생하는지**, 그리고 **그 실패가 공정(게이트/수리/승격)으로 얼마나 관리 가능한지**입니다.
즉, 이 장의 결론은 “모델 비교표”가 아니라, **모델 크기/계열에 따른 운영 전략**으로 귀결됩니다.

---

## 7.1 관찰의 전제: 모든 모델은 ‘단순 실수’를 한다

이전 세션에서 gemma3:4b, gemma3:12b, qwen3-coder:480b-cloud를 돌리며 가장 강하게 남은 인사이트는 이것입니다.

* **모델 종류/크기와 무관하게**

  * 문법/형식/규약 같은 “작은데 치명적인” 오류가 발생한다.
* 특히 사람 입장에서는 “이걸 왜 틀리지?” 싶은 부분에서 틀린다.
* 따라서 “대형 모델이면 안전”이라는 가정은 실험적으로 성립하지 않았다.

FineDev는 이 전제를 받아들입니다.

> 모델은 완벽하지 않다 → 그래서 공정이 필요하다.

이 전제가 있어야, 모델 선택을 “신앙”이 아니라 “운영 정책”으로 다룰 수 있습니다.

---

## 7.2 4b급(로컬 SLM)에서 두드러진 특성

4b는 이번/이전 실험에서 **가장 중요한 분기점**이었습니다. 단순히 “성능이 낮다”보다, **불안정성이 드러나는 축이 명확**했습니다.

### 7.2.1 4b의 대표 실패 축

1. **출력 안정성 문제**

* raw 출력에서 JSON 깨짐, 스키마 미준수
* 코드도 “완성되긴 했는데 끝이 잘리거나” “들여쓰기가 깨지는” 케이스

2. **프롬프트 길이 민감**

* 규칙/조건이 길어질수록 흔들림
* “장황한 계약서”를 주면 오히려 실패율이 올라감

3. **규약 준수의 취약함**

* “import 하지 마라” 같은 금지 규칙을 무시하는 경우가 반복적으로 발생
* 작은 모델은 익숙한 레시피(정규식 import 등)로 회귀하는 경향

4. **고정점(stuck loop)**

* 같은 오해를 반복하거나
* 지시를 과잉 해석해 엉뚱한 방식으로 만족시키는 현상

  * 예: 하이픈을 단어 사이가 아니라 문자 사이에 끼워 넣기

### 7.2.2 4b 운영 전략(FineDev 관점)

4b는 “안 된다”가 아니라, 다음 조건에서 **가치가 폭발**합니다.

* **작업 단위를 작게**(함수 단위, 200라인 전후)
* **프롬프트를 최소화**
* **examples 중심**으로 유도
* **결정론적 게이트**로 빠르게 컷
* 고정점 반복 시 **승격/역할 분리** 트리거

즉, 4b는 FineDev의 “기본 생산 엔진”이 될 수 있습니다.
다만 “마지막 1%”를 4b 단독으로 매번 해결하려고 하면, 비용이 시도 횟수로 새어나갑니다. 그 지점이 승격 정책의 필요성입니다.

---

## 7.3 12b급(중형 SLM)에서 관찰된 점: 실용권 진입

이전 실험에서 gemma3:12b는 4b와 비교해 **성공률이 급격히 달라지는 분기점**이었습니다.

### 7.3.1 12b에서 개선된 영역

* `json_parse`, `code_import`, `tests` 통과가 대폭 개선
* experiment2(소형 함수들)는 “거의 전부 통과” 수준
* 즉 “SLM이라서 안 된다”가 아니라,

  * **4b는 불안정하지만 12b는 실용권**이라는 강한 근거가 생김

### 7.3.2 12b에서도 남는 문제

* 500~1000라인급에서는

  * syntax_ok가 깨지거나
  * 완성 자체가 불안정
  * 시간도 급증
* context/num_predict를 늘리면 오히려

  * 지연/실패/OOM/서버 불안정 리스크 증가

즉, 12b는 “함수 단위 개발”에서는 매우 강하지만,
“큰 파일 1회 생성”의 문제를 근본적으로 해결하지는 못했습니다.

### 7.3.3 12b 운영 전략

* 4b가 생산하되 고정점에 빠지면 12b로 승격
* 또는:

  * Producer=4b
  * Planner/Fixer=12b
    같은 **역할 분리**가 매우 유효할 가능성이 큼

특히 이번 세션에서도 planner를 4b로 돌리니 고정점 탈출이 제한적이었는데,
planner/fixer를 12b로 올리면 “지시 품질”이 올라가 수렴이 빨라지는 구조가 됩니다.

---

## 7.4 대형 LLM(예: 480b급 포함)에서 관찰된 점: “실수는 남고, 형태가 바뀐다”

대형 모델은 평균적으로 더 잘합니다. 그런데 이번 논의에서 중요한 관찰은:

* 큰 모델도 **사소하지만 치명적인 실수**를 한다.
* 실수의 ‘근원’은 유사하지만, ‘형태’가 바뀐다.

### 7.4.1 대형 모델의 전형적 실수 형태

* 아주 작은 오타(예: from **future** 오타 같은 치명적 한 줄)
* 규약/요구 해석의 미세한 어긋남
* “설명은 완벽한데 코드가 한 줄 틀림”
* 출력 형식은 그럴듯한데 실행이 안 되는 사소한 결함

이게 왜 더 위험하냐면:

* 사람은 큰 모델 결과를 더 신뢰하기 쉬워서
* 작은 결함을 놓치기 쉽고
* 그대로 배포/통합되면 비용이 더 커질 수 있습니다.

즉, 큰 모델은 “더 적게 틀리지만, 틀리면 더 교묘하게 틀릴 수 있다”는 운영 리스크가 있습니다.

### 7.4.2 대형 모델의 운영 전략

대형 모델은 FineDev에서 다음 역할에 최적입니다.

* 고정점 탈출(플래너/리뷰/수정 전략 제시)
* 대형 리팩터/설계 변경(큰 구조 수정)
* 긴 컨텍스트 통합(다수 모듈을 한 번에 이해해야 하는 작업)

하지만 여전히:

* 최종 산출물은 게이트(compile/tests/constraints)를 통과해야 하고,
* 단발 생성만으로 신뢰하면 안 됩니다.

---

## 7.5 “왜 다 비슷하게 실수하나?”에 대한 FineDev식 해석

당신이 느낀 충격(480b도 바보 같은 실수)은 중요한 시사점이 있습니다.

FineDev 관점에서 이 현상은 “모델 한계”라기보다 **업무 과제의 성격**에서 옵니다.

* 코딩은 확률적으로 그럴듯한 텍스트 생성이 아니라,
* **규약/형식/환경**이라는 ‘외부 제약’과 맞물려야 하며,
* 작은 실수도 즉시 실패로 연결됩니다.

모델이 아무리 좋아도:

* “한 줄 오타” 확률을 0으로 만들기는 어렵고,
* “요구 해석의 미세한 차이”도 사라지지 않습니다.

그래서 FineDev는:

* 실수 자체를 0으로 만들려 하기보다,
* **실수를 감지하고 수리하는 공정**을 핵심 가치로 둡니다.

---

## 7.6 모델 크기별 FineDev 권장 운영 정책(요약)

### 기본 권장(현실적인 하이브리드)

* **Producer(대량 생산)**: 4b (저비용, 함수 단위)
* **Planner/Fixer(고정점 탈출)**: 12b (또는 더 큰 모델)
* **Escalation(예외 처리)**: 대형 LLM(클라우드) — 정말 어려운 케이스만

### 승격 트리거 예시

* 동일 failure signature 2회 이상 반복
* attempt 3 이상에서 examples mismatch 유형이 변하지 않음
* constraints 위반 반복(import 금지 등)
* 실행 시간/타임아웃/서빙 불안정 감지

이 정책의 목적은 간단합니다.

* 대부분은 4b로 처리하고
* “마지막 1%”만 상위로 처리해서
* 비용을 통제하면서 신뢰성을 확보한다

---

## 7.7 이 장의 결론

이 장의 결론은 “12b가 좋다” 같은 단순 비교가 아닙니다.

1. **모든 모델은 실수한다** → 그래서 게이트/수리/승격이 필수
2. **4b↔12b는 실용성 분기점**이 될 수 있다(특히 함수 단위)
3. **대형 모델도 오케스트레이션 없이는 업무용 안정성을 보장하지 못한다**
4. 따라서 FineDev의 경쟁력은 모델이 아니라 **운영 정책(분해+수렴+승격)**에 있다

# 8장. 길이 축(200라인 vs 500~1000라인)과 난이도 분리

이 장은 FineDev에서 매우 중요한 결론 하나를 확정합니다.

> **“코드가 길어지는 것”은 단순히 같은 문제의 스케일업이 아니라, 난이도 축이 바뀌는 것이다.**

즉 200라인짜리 함수/모듈을 잘 만드는 능력과, 500~1000라인짜리 단일 파일을 한 번에 안정적으로 생성하는 능력은 **같은 능력의 연장선이 아닐 수 있습니다.** 이전 실험과 이번 세션의 관찰은 이 분리를 강하게 지지합니다.

---

## 8.1 왜 ‘길이’는 별도의 난이도 축인가

짧은 코드(예: 함수 단위)는 실패해도 대개 다음 중 하나로 귀결됩니다.

* 문법 오류(compile/ast에서 잡힘)
* 예시 불일치(examples mismatch)
* 제약 위반(import 금지 등)

즉, **실패 원인과 수정 방향이 비교적 명확**합니다.

하지만 500~1000라인 같은 “단일 대형 파일”은 실패가 달라집니다.

* 문법이 깨지는 빈도가 증가(들여쓰기 붕괴, 블록 미종결)
* 코드가 중간에 끊김(완결성 붕괴)
* 내부 일관성 붕괴(함수/클래스 참조 불일치, 변수명 혼선)
* “한 부분을 고치면 다른 부분이 망가지는” 연쇄 효과
* 생성 시간/토큰이 늘어 운영 리스크가 급증(타임아웃, 서버 불안정)

즉, 단순히 “더 길다”가 아니라 **시스템/운영/일관성 문제**가 본격적으로 지배하는 영역으로 바뀝니다.

---

## 8.2 대형 단일 파일 생성이 특히 불리한 이유(실험 기반 해석)

### 8.2.1 완결성(Completion) 실패 확률이 급격히 증가

길이가 늘면 모델이 “끝까지 완성”해야 할 양이 늘어나고, 다음 현상이 잦아집니다.

* 마지막 함수/클래스가 미완성
* 괄호/따옴표/블록이 닫히지 않음
* 도중에 “설명/주석”으로 빠져버림
* 코드가 끊겨서 compile 단계에서 즉시 실패

이런 실패는 200라인 내외에서는 비교적 적지만,
1000라인에 가까워지면 “거의 시스템적 현상”처럼 증가합니다.

### 8.2.2 장거리 일관성(Long-range consistency) 문제가 커짐

긴 코드에서는 초반에 정의한 구조를 끝까지 일관되게 유지해야 합니다.

* 이름 규칙(함수/클래스/변수)
* 모듈 구조
* 상태 관리(전역/클래스/인스턴스)
* 타입/데이터 구조

모델은 중간중간 “그럴듯한 다른 선택지”로 갈아타기 쉽고,
길이가 길어질수록 **이 일관성 붕괴의 기회가 늘어납니다.**

### 8.2.3 디버깅/수리 비용이 급증한다

FineDev는 수리 루프를 돌립니다. 그런데 대상이 1000라인이면:

* 실패 원인을 찾는 비용이 커짐(로그가 길어짐)
* 모델에게 주는 피드백(실패 로그 + 코드)이 길어짐
* 프롬프트가 길어져 작은 모델이 흔들림
* “부분 수정”보다 “전체 재작성”이 빈번해져 오히려 악화

즉, 길이가 늘면 수리 루프의 경제성이 떨어지고, 수렴이 어려워집니다.

---

## 8.3 컨텍스트/출력 길이를 늘리면 해결될까? (실험에서 본 반례)

이전 실험에서 `num_ctx`를 키우고 `num_predict`를 크게 주면 “긴 코드도 되지 않을까?”를 시도했는데, 여기서 매우 중요한 관찰이 나왔습니다.

* `num_ctx 16384`, `num_predict 8000` 같은 설정에서는

  * **10분 단위 지연**
  * 결과 없음 / JSON parse 실패
  * OOM/서버 불안정 가능성 증가

즉, 컨텍스트를 늘리는 건 마법이 아닙니다.

### 길이를 늘릴수록 폭발하는 리스크(개조식)

* 추론 시간이 선형 이상으로 증가(특히 로컬/서빙 환경)
* 중간 실패 시 재시도가 비싸짐
* 서버가 불안정해지면 “모델 성능”을 측정할 수 없음
* 실험 러너가 타임아웃/HTTP 에러를 빈번히 맞음

따라서 FineDev는 “긴 컨텍스트로 한 방”을 기본 전략으로 채택하지 않습니다.

---

## 8.4 FineDev의 결론: “긴 파일 1회 생성” 대신 “작게 쪼개서 조립”이 기본

이 장의 결론은 Micro Orchestration으로 자연스럽게 연결됩니다.

### 8.4.1 길이 축을 다루는 기본 전략

* **함수 단위(function=file)**로 쪼갠다
* 카탈로그(의존 함수 목록)에서 필요한 것만 선택 주입한다
* topo 순서로 빌드한다
* 각 유닛은 200라인 내외를 목표로 한다

### 8.4.2 왜 이것이 길이 문제를 해결하는가

* 각 유닛은 짧아서 완결성/문법 안정성이 올라감
* 일관성 문제는 “유닛 내부”로 제한됨
* 수리 루프는 짧아져 비용이 낮음
* 실패가 발생해도 전체가 아니라 해당 유닛만 고치면 됨
* 결과적으로 대형 프로젝트도 “전기세만 늘어나는 구조”에 가까워짐

---

## 8.5 “그럼 500~1000라인은 절대 안 되나?” — FineDev의 실용적 입장

FineDev는 “안 된다”라고 단정하기보다, **그 과제가 다른 전략을 요구한다**고 봅니다.

### 8.5.1 500~1000라인이 가능한 경우

* 이미 템플릿/스캐폴딩이 있고, 모델은 “채우기”만 하는 경우
* 파일 구조가 고정되어 있고, 변경 범위가 제한된 경우
* 코드 생성이 아니라 “코드 변환/리팩터링”처럼 국소 변경인 경우

### 8.5.2 500~1000라인이 어려운 경우

* 백지 상태에서 단일 파일을 한 방에 완성해야 하는 경우
* 설계/요구가 애매한 상태에서 길게 설명해야 하는 경우
* 로컬 SLM 환경에서 긴 컨텍스트/긴 출력이 필요한 경우

따라서 FineDev의 운영 정책은:

* 200라인 전후: SLM 중심으로 다량 생산
* 500라인 이상:

  * 가능한 한 분해해서 여러 유닛으로 만들고,
  * 정말 단일 파일이어야 하면 상위 모델/다단계 생성/템플릿 기반으로 간다

---

## 8.6 길이 축을 KPI로 바꾸면 무엇이 보이나

FineDev가 길이 축을 “난이도 분리”로 보는 이유는, 운영 KPI가 완전히 달라지기 때문입니다.

### 200라인 유닛 KPI 예

* pass@k
* 평균 attempt 수
* examples mismatch 유형 분포
* 제약 위반률

### 1000라인 단일 파일 KPI 예

* 평균 생성 시간
* 완결성(끝까지 생성) 비율
* 컴파일 성공률
* 내부 참조 일관성 오류율
* 타임아웃/서빙 실패율

즉, 길이가 커지면 “코드 품질”보다 먼저 **운영 안정성 지표**가 핵심이 됩니다.

---

## 8.7 이 장의 결론(요약)

1. 200라인과 1000라인은 같은 문제의 스케일업이 아니라, 난이도 축이 바뀐다.
2. 긴 파일 1회 생성은 완결성/일관성/운영 리스크가 급증한다.
3. 컨텍스트/출력 길이 증가는 만능이 아니며, 로컬 환경에서는 실패 비용이 폭발한다.
4. 따라서 FineDev의 기본 전략은 “한 방 생성”이 아니라 **Micro Orchestration(분해·조립)**이다.
5. 500~1000라인이 필요하면 템플릿/다단계/상위 모델 등 별도 전략으로 다룬다.

# 9장. 시스템/서빙 이슈가 성능을 오판하게 만드는 사례

이 장은 FineDev의 “운영 철학”을 결정한 핵심 경험을 정리합니다. 요약하면:

> 많은 실패는 모델이 못해서가 아니라, **서빙/요청 포맷/러너/로깅/패키징** 같은 시스템 계층에서 발생했고,
> 이를 분해·기록하지 않으면 우리는 모델을 쉽게 오판한다.

이 장은 그래서 “모델 성능 비교”가 아니라, **실험 시스템을 어떻게 설계해야 모델을 공정하게 평가하고, 실제 개발 공정으로 전환할 수 있는지**를 다룹니다.

---

## 9.1 왜 시스템 이슈가 치명적인가: 실패 원인을 ‘모델 탓’으로 귀속시키기 쉽다

AI 코딩 실험에서 실패가 발생하면, 사람은 자연스럽게 이렇게 결론 내리기 쉽습니다.

* “모델이 못한다”
* “SLM이라서 안 된다”
* “이 프롬프트로는 불가능하다”

하지만 실제로는 아래가 더 흔합니다.

* 요청 파라미터가 잘못되어 모델이 정상 동작하지 않음
* 출력 포맷 처리(스키마/JSON)가 깨져서 이후 단계가 전부 막힘
* 러너(import/test)가 잘못되어 코드가 맞아도 실패
* 서버는 에러를 냈는데 클라이언트가 에러 바디를 기록하지 않아 원인 불명

이 상황에서 “실패율”은 모델 품질을 의미하지 않고, **시스템 결함의 확률**을 의미하게 됩니다. 즉 측정 자체가 무너집니다.

FineDev는 이 문제를 해결하려고 **게이트/로깅/재현성**을 최상위 요구사항으로 둡니다.

---

## 9.2 사례 A: PAD_END만 출력되는 현상 — 모델 문제가 아니라 런타임/서빙 문제 가능성

이전 실험에서 관찰된 현상:

* 응답이 `PAD_END` 한 줄만 나오고
* 매우 빨리 종료되는 패턴

이런 현상은 보통 모델이 “내용을 못 만들었다”라기보다 아래 가능성이 큽니다.

### 가능 원인(서빙 계층)

* 요청 파라미터가 비정상이라 모델이 즉시 종료 토큰으로 빠짐
* format/schema 처리 오류로 출력이 잘려서 기록됨
* 서버 내부 에러가 났지만 클라이언트가 에러를 정상적으로 수집 못함
* 토큰/컨텍스트/stop 설정이 잘못되어 의도치 않게 즉시 stop

### FineDev적 교훈

* “출력이 이상하다”는 것은 모델의 창의성 문제가 아니라,

  * 요청/서빙 파라미터,
  * 포맷 핸들링,
  * 에러 핸들링
    을 먼저 의심해야 한다.
* 이걸 분리하지 못하면, 모델에 대한 판단이 즉시 왜곡된다.

---

## 9.3 사례 B: HTTP 500 — ‘서버가 죽었다’가 아니라 ‘요청이 틀렸다’

이전 실험에서 매우 결정적이었던 사례입니다.

### 겉으로 보이는 현상

* HTTP 500이 발생
* 실험자는 “서버가 죽었나?” / “모델이 불안정하네?”라고 생각하기 쉬움

### 실제 원인(핵심)

* `format=schema`에서 JSON Schema를 **문자열로 전달**함
* Ollama가 기대한 것은

  * `"json"` 또는
  * **유효한 JSON Schema object**
* 따라서 서버가 반환한 실질 에러는:

  * `expected "json" or a valid JSON Schema object`

### 왜 처음에 몰랐나

* 러너가 에러 바디(response body)를 기록하지 않아서
* 500이라는 숫자만 보고 추측하게 됨

### 해결과 교훈

* 응답 body를 기록하도록 고치자 즉시 원인이 드러남
* 즉, 500은 “모델 문제”가 아니라 “클라이언트의 요청 포맷 문제”였다

**FineDev의 원칙이 여기서 확정됩니다.**

* 네트워크/서빙 에러가 나면:

  1. 상태 코드만 보지 말고
  2. 반드시 에러 바디를 저장하고
  3. 재현 가능한 형태로 로그를 남겨라

---

## 9.4 사례 C: 실험 러너의 설계 결함이 모델을 오판하게 만든다 (import/test 경로 문제)

이번 세션에서도 유사한 성격의 문제가 있었습니다.

### 현상

* pytest에서 `ModuleNotFoundError: No module named 'mypkg'`
* 얼핏 보면 “모델이 import를 잘못했나?”처럼 느껴질 수 있음

### 실제 원인

* 패키지가 editable install(-e)로 설치되지 않아 테스트가 모듈을 못 찾은 것
* 즉 코드가 맞든 틀리든, 환경이 실패하도록 구성되어 있었음

### 교훈

* “코드가 맞는데 실행이 안 됨”은 모델 문제보다

  * 패키징,
  * 설치,
  * import 경로,
  * `__init__.py`,
  * 테스트 러너 설정
    문제일 가능성이 매우 크다.

이 때문에 FineDev는 “코드 생성” 이전에

* 프로젝트 스캐폴딩과 실행 경로를 고정하고,
* import/export를 자동화하며,
* 환경 검증 게이트(import gate)를 두는 것을 권장합니다.

---

## 9.5 시스템 이슈를 줄이기 위한 FineDev의 운영 원칙

위 사례들은 모두 “로깅이 부실하면 모델을 오판한다”로 수렴합니다. 따라서 FineDev는 아래를 **필수 운영 규칙**으로 둡니다.

### 9.5.1 요청/응답 전문 로깅(특히 에러 바디)

* 서버 호출 시:

  * 요청 파라미터(모델명, 포맷, 옵션)
  * 응답 내용(성공/실패)
  * 실패 시 에러 바디(필수)
* 이를 남겨야 “서버가 죽었는지, 요청이 틀렸는지”를 즉시 구분 가능

### 9.5.2 단계별 실패 원인 분해 로그

* generate 성공/실패
* extract 성공/실패
* compile 성공/실패
* constraints 성공/실패
* examples 성공/실패
* pytest 성공/실패

이렇게 분해하면

* “모델이 못함”이 아니라
* “어느 단계에서 무엇이 깨졌는지”로 말할 수 있습니다.

### 9.5.3 재현 가능한 실행(Determinism of Evaluation)

* 모델 출력은 확률적이지만,
* 평가(게이트)는 결정론적이어야 합니다.
* 게이트가 불안정하면 실험이 의미 없고, 개선 방향도 안 보입니다.

---

## 9.6 “모델 실패”와 “시스템 실패”를 분리하는 기준

FineDev에서는 실패를 크게 두 분류로 나눕니다.

### 1) 모델 실패(Model-side)

* 문법/로직/요구 오해
* examples mismatch
* 테스트 실패

→ 수리 루프(Repair/Planner/승격)로 개선 가능

### 2) 시스템 실패(System-side)

* HTTP 500/타임아웃/OOM
* 스키마/포맷 전달 오류
* 러너(import 경로/설치) 오류
* 로그 미기록으로 원인 불명

→ 모델이 고칠 수 없으며, 시스템을 먼저 고쳐야 함

이 분리 원칙이 없으면, “재작업”은 오히려 실패 비용만 늘립니다.
(모델이 통제할 수 없는 실패에 모델을 투입하는 셈)

---

## 9.7 이번 세션에서 추가된 진전: “프롬프트 전문 로깅”의 의미

이번 세션에서 사용자 요청으로 추가된 개선이 하나 있습니다.

* 각 attempt에서 사용된 프롬프트(gen/repair/planner)를 runs.jsonl에 저장

이것이 왜 중요한가?

* 시스템 실패를 제거한 뒤에는, 남는 실패는 대부분 “프롬프트/지시 해석/수리 지시 품질” 문제입니다.
* 프롬프트 전문이 없으면, 우리는 또다시 추측하게 됩니다.
* 프롬프트 전문이 있으면:

  * 어떤 문장이 모델을 흔들었는지,
  * 어떤 지시가 고정점을 만들었는지,
  * 어떤 repair가 과잉 보정을 유발했는지
    를 실험적으로 추적할 수 있습니다.

즉, FineDev는 “모델 튜닝” 이전에 “프롬프트/공정 튜닝”이 가능해집니다.

---

## 9.8 이 장의 결론(요약)

1. 실험 실패의 상당 부분은 모델이 아니라 **시스템/서빙/러너**에서 발생한다.
2. 에러 바디/단계별 로그가 없으면, 실패는 쉽게 모델 탓으로 오판된다.
3. PAD_END, HTTP 500, import 경로 문제는 모두 “모델 문제처럼 보이지만 시스템 문제”인 대표 사례다.
4. FineDev는 그래서 **결정론적 게이트 + 로깅/재현성**을 최우선 설계 원칙으로 둔다.
5. 모델에게 맡길 수 없는 실패(시스템 실패)를 먼저 제거해야 수리 루프가 의미가 있다.

# 10장. FineDev 아키텍처(전체 구조)

이 장은 FineDev를 “한 장의 그림”으로 설명하는 장입니다. FineDev는 모델을 한 번 호출해서 코드를 얻는 방식이 아니라, **스펙 기반 생산 라인**처럼 동작합니다. 핵심은 두 가지입니다.

* **Micro Orchestration**: 작업을 작은 단위(함수/모듈)로 쪼개서 생산한다.
* **Output Fine Tuning**: 결정론적 게이트와 수리 루프로 마지막 1% 오류를 제거한다.

따라서 전체 아키텍처는 “모델”이 아니라 **파이프라인/정책/로그/DB** 중심으로 설명하는 것이 정확합니다.

---

## 10.1 전체 구조 한눈에 보기(개념적 레이어)

FineDev는 크게 6개의 레이어로 구성됩니다.

1. **Spec Layer (설계/요구의 표준화)**
2. **Build Graph Layer (의존성/조립 구조)**
3. **Generation Layer (Producer 모델 호출)**
4. **Deterministic Validation Layer (게이트)**
5. **Repair & Routing Layer (수리/라우팅/승격)**
6. **Knowledge Layer (실패 시그니처/경험치 DB/Audit 옵션)**

이 레이어들이 합쳐져 “전기세 공장” 같은 반복 생산 구조를 만듭니다.

---

## 10.2 Spec Layer: 설계가 곧 템플릿(그리고 테스트)

### 역할

* FineDev는 “프롬프트”가 아니라 “스펙”을 입력으로 받습니다.
* 스펙은 사람이 읽을 수 있고, 기계가 실행할 수 있습니다.
* 스펙의 examples/constraints는 그대로 게이트로 연결되어 **자동 검증 규칙**이 됩니다.

### 구성요소(권장)

* 식별: name, version
* 인터페이스: signature, types
* 요구: purpose(1~2문장), examples(핵심)
* 계약: constraints(판정 가능한 것만)
* 참조: deps(필요 시), catalog(선행 함수 목록)
* 힌트: notes(짧게)

### 설계 철학

* 스펙을 잘 쓰는 일이 곧 “템플릿을 만든다”는 의미가 됩니다.
* 사용자 말대로, 템플릿을 무한히 준비할 수는 없지만,

  * “설계=템플릿”으로 생각하면
  * 필요한 설계만 잘 해두면 생산이 자동화됩니다.

---

## 10.3 Build Graph Layer: 함수 단위 생산을 가능하게 하는 ‘조립 지도’

Micro Orchestration이 성립하려면 “무엇부터 만들고 무엇을 나중에 만들지”가 정해져야 합니다. 그게 Build Graph(의존성 그래프)입니다.

### 역할

* 함수/모듈 간 의존성(directed edges)을 관리
* topo sort로 빌드 순서를 결정
* 실패한 유닛을 격리해서 전체 공정이 멈추지 않게 함

### 왜 필요한가

* “함수 단위 개발”은, 그 함수가 동작할 환경/의존성이 이미 정의되어 있어야 합니다.
* 이 레이어는 그 설계를 **실행 가능한 조립 순서**로 바꿔줍니다.

---

## 10.4 Generation Layer: Producer 모델의 역할을 좁힌다

FineDev는 Producer에게 모든 걸 맡기지 않습니다.

### Producer의 역할

* 스펙에 따라 후보 코드를 생성
* 단, 이 코드는 “최종 산출물”이 아니라 “검증 대상 후보”입니다.

### 왜 역할을 좁히나

* 작은 모델은 프롬프트가 길어지면 흔들립니다.
* 큰 단위 작업을 주면 완결성/일관성 문제가 커집니다.
* 그래서 Producer는:

  * **짧은 단위**
  * **명확한 인터페이스**
  * **examples 중심**
    으로 후보를 만드는 역할만 하게 합니다.

### 출력 형태

* 기본은 “코드만”
* 구조화 출력(JSON 등)은 코딩 과제에서는 최소화(필요 시 Planner로 분리)

---

## 10.5 Deterministic Validation Layer: 게이트는 ‘수렴 엔진’의 센서

이 레이어는 FineDev의 가장 강한 차별점입니다.

### 역할

* 후보 코드의 품질을 “기계적으로” 판정
* 실패 원인을 단계별로 분해
* 수리 루프에 넣을 수 있는 신호를 생성

### 게이트 구성(권장 순서)

1. extract (코드만)
2. fixup (안전 정규화)
3. syntax/ast (문법)
4. constraints (정책)
5. examples (스펙 검증)
6. import/package (환경 정합)
7. pytest (통합)

### 핵심 원칙

* 게이트는 휴리스틱을 섞지 않는다.
* 실패 메시지는 짧고 구체적이어야 한다.
* “싼 것부터 먼저” 실패시키는 구조여야 한다.

---

## 10.6 Repair & Routing Layer: 고정점에서 탈출하고 pass@k를 올린다

이 레이어가 FineDev를 단발 호출과 구분짓습니다. “수리”는 단순 재시도가 아니라 정책 기반입니다.

### 10.6.1 Repair Loop(수리 루프)

* 실패가 나면, 실패 메시지 + edit directives + 이전 코드를 포함해 재생성/수정
* 목표는 pass@1이 아니라 **pass@k 수렴**입니다.

### 10.6.2 Failure Signature(실패 시그니처)

* 실패 로그를 규칙 기반으로 요약한 타입
* 동일 시그니처 반복 시 “고정점”으로 판단 가능

### 10.6.3 Routing(라우팅)

실패 유형에 따라 대응을 달리합니다.

* `syntax_error` → 문법 교정 지시(짧게) + 재생성
* `constraint_no_imports` → import 의존 탐지 후 재구현 지시 / 또는 승격
* `missing_separators` → 토큰 단위 join 지시(문자 단위 금지)
* `too_many_hyphens` → 과잉 보정 방지 지시
* `system_error(500/timeout)` → 모델 재시도가 아니라 시스템 점검으로 라우팅

### 10.6.4 Promotion/Escalation(승격)

* 고정점 반복 / 난이도 급증 / 시간 초과 등 조건에서

  * 12b 또는 상위 모델로 승격
  * 또는 역할 모델(planner/fixer)을 강화

이번 세션에서 planner를 4b로 돌리니 한계가 보였던 이유가 여기에 있습니다.
planner/fixer의 힘이 일정 수준 이상이어야 고정점 탈출이 빨라집니다.

---

## 10.7 Knowledge Layer: 경험치 DB와 Audit 옵션

### 10.7.1 Experience DB(경험치 DB)

* 실패 시그니처 + 상황 + 성공한 수정 전략을 축적
* 목적:

  * 반복 실패의 비용을 줄임
  * 점점 더 “결정론적인 공정”에 가까워짐
* 장기적으로는:

  * patch 데이터로 실제 모델 fine-tuning까지 연결 가능(진짜 Output 학습)

### 10.7.2 Audit AI(옵션)

* 계약/게이트에 넣기 애매한 품질 요소를 점검
* 예: 스타일, 리팩터링, 보안, 성능, 유지보수성
* 원칙:

  * Audit은 **통과/실패를 강제하지 않는다**
  * 휴리스틱은 계약을 오염시키지 않게 분리한다

---

## 10.8 FineDev의 ‘작동 순서’를 운영 관점에서 다시 정리

FineDev는 실제로는 아래 3단계로 이해하면 가장 쉽습니다.

### 1) Frame (틀을 잡는다)

* 스펙 표준화
* 프로젝트 스캐폴딩/패키징 고정
* 게이트/로그/정책 준비

### 2) Work (모델이 틀 안에서 일한다)

* 함수 단위 생성(Producer)
* 필요 시 최소 카탈로그 주입
* 프롬프트는 최소화

### 3) Finish (검증·수리·승격으로 완성한다)

* 결정론적 게이트로 빠르게 분해
* 수리 루프로 pass@k 수렴
* 고정점이면 승격/플래너/리라이트
* 경험치 DB 축적
* (옵션) Audit AI

이 3단계가 당신이 처음 정리한 “1단계 틀 / 2단계 작업 / 3단계 검증·재작업·승격”을 FineDev 아키텍처로 구현한 것입니다.

---

## 10.9 이 장의 결론: FineDev는 ‘모델 기반 개발’이 아니라 ‘공정 기반 개발’이다

FineDev의 핵심은:

* 모델은 후보를 만들고,
* 시스템은 그 후보를 **실행 가능한 산출물로 수렴**시킨다.

이 관점으로 보면,

* 어떤 모델을 쓰든(4b/12b/대형)
* 실패는 발생하지만,
* 공정이 수렴을 만든다면
  개발은 자동화될 수 있습니다.

# 11장. Micro Orchestration: 함수 단위 개발 전략

이 장은 FineDev의 “생산 방식”을 규정합니다. FineDev가 말하는 Micro Orchestration은 거창한 에이전트나 복잡한 워크플로우가 아니라, **개발 단위를 ‘함수’로 고정하고**, 이를 **검증 가능한 조각으로 대량 생산**한 뒤, **의존성 순서대로 조립**하는 방식입니다.
이 전략은 특히 로컬 SLM(4b~12b) 환경에서 가장 큰 효과를 냅니다. 이유는 간단합니다. **모델이 흔들리는 원인의 상당수가 ‘길이/복잡성/컨텍스트 과잉’에서 오기 때문**입니다.

---

## 11.1 “함수 단위”가 중요한 이유: 실패 확률을 구조적으로 낮춘다

이전 실험에서 500~1000라인 단일 파일 생성은 12b에서도 불안정했고, 컨텍스트/출력 길이를 늘리는 방식은 시간·실패율·서빙 리스크를 키웠습니다. 반면 experiment6/7과 이번 세션 MVP1에서 확인된 방향성은:

* **함수 단위(또는 200라인 내외 단위)에서 성공률이 급격히 올라간다**
* 실패 원인이 단순해지고, 수정 비용이 작아진다
* 재작업(pass@k) 루프가 경제성을 가진다

즉, Micro Orchestration은 “모델을 잘 쓰는 팁”이 아니라 **실패 모드를 줄이는 아키텍처**입니다.

---

## 11.2 기본 원칙: Function = File (함수 하나가 파일 하나)

Micro Orchestration을 실제로 구현하려면 “작업 단위”를 강하게 고정해야 합니다. FineDev에서는 가장 단순하고 강한 규칙을 권장합니다.

### 원칙

* **하나의 함수 구현은 하나의 파일로 저장한다.**
* 파일은 “구현 전용(impl)”으로 두고,
* 공개 API는 `__init__.py` 또는 별도 aggregator에서 export 한다.

### 이렇게 하는 이유

* 각 함수는 독립적이어서 테스트/검증이 쉬움
* 실패 시 영향 범위가 좁음(해당 파일만 고치면 됨)
* merge 충돌/다중 변경이 줄어듦
* “하나의 생성 결과”가 지나치게 길어지는 것을 방지

### 파이썬에서 자연스러운 이유

* 파이썬 패키지는 모듈 파일 단위로 구성되며,
* `__init__.py`에서 원하는 함수만 외부에 노출할 수 있음
* 즉 “함수=파일”이 전혀 부자연스럽지 않고, 오히려 관리하기 좋습니다.

---

## 11.3 파일/폴더 구조(권장 레이아웃)

Micro Orchestration을 위한 기본 구조는 아래처럼 잡는 것이 운영이 쉽습니다.

* `specs/`

  * 함수별 스펙(yml)
* `src/mypkg/`

  * `__init__.py` (공개 API export)
  * `_impl/`

    * `f_slugify.py` (함수 구현 파일)
    * `f_xxx.py` ...
* `tests/`

  * 함수 단위/통합 테스트
* `tools/`

  * cli, runner, provider(ollama/openai), gates
* `logs/`

  * runs.jsonl(시도/프롬프트/출력/게이트 결과)

### 역할 분리의 효과

* `_impl/`은 “생성된 코드”가 쌓이는 창고
* `__init__.py`는 “공개 인터페이스 계약”
* 테스트는 “최종 판정”
* tools는 “공정 엔진”
* logs는 “경험치 DB로 가는 원천 데이터”

이렇게 나누면 프로젝트가 커져도 관리가 됩니다(1000 함수까지도 같은 원리).

---

## 11.4 카탈로그 주입(Catalog Injection): 필요한 참조만 주입한다

함수 단위 개발의 어려운 점은 사용자가 이미 짚으신 것처럼:

* 그 함수가 동작하려면 주변 환경/의존성이 이미 정의되어 있어야 한다

이를 해결하는 핵심 도구가 **카탈로그**입니다.

### 카탈로그란?

* “현재 패키지에 존재하는 선행 함수/유틸 목록”을 요약한 문서/데이터
* 예:

  * 함수명, 시그니처, 위치, 간단 설명
  * (선택) 사용 예시 1줄

### 주입 원칙(중요)

* 카탈로그 전체를 매번 넣지 않는다.
* **필요한 것만 선택적으로 주입한다.**

  * 이유: 프롬프트 길이는 작은 모델의 최대 적

### 운영 방식

* 스펙에 deps가 있으면:

  * 그 deps에 해당하는 카탈로그 항목만 프롬프트에 붙인다.
* deps가 명시되지 않았으면:

  * 기본적으로 주입하지 않는다.
  * 필요 시 Repair 단계에서만 주입한다.

이 방식이 “무한 템플릿” 문제의 타협점입니다.
템플릿을 무한히 만드는 대신, **설계(스펙)에서 deps를 명시**하면 필요한 참조만 자동으로 들어갑니다.

---

## 11.5 Topological Build(Topo 조립): 의존성 순서로 생산한다

함수 1000개 프로젝트에서 가장 중요한 건 “생성”이 아니라 **조립 순서**입니다.

### 의존성 그래프

* 각 함수는 노드(node)
* A가 B를 호출하면 edge: A → B (A depends on B)
* 이 그래프를 topo sort하면 생성/검증 순서가 결정됩니다.

### topo 빌드의 장점

* 선행 함수가 먼저 통과하므로, 후행 함수는 안정적인 환경에서 생성됨
* 실패가 격리됨:

  * B가 실패하면 B만 고치고 다시 돌리면 됨
  * A는 B가 통과할 때까지 생성하지 않거나, stub 전략을 사용 가능

### 실무적 운영 팁(개조식)

* leaf(의존 없는 함수)부터 만든다
* core utilities를 먼저 통과시켜 “기반”을 단단히 한다
* 실패한 노드는 격리하고 전체 파이프라인을 멈추지 않는다
* 재시도는 실패 노드에만 집중한다

---

## 11.6 “설계=템플릿” 관점으로 본 Micro Orchestration

사용자께서 말한 돌파구가 여기서 정확히 구현됩니다.

* 함수 단위 개발을 하려면 설계가 중요하고,
* 설계를 끝내면 생산은 “전기세만 늘어나는” 구조가 된다.

Micro Orchestration에서 설계란 결국:

* 스펙(시그니처, 예시, 제약, deps)을 만드는 행위
* 공개 API를 정하는 행위(`__init__.py` export)
* 테스트(또는 examples)로 요구를 고정하는 행위

즉, 설계가 곧 템플릿이고, 템플릿이 곧 공정의 입력입니다.

---

## 11.7 함수 단위 개발의 난점과 FineDev식 해결

### 난점 1) “함수만 만들어서는 동작하지 않는다”

* 의존성/환경이 불명확하면 import부터 깨짐

해결:

* 패키징 구조를 먼저 고정(스캐폴딩)
* `__init__.py` export 자동화
* import gate로 환경 문제를 모델 문제와 분리

### 난점 2) 카탈로그가 커지면 프롬프트가 길어진다

해결:

* 모듈 단위 카탈로그 분리
* deps 기반 선택 주입
* repair 단계에서만 추가 주입

### 난점 3) 함수가 많아지면 운영이 복잡해진다

해결:

* failure signature로 자동 라우팅
* 경험치 DB로 반복 실패를 자동 처방
* 승격 정책으로 “어려운 함수만” 상위 모델 사용

---

## 11.8 Micro Orchestration의 성공 기준(KPI)

Micro Orchestration은 “생각”이 아니라 “운영”이므로 KPI가 필요합니다.

### 권장 KPI(개조식)

* 함수 단위 pass@1 / pass@k
* 평균 시도 횟수(attempts per function)
* stage별 실패 비율(문법/제약/예시/테스트)
* topo 빌드에서 병목 노드 수(자주 실패하는 핵심 함수)
* 함수 1000개 기준 전체 완료 시간/비용

---

## 11.9 이 장의 결론

Micro Orchestration은 다음을 가능하게 합니다.

1. 개발을 “큰 창작”에서 “작은 조립”으로 바꾼다.
2. 모델의 불안정성을 구조적으로 줄인다(짧은 단위, 짧은 루프).
3. 실패를 격리하고, 대규모 프로젝트에서도 공정이 붕괴하지 않게 한다.
4. 설계를 스펙/테스트로 고정하면, 생산은 반복 자동화(전기세 공장)가 된다.

# 12장. Output Fine Tuning: “99%→100% 실행 가능” 수렴 기술

이 장은 FineDev의 “품질 엔진”을 설명합니다. Micro Orchestration이 **생산 단위를 줄여** 성공 확률을 올린다면, Output Fine Tuning(OFT)은 그 위에서 **남는 1% 오류를 잡아** 결과를 “실행 가능한 산출물”로 수렴시킵니다.

핵심은 단순합니다.

> 모델은 99%를 만들어준다.
> FineDev는 그 1%를 **결정론적 검증 + 정책 기반 수리 루프**로 100%로 만든다.

그리고 중요한 점은, OFT는 “모델 학습”을 뜻하지 않습니다(물론 장기적으로 학습으로도 연결 가능). OFT의 1차 목적은 **운영 공정으로 수렴을 만든다**입니다.

---

## 12.1 OFT의 기본 구조: Validate → Diagnose → Repair → Converge

Output Fine Tuning은 아래 4단계가 반복되는 루프입니다.

1. **Validate(검증)**

   * compile/constraints/examples/pytest 같은 결정론적 게이트로 판정

2. **Diagnose(진단)**

   * 실패 메시지를 읽고 “무슨 종류의 실패인지” 분류
   * 이를 failure signature로 요약

3. **Repair(수리)**

   * 실패 종류에 맞는 수리 전략을 선택
   * (재시도 / 수정 지시 / 패치 / 리라이트 / 승격)

4. **Converge(수렴)**

   * pass@k가 올라가도록 루프를 설계
   * 동일 실패 반복(고정점)에서는 다른 전략으로 전환

이 루프를 설계하는 것이 곧 OFT이며, “모델이 잘하냐/못하냐”보다 이 루프가 수렴하느냐가 실무 성패를 결정합니다.

---

## 12.2 OFT의 핵심 원칙 5가지

### 원칙 1) “판정은 결정론적으로, 수리는 최소한으로”

* 판정(게이트)은 100% 결정론적이어야 함
* 수리(모델)는 가능한 한 **최소 변경(minimal diff)** 을 유도해야 함

  * 큰 재작성은 흔들림/회귀를 유발

### 원칙 2) “프롬프트를 길게 하지 말고, 피드백을 짧게 쪼개라”

* 장황한 규칙 추가는 4b에서 특히 실패율을 올림
* 대신 게이트의 실패 메시지를 **짧고 행동 가능한 지시**로 변환해 주입

### 원칙 3) “고정점을 감지하면 전략을 바꿔라”

* 같은 실패가 반복되는 순간 “더 시도”는 낭비가 되기 쉽다
* 동일 signature 반복 시:

  * Planner 호출
  * 다른 모델/역할로 전환
  * 결정론적 리라이트 적용
  * 또는 문제를 “스펙 강화(예시 추가)”로 되돌림

### 원칙 4) “모델이 통제할 수 없는 실패는 즉시 시스템으로 라우팅”

* HTTP 500, 타임아웃, import 경로 문제 같은 시스템 실패는

  * 모델 재작업으로 해결되지 않음
* 이 분리가 없으면 “재작업”이 환각/낭비를 키움

### 원칙 5) “반복 실패는 DB화하여 다음엔 결정론적으로 처리”

* 같은 실수는 계속 나온다(특히 작은 모델)
* “재작업으로 고치는 것”보다

  * 실패 시그니처에 룰/패치 템플릿을 매핑해
  * 다음엔 빠르게 수렴시키는 것이 중요

---

## 12.3 실패 진단: Failure Signature(시그니처) 설계

OFT의 실전은 “분류기”에서 시작합니다. 실패를 잘 분류해야 수리 전략이 선택됩니다.

### Failure Signature의 목적

* 고정점 감지
* 라우팅 결정(Planner/승격/리라이트)
* 경험치 DB 키로 사용
* 통계/대시보드 지표

### 설계 원칙

* **결정론적으로 생성**되어야 함(규칙 기반)
* 지나치게 세분화하면 운영이 어려움
* 메시지의 핵심만 잡는 수준이 적절

### 대표 시그니처(예시)

* `format_error` (코드 추출 불가, 구조 깨짐)
* `syntax_error` (compile/ast 실패)
* `constraint_import_violation` (import 금지 위반)
* `example_missing_separators` (예상에 '-'가 있는데 출력에 없음)
* `example_over_separators` (하이픈 과잉: 문자 단위 분해 의심)
* `example_punct_not_removed` (구두점 남음)
* `example_non_ascii_not_removed` (한글 등 비ASCII가 남음)
* `pytest_fail` (통합 테스트 실패)
* `system_error_500/timeout` (서빙/런타임 오류)

이번 세션 slugify는 사실상 “시그니처 분류와 라우팅이 왜 필요한지”를 보여주는 교과서 케이스였습니다.

---

## 12.4 수리 전략 라이브러리: 어떤 실패에 무엇을 할 것인가

OFT는 “재시도”만으로는 부족합니다. 실패 유형별로 최소한의 전략 세트를 갖춰야 합니다.

아래는 FineDev에서 권장하는 **수리 전략 카탈로그**입니다.

---

### 12.4.1 Retry(무지성 재시도): “가끔은 싸고 효과적”

**언제 유효한가**

* 첫 시도에서 출력이 잘렸거나(일시적)
* 문법이 사소하게 깨졌거나(들여쓰기 한 줄)
* 모델이 우연히 흔들린 경우

**언제 무효한가**

* 같은 examples mismatch가 반복될 때
* 제약 위반이 반복될 때(import)
* 고정점 signature가 2회 이상 나올 때

FineDev는 Retry를 “0~1회” 정도만 권장합니다. 그 이후는 수리/라우팅이 필요합니다.

---

### 12.4.2 Repair by Edit Directives(수정 지시 기반 수리)

가장 기본적이고 가장 중요한 수리 방식입니다.

**입력으로 주는 것**

* 실패 메시지(예: ExampleMismatch)
* 이전 코드
* 아주 짧은 수정 지시(불릿 2~5개)

**좋은 지시 예(슬러그파이 케이스)**

* “토큰 사이에만 `-`를 넣고 문자 사이에는 넣지 말 것.”
* “구두점(, ! 등)은 제거할 것.”
* “비ASCII 문자는 제거할 것(예: 한글 제거).”
* “공백만 있는 입력은 빈 문자열을 반환할 것.”

**핵심**

* 지시는 짧고, 행동 가능하고, 반례를 포함해야 함(과잉 보정 방지)

---

### 12.4.3 Patch Mode(패치 모드): “재생성 말고 수정하라”

Producer가 계속 “다시 쓰기”로 회귀하면 흔들립니다. 이때는 명시적으로 패치 모드로 전환합니다.

**패치 모드 특징**

* 기존 코드를 유지
* 필요한 부분만 변경하도록 강제
* diff 중심으로 출력하게 할 수도 있음(단 코딩 출력 형식은 간단히)

**언제 쓰나**

* 고정점이 “구조적 재작성” 때문에 생길 때
* 작은 수정이면 통과할 것 같을 때

---

### 12.4.4 Deterministic Rewrite(결정론적 리라이트): “반복되는 단순 오류는 기계적으로 고친다”

당신이 제안한 “syntax bug처럼 매번 틀리는 버그는 고쳐도 된다”는 지점이 여기입니다.

**원칙**

* 리라이트는 휴리스틱이면 안 됨
* 안전한 변환만 수행(결정론적)

**예시**

* 불필요한 BOM 제거, trailing whitespace 정리(비로직)
* 금지 import가 “미사용”인 경우 제거(사용 여부는 AST로 판정)
* 명백한 `from __future__` 오타 같은 고정 패턴 교정(단, 정책적으로 고정된 경우)

**주의**

* import를 강제로 지우면 코드가 망가질 수 있음
  → “import 사용 여부 탐지” 후에만 안전 리라이트 가능
  → 사용 중이면 리라이트가 아니라 “재구현” 라우팅이 맞음

---

### 12.4.5 Escalation(승격) & Role Switch(역할 전환)

OFT는 “모델을 바꾸지 않는다”가 아니라 “필요할 때만 바꾼다”입니다.

**승격이 필요한 순간**

* 동일 failure signature 2회 이상 반복
* repair 지시를 넣어도 같은 방향으로 오해
* 4b planner/producer 조합으로 고정점 탈출이 안 될 때

**역할 전환 예**

* Producer(4b) 유지 + Planner/Fixer를 12b로 승격
* 또는 교차 모델(예: gemma ↔ llama)로 “다른 습관”을 이용

사용자가 제안한 “복수 AI로 서로 견제”는 여기서 실험할 가치가 있습니다.
단, 핵심은 “무작정 번갈아”가 아니라 **고정점 트리거 조건에서만 교차 호출**하는 것입니다.

---

## 12.5 고정점(Stuck Loop) 문제: 왜 생기고 어떻게 탈출하나

이번 세션 slugify에서 가장 흥미로운(그리고 중요한) 현상이 고정점이었습니다.

### 고정점의 대표 형태

* 하이픈을 “단어 사이”가 아니라 “문자 사이”에 넣어 버림
  → 모델이 규칙을 가장 단순 단위로 만족시키는 과잉 보정
* 하이픈을 아예 제거해버림
  → “정제”를 “삭제”로 오해
* import 금지인데 import를 계속 사용
  → 고정 레시피로 회귀

### 고정점 탈출 전략(우선순위)

1. **반례 지시 추가(짧게)**

   * “문자 사이 하이픈 금지” 같은 1줄 반례가 효과적
2. **examples 보강**

   * 고정점을 직접 실패하게 만드는 예시를 추가
3. **패치 모드 전환**

   * 재작성 대신 최소 수정 강제
4. **Planner 호출(요약 지시)**

   * producer 프롬프트를 짧게 유지
5. **승격/교차 모델**

   * 다른 모델의 “습관”으로 탈출
6. **결정론적 리라이트(가능한 경우만)**

OFT는 이 순서를 “정책”으로 갖는 것이 중요합니다.

---

## 12.6 경험치 DB: OFT를 ‘점점 결정론적으로’ 만드는 장치

OFT의 장기 목표는 “매번 모델이 고치게 한다”가 아니라:

> 반복되는 실패는 점점 **모델 호출 없이** 해결하거나,
> 최소한 한 번의 짧은 지시로 해결하게 만드는 것

이를 위해 경험치 DB는 아래 정보를 축적합니다.

### 저장 단위(권장)

* `failure_signature`
* `spec_fingerprint`(스펙/테스트 요약 해시)
* `prompt_snippet`(적용한 지시)
* `patch`(성공한 수정 코드 또는 diff)
* `result`(통과 여부)
* `provider/model`(어떤 모델에서 성공했는지)
* `timestamp`, `latency`, `attempts`

### 활용 방식

* 동일 signature가 뜨면:

  1. 해당 signature에 매핑된 “검증된 지시문”을 repair prompt에 자동 삽입
  2. 또는 안전한 리라이트 룰을 적용
  3. 또는 성공률 높은 모델/역할로 라우팅

사용자가 말한 “수백 개 개발 경험치를 DB화 → 결정론적 모델”이 바로 이 구조로 실현됩니다.

---

## 12.7 OFT에서 ‘계약 vs 휴리스틱’ 분리 원칙의 적용

OFT는 품질을 올리고 싶어서 무엇이든 넣고 싶어집니다. 하지만 FineDev는 다음을 강하게 금지합니다.

* 휴리스틱을 계약/게이트로 끌어오지 말 것

### 계약(게이트)에 남는 것

* 판정 가능한 규칙(compile/constraints/examples/tests)

### 휴리스틱은 Audit로 분리

* 스타일, 리팩터링, 성능, “더 좋은 코드” 같은 것

이 분리 덕분에 OFT는 “수렴 엔진”으로 작동하고, 품질 향상은 옵션으로 확장할 수 있습니다.

---

## 12.8 OFT의 성공 기준(KPI)

OFT는 결국 운영 지표로 평가합니다.

### 핵심 KPI(개조식)

* pass@1 / pass@k (k=3~5)
* 평균 attempts per function
* 동일 signature 반복률(고정점 비율)
* signature별 해결 시간/비용
* 승격률(얼마나 자주 상위 모델이 필요한가)
* 결정론적 리라이트 적용률 및 성공률
* “시스템 실패” 비율(500/timeout) — 공정 결함 지표

slugify 같은 단일 함수로는 작은 지표만 보이지만, 함수 수가 늘수록 OFT의 가치가 통계적으로 크게 드러납니다.

---

## 12.9 이 장의 결론

Output Fine Tuning은 “모델을 더 똑똑하게 만들자”가 아니라:

* **실패를 결정론적으로 감지하고**
* **실패 유형별로 최소한의 수리 전략을 적용하며**
* **고정점이면 정책적으로 탈출하고**
* **경험치 DB로 반복 실패를 자동화**해서

결과를 “99% 그럴듯한 코드”에서 “100% 실행 가능한 산출물”로 수렴시키는 기술입니다.

# 13장. Audit AI(옵션): 휴리스틱 분리 원칙

이 장은 FineDev에서 “품질”을 다루는 방식의 핵심을 설명합니다. 결론부터 말하면 FineDev는 품질을 중요하게 보되, 그 품질을 **결정론적 계약(게이트)** 안으로 끌고 들어오는 것을 강하게 경계합니다. 이유는 단순합니다.

* 계약/게이트는 **반드시 결정론적**이어야 수렴한다.
* 휴리스틱(주관/추정/맥락 의존)은 계약을 오염시키고, 공정을 불안정하게 만든다.
* 그러므로 휴리스틱은 **Audit AI라는 옵션 레이어로 완전히 분리**한다.

Audit AI는 “무조건 통과/실패를 결정하는 심판”이 아니라, 인간 리뷰처럼 **경고·추천·리스크 탐지**를 제공하는 보조 단계입니다.

---

## 13.1 왜 Audit가 필요한가: 결정론만으로는 ‘좋은 코드’가 되지 않는다

FineDev의 게이트는 다음을 보장합니다.

* 문법이 맞다
* 정책을 지킨다(import 금지 등)
* 예시를 만족한다
* 테스트를 통과한다

하지만 실무에서는 이것만으로 부족한 경우가 많습니다.

* 보안 취약점 가능성(예: 위험한 eval, 경로 처리)
* 성능 병목(불필요한 O(n^2))
* 유지보수성(가독성, 중복, 네이밍)
* API 사용 관례 위반(라이브러리 best practice)
* 코드 품질 일관성(프로젝트 스타일/패턴)

이런 것들은 “결정론적으로 통과/실패”를 만들기 어렵거나, 만들더라도 비용이 큽니다(모든 것을 룰로 만들면 ‘계약 지옥’이 됨).
따라서 FineDev는 이 영역을 Audit(옵션)으로 분리합니다.

---

## 13.2 핵심 원칙: “계약/게이트에는 결정론만, 휴리스틱은 Audit로”

이 원칙은 FineDev 전체 설계의 기둥입니다.

### 13.2.1 계약/게이트에 들어갈 수 있는 것(허용)

* AST/compile로 판정 가능한 것
* 정규식/명확 규칙으로 판정 가능한 것
* 예시/테스트로 판정 가능한 것
* 보안도 “정확히 룰로 정의 가능”한 일부(예: 특정 API 금지)는 계약 가능

### 13.2.2 Audit로 보내야 하는 것(분리)

* “더 깔끔하게”
* “성능 좋게”
* “가독성 좋게”
* “리팩터링”
* “이 구현이 일반적으로 더 나음” 같은 주장
* 잠재 버그 가능성(확정이 아니라 가능성)

즉 Audit는 “정답/오답”을 판정하는 게 아니라, **리스크를 알려주는 레이어**입니다.

---

## 13.3 Audit AI의 역할 정의: 인간 리뷰에 가까운 ‘옵션 레이어’

Audit AI는 전형적으로 다음을 합니다.

### (A) 리스크 탐지

* 잠재적인 버그/엣지 케이스 누락 지적
* 보안 위험 가능성 지적
* 성능 문제 가능성 지적

### (B) 개선 제안

* 더 단순한 구현
* 중복 제거
* 네이밍 개선
* 문서화/주석 보강

### (C) 정책/가이드 준수 여부 “경고”

* 팀 컨벤션에 맞는가?
* 표준 라이브러리 사용 방식이 적절한가?

**중요:** Audit의 결과는 기본적으로 “권고”이며, **빌드를 실패시키지 않습니다.**

---

## 13.4 Audit 결과를 어떻게 시스템에 반영할 것인가

Audit를 넣을 때 가장 위험한 설계는 이겁니다.

* Audit가 “이건 별로야”라고 하면 바로 실패 처리 → 재작업 강제

이렇게 하면 휴리스틱이 곧 계약이 됩니다. FineDev는 이를 피합니다.

### 13.4.1 권장 반영 방식 3종

1. **Report-only (기본)**

* Audit 결과를 리포트로 남김
* 개발자(사람)가 선택적으로 반영
* FineDev의 기본 모드

2. **Patch suggestion (자동 수정 제안, 자동 적용은 아님)**

* Audit AI가 “패치 제안(diff)”을 만들어 줌
* 적용은 사람이 선택하거나 별도 정책(승인) 필요

3. **Policy-gated auto-apply (제한적 자동 적용)**

* 아주 제한된 범위에서만 자동 적용
* 예: import 정리, 주석 추가 같은 무해한 변경
* 로직 변경이 들어가면 자동 적용 금지

---

## 13.5 Audit를 ‘선택’으로 두는 이유: 품질 목표는 프로젝트마다 다르다

기업형 개발에서도 품질의 정의는 프로젝트마다 다릅니다.

* 프로토타입: 동작이 우선
* 내부 도구: 유지보수성/가독성 우선
* 보안 민감: 안전성 우선
* 트래픽 큰 서비스: 성능 우선

Audit를 계약으로 넣어버리면, 이 모든 상황을 하나의 규칙으로 통일해야 합니다. 그건 불가능합니다.

그래서 FineDev는:

* “동작/테스트 통과”는 결정론적으로 강제하고
* 그 이상(성능/스타일/리팩터링)은 옵션으로 둡니다.

---

## 13.6 Audit AI의 출력 포맷(권장): 구조화된 ‘권고 리스트’

Audit는 사람이 읽어야 효과가 크므로, 출력은 구조화하되 너무 복잡하지 않게 설계합니다.

### 권장 출력 항목(개조식)

* `severity`: info / warning / high
* `category`: bug / security / perf / style / maintainability
* `finding`: 무엇이 문제/리스크인지
* `evidence`: 코드 위치(라인) 또는 짧은 근거
* `recommendation`: 어떻게 개선할지
* (선택) `patch`: diff 또는 수정 제안

이렇게 하면 경험치 DB에도 저장하기 쉽고, 이후 자동화도 가능합니다.

---

## 13.7 Audit와 Output Fine Tuning의 관계: “수렴 이후에만 건드려라”

FineDev 운영에서 중요한 순서 원칙이 있습니다.

> **먼저 ‘실행 가능’에 수렴시킨 뒤에, Audit로 품질을 올려라.**

이 순서가 중요한 이유:

* 수렴 이전에 품질까지 동시에 잡으려 하면

  * 프롬프트가 길어지고
  * 규칙이 늘어나고
  * 작은 모델은 흔들리고
  * 실패 원인 분해가 어려워집니다.

즉, Audit는 “후반 최적화 단계”가 되어야 하고, **수렴 루프와 섞이면 안 됩니다.**

---

## 13.8 Audit AI를 넣었을 때 기대 효과(그리고 한계)

### 기대 효과

* 사람이 놓칠 수 있는 리스크를 빠르게 발견
* 코드 품질을 점진적으로 끌어올림
* 팀 규칙/컨벤션의 표준화(권고 형태로 유지)
* 경험치 DB에 “좋은 패치 패턴” 축적 가능

### 한계(명확히 인정해야 함)

* Audit는 휴리스틱이므로 오탐/과잉 경고가 발생할 수 있음
* Audit가 만든 패치가 로직을 망가뜨릴 수 있음(특히 자동 적용 시)
* 따라서:

  * 기본은 report-only
  * 자동 적용은 매우 제한적으로

---

## 13.9 “휴리스틱 분리”를 실전에서 지키는 체크리스트

* [ ] 이 규칙은 기계적으로 pass/fail 판정 가능한가?

  * YES → 계약/게이트 후보
  * NO → Audit로 분리
* [ ] Audit 결과로 자동 실패 처리하고 있지 않은가?
* [ ] Audit가 로직을 바꾸는 패치를 자동 적용하고 있지 않은가?
* [ ] Audit는 수렴 이후에 실행되는가?
* [ ] Audit 결과는 구조화되어 DB에 저장 가능한가?

---

## 13.10 이 장의 결론

FineDev에서 Audit AI는 “품질을 올리는 수단”이지만, 더 중요한 역할은:

* **휴리스틱을 계약에서 분리해 공정을 안정화시키는 장치**

입니다.

* 계약/게이트는 결정론(수렴 엔진)
* Audit는 휴리스틱(인간 리뷰 레이어)
* 둘을 섞지 않아야, FineDev는 작은 모델로도 안정적으로 확장됩니다.

# 14장. MVP1 목표와 기존 실패와의 차이

이 장은 “우리가 왜 MVP1을 새로 만들었는가?”를 명확히 합니다. 이전 세션의 실패는 단순히 “모델이 약했다”가 아니라, **실험/운영 공정이 불완전해서 실패 원인을 분해하지 못했고**, 그 결과 **모델을 오판하거나 재작업이 무의미해지는 구간**이 반복된 것이 핵심이었습니다.
MVP1은 그 실패를 되풀이하지 않기 위해, 목표를 “코딩 성공”이 아니라 **FineDev 공정의 최소 단위가 실제로 수렴하는지**를 검증하는 것으로 바꾼 것입니다.

---

## 14.1 MVP1의 목적: “모델 평가”가 아니라 “공정 성립”을 확인한다

### 기존 실험에서의 흔한 착각

* 실패가 나면 → 모델이 못한다고 생각함
* 성공이 나면 → 모델이 잘한다고 생각함

하지만 이전 세션에서 관찰된 진짜 문제는 다음이었습니다.

* 실패 원인이 모델인지 시스템인지 구분되지 않음
* 출력 형식/스키마/서빙 문제로 다음 단계가 막힘
* import/패키징 문제로 코드가 맞아도 실패
* 로그가 부족해 ‘왜 실패했는지’를 알 수 없음

즉, “모델이 코딩한다/못한다”를 보기 전에
**실험 시스템 자체가 코드를 올바르게 생성·검증·수리할 수 있는지**가 먼저였습니다.

### MVP1의 목적 정의

MVP1은 다음을 확인하기 위한 최소 실험입니다.

1. **스펙(spec) → 구현 파일 생성**이 자동으로 되는가
2. **결정론적 게이트(예시/테스트)**가 올바르게 실패를 잡는가
3. **재작업(pass@k)** 루프가 실제로 수렴하는가
4. 실패가 나면 **원인이 로그로 재현 가능한가**

즉 “코딩 성공”이 아니라 **공정 성공**이 목표입니다.

---

## 14.2 MVP1이 “기존 실패”와 다른 가장 큰 점: 실패 원인을 쪼갠다

이전 세션에서 가장 큰 교훈 중 하나는:

> “실패 원인을 모르면 모델을 오판한다”

MVP1은 이 교훈을 시스템에 박아 넣었습니다.

### 기존 실험의 문제점(요약)

* 실패는 하나의 “실패”로만 보임
* 결과적으로:

  * JSON이 깨져도
  * import가 깨져도
  * 테스트가 깨져도
    모두 “모델이 못함”으로 귀결될 수 있음

### MVP1의 차별점

MVP1은 실패를 단계별로 분해합니다.

* extract / syntax / constraint / examples / pytest
* 각 단계는 “결정론적”으로 pass/fail을 내고
* 실패 메시지가 다음 재작업에 그대로 들어갑니다.

이렇게 하면:

* 모델 실패와 시스템 실패가 분리되고
* 재작업이 의미 있는 경우/없는 경우도 분리됩니다.

---

## 14.3 MVP1이 확인하려는 핵심 가설(실험 질문으로 표현)

MVP1은 규모가 작지만, 확인하려는 가설은 매우 중요한 “최소 구성”입니다.

### 가설 A: 함수 단위(짧은 코드)에서는 4b도 수렴 가능하다

* 4b가 pass@1은 흔들릴 수 있지만
* pass@k(3~5) + 결정론적 게이트 + 짧은 수리 지시로
* 실용적인 성공률을 만들 수 있는가?

MVP1은 slugify 같은 단순 함수로 이걸 확인합니다.

### 가설 B: 프롬프트를 길게 하지 않아도 examples가 수렴을 만든다

* “규칙을 잔뜩 나열”하는 대신
* 예시 기반으로 요구를 고정하면
* 작은 모델도 더 안정적으로 맞출 수 있는가?

### 가설 C: 로그/관측 가능성이 확보되면 실패를 ‘학습 대상’으로 바꿀 수 있다

* 프롬프트 전문과 단계별 결과를 남기면
* 실패가 “좌절”이 아니라 “개선 데이터”가 되는가?

---

## 14.4 MVP1 범위 제한이 의도적으로 “좁은” 이유

MVP1은 일부러 범위를 좁힙니다. 이는 “쉬운 것부터”가 아니라, **오판을 막고 공정을 검증하기 위해 필요한 최소 범위만 남긴 것**입니다.

### MVP1에서 의도적으로 배제한 것

* 대형 파일 생성(500~1000라인)
* 복잡한 의존성 그래프(topological build)
* UI/웹 프론트 같은 복합 산출물
* 다중 파일 동시 생성
* 고급 품질(Audit) 자동 반영

### 왜 배제했나

* 공정이 아직 성립하지 않았는데 범위를 늘리면

  * 실패 원인이 다시 뒤섞여 모델을 오판하게 됩니다.
* MVP1은 “공정 엔진이 정상인가”만 확인합니다.

---

## 14.5 기존 실패와 비교했을 때 MVP1이 “확인하려는 것”의 초점

이 질문에 대한 답이 MVP1의 핵심입니다.

### “기존 실패”가 주로 보여준 것

* 시스템/서빙/스키마/로깅 문제로 인해
* 모델의 실제 능력을 제대로 보지 못했다
* 긴 출력/긴 컨텍스트는 로컬 환경에서 운영 리스크가 컸다

### “MVP1”이 확인하려는 것

* 환경이 제대로 갖춰진 상태에서,
* 함수 단위 스펙을 입력하면,
* 로컬 SLM(4b)이
* **게이트 기반 수리 루프**로
* 실제로 테스트 통과에 수렴할 수 있는가?

즉:

* 기존 실패는 “왜 안 되는지”를 보여줬고
* MVP1은 “되는 최소 조건이 무엇인지”를 확인합니다.

---

## 14.6 MVP1 성공/실패 판정 기준(명확한 Definition)

MVP1은 “성공”을 감성적으로 판단하지 않습니다.

### MVP1 성공 기준(개조식)

* 패키징/테스트 환경이 정상 동작(ImportError 없음)
* spec 기반으로 파일 생성이 자동화됨
* 실행은 아래를 만족:

  * 예시 mismatch가 나면 정확히 보고됨
  * pytest 실패가 나면 원인이 로그로 남음
* attempts 3~5 내에 통과할 수 있는 케이스가 존재(수렴 가능성 확인)
* runs.jsonl에 프롬프트/출력/게이트 결과가 남아 재현 가능

### MVP1 실패 기준

* 실패 원인이 불명확(로그 부족)
* 시스템 실패(설치/경로/서빙)에 의해 반복적으로 막힘
* 실패가 분해되지 않아 모델 개선 포인트를 못 찾음

---

## 14.7 이번 세션 slugify는 MVP1 목적에 어떻게 부합했나

slugify는 “아주 작은 함수인데도 틀리는” 대표 사례였고, 그래서 오히려 MVP1에 적합했습니다.

* 작은 실수(하이픈, 구두점, 비ASCII 처리)가 반복됨
* attempts를 늘려도 같은 방향으로 반복되는 “고정점”이 발생
* import 금지 같은 정책 위반도 발생

이게 보여준 것은:

* 모델은 코드를 생성할 수 있지만,
* 마지막 1%에서 흔들릴 수 있으며,
* 그 흔들림을 잡으려면

  * 프롬프트를 늘리는 것만으로는 부족하고
  * 고정점 감지/라우팅/승격 같은 OFT 기술이 필요하다는 점입니다.

즉 slugify는 MVP1이 확인하려던 “수렴 공정”의 필요성을 매우 선명하게 드러낸 케이스였습니다.

---

## 14.8 이 장의 결론

MVP1은 “코딩 데모”가 아닙니다.
MVP1은 FineDev의 최소 구성요소가 실제로 작동하는지, 즉:

* 스펙 기반 생성
* 결정론적 게이트
* 수리 루프(pass@k)
* 로깅/재현성

이 네 가지가 **실험 시스템으로 성립하는지** 확인하는 단계입니다.

그리고 기존 실패와 가장 큰 차이는:

> MVP1은 실패를 하나로 뭉뚱그려 보지 않고, 단계별로 쪼개서 ‘수리 가능한 실패’로 바꿨다.

# 15장. MVP1 파이프라인 단계별 동작

이 장은 MVP1이 **실제로 어떤 순서로 실행**되고, 각 단계가 어떤 의미를 가지며, 실패 시 어디로 되돌아가는지(수렴 루프 포함)를 “공정 흐름” 관점에서 상세히 설명합니다.
MVP1은 slugify 같은 단일 함수 스펙을 입력으로 받아, **생성 → 게이트 검증 → 재작업**을 반복하여 최종적으로 테스트 통과 산출물을 만드는 최소 공정입니다.

---

## 15.1 MVP1 파이프라인 한 줄 요약

> **Spec(YAML) → (Generate 후보 코드) → (Extract/Normalize) → (Gate: 제약/예시/pytest) → 실패면 Repair → 통과면 파일 반영**

MVP1은 이 흐름이 “자동으로” 돌아가도록 만든 최소 프레임워크입니다.

---

## 15.2 입력/출력: 무엇을 넣고 무엇이 나오는가

### 입력(Input)

* `specs/functions/slugify.yml` 같은 함수 스펙 파일 1개

  * 시그니처
  * 목적
  * 예시(examples)
  * 제약(constraints)
  * (선택) notes

### 출력(Output)

* 구현 파일: `src/mypkg/_impl/f_slugify.py`
* 공개 export: `src/mypkg/__init__.py`에서 `slugify` 노출
* 실행 로그: `runs.jsonl` (시도별 프롬프트/출력/게이트 결과/실패 메시지 포함)

---

## 15.3 단계별 실행 흐름(단계 정의 + 의미 + 예상 결과)

아래는 “한 번의 attempt(시도)”가 실행되는 내부 단계입니다. 이 단계를 attempt 횟수만큼 반복합니다(pass@k).

---

### Step 0) 사전 조건 확인(환경/패키징)

**의미**

* 모델이 아니라 시스템이 정상인지 확인하는 단계
* 특히 Python 패키징/설치 문제는 모델과 무관한 실패를 만듭니다.

**대표 체크**

* `pip install -e ".[dev]"`가 되어 있는지
* `mypkg` import가 되는지
* pytest가 실행 가능한지

**예상 결과**

* 정상이라면 다음 단계로 진행
* 비정상이라면 “모델 실패”가 아니라 “시스템 실패”로 분류해야 함

---

### Step 1) Prompt 구성(Gen 또는 Repair)

**의미**

* attempt가 1이면 Gen prompt를 만든다.
* attempt가 2 이상이면 Repair prompt를 만든다(이전 실패 기반).

**Gen prompt에 들어가는 것(최소)**

* 함수 시그니처
* 목적 1~2문장
* examples
* 최소 제약(치명적인 것만)

**Repair prompt에 추가되는 것**

* 실패 메시지(ExampleMismatch, ConstraintViolation, pytest 로그 등)
* edit directives(짧은 수정 지시)
* 이전 코드(가능하면 전체)

**예상 결과**

* 프롬프트는 길어지지 않아야 함
* 길어지면 4b가 흔들릴 확률이 증가

---

### Step 2) 모델 호출(Provider)

**의미**

* 실제 모델(ollama/로컬 SLM or 더미 provider)을 호출하여 raw output을 받는다.

**예상 결과**

* raw output은 “완성 코드”가 아니라 “후보”일 뿐
* 모델은 설명을 섞을 수 있으므로 다음 단계가 필요

---

### Step 3) Extract Gate(코드 추출)

**의미**

* raw output에서 코드만 뽑는다.
* 마크다운/설명/잡텍스트를 제거하여 실행 가능한 형태를 만든다.

**실패 유형**

* 코드 블록이 없음
* 여러 블록이 충돌
* 빈 출력

**예상 결과**

* 통과하면 “후보 코드 문자열” 확보
* 실패하면 즉시 attempt 실패(Repair로)

---

### Step 4) Normalize/Fixup(안전 정규화)

**의미**

* 로직을 바꾸지 않는 선에서 실행 가능성을 높인다.

  * 앞뒤 잡텍스트 제거
  * 들여쓰기/라인 엔딩 정리
  * 불필요한 코드펜스 제거 등

**예상 결과**

* 이 단계는 안정화에 도움
* 하지만 과도하면 오히려 코드를 망칠 수 있으므로 “보수적으로” 적용

---

### Step 5) Syntax Gate(문법/파싱 검사)

**의미**

* `compile()`/`ast.parse()`로 문법 오류를 결정론적으로 컷한다.
* 문법이 깨진 상태에서 examples/pytest를 돌리는 건 낭비이므로 가장 앞단에서 잡는다.

**실패 메시지**

* SyntaxError/IndentationError + line number

**예상 결과**

* 통과하면 다음 단계로
* 실패하면 repair로(“line N 고쳐라”처럼 매우 명확한 피드백 가능)

---

### Step 6) Constraint Gate(계약/정책 검사)

**의미**

* spec에 있는 결정론적 제약을 검사한다.
* 예: import 금지

**실패 메시지 예**

* `ConstraintViolation: import not allowed (line 1): import re`

**예상 결과**

* 통과하면 examples로
* 실패하면 여기서 즉시 컷(테스트 돌려봤자 정책 위반이면 불합격이므로)

> 중요한 운영 포인트
> import 금지 위반을 “그냥 지워서” 통과시키면 위험합니다.
> 따라서 constraint 실패는 보통 “재구현 요구(Repair)”로 보내야 하며,
> import가 실제로 쓰였는지(AST로) 분석한 뒤에만 안전 제거가 가능합니다.

---

### Step 7) Examples Gate(스펙 예시 검증)

**의미**

* spec에 정의된 examples를 실행하여 expected와 비교한다.
* pytest보다 빠르고, 피드백이 직관적입니다.
* MVP1에서는 이 단계가 “수렴의 핵심”입니다.

**실패 메시지 형태(권장)**

* `ExampleMismatch #i: input=... expected=... got=...`
* 필요하면 결정론적 note를 추가:

  * “expected에 '-'가 있는데 got에는 없다”
  * “got이 문자 단위로 분해된 듯하다”
    이런 힌트는 “판정 가능한 사실”일 때만 붙임(휴리스틱 금지 원칙)

**예상 결과**

* 통과하면 “기능 요구 충족 후보”
* 실패하면 repair로(지시가 짧아져도 수리 가능)

---

### Step 8) 파일 반영(Write + Export)

**의미**

* 통과한 후보 코드를 실제 파일로 기록한다.

  * `src/mypkg/_impl/f_slugify.py`
* `src/mypkg/__init__.py`에 export를 추가한다.

  * 외부에서 `from mypkg import slugify`가 가능해짐

**예상 결과**

* 이 단계가 되어야 pytest에서 import가 정상화됨
* 잘못 반영되면 “환경 실패”가 다시 발생할 수 있으므로 조심스럽게 처리

---

### Step 9) Pytest Gate(통합 테스트)

**의미**

* 최종 판정 단계
* 예시만 통과해도, 테스트가 더 많은 케이스를 포함하면 여기서 걸러짐

**예상 결과**

* 통과하면 최종 성공(해당 함수 “완성”)
* 실패하면 pytest 로그를 repair prompt에 넣고 재작업

---

## 15.4 Attempt 루프(pass@k)에서 실제로 일어나는 일

MVP1의 “attempts=5” 같은 옵션은 아래를 의미합니다.

* Attempt 1: Gen prompt로 후보 생성 → 게이트 체인 실행
* Attempt 2~k: 실패 원인을 포함한 Repair prompt로 다시 생성/수정 → 게이트 체인 재실행

여기서 중요한 것은:

* attempt는 단순 반복이 아니라,
* **실패 신호(게이트 메시지)가 다음 시도를 바꾼다**는 점입니다.

---

## 15.5 고정점(반항/반복 오류)이 발생했을 때의 경로

이번 세션에서 이미 확인된 것처럼, 4b는 다음과 같은 고정점에 빠질 수 있습니다.

* 제약 위반 반복(import 계속 사용)
* examples mismatch 반복(하이픈 누락, 과잉 삽입)
* 지시를 문자 단위로 해석하는 과잉 보정

MVP1(현재 버전)의 의도는:

* 이런 고정점을 “관측 가능하게” 만들고,
* failure signature로 감지한 뒤,
* Planner(옵션) 또는 프롬프트 튜닝을 통해 탈출하는 것입니다.

즉 MVP1은 고정점까지 “포착”하고 로그로 남기는 단계이며,
MVP2부터는 고정점 탈출 전략을 더 자동화합니다.

---

## 15.6 단계별 기대 결과를 요약하면

* Extract/Syntax/Constraint는 “기초 실행 가능성”을 보장
* Examples는 “요구 충족(스펙 준수)”을 보장
* Pytest는 “프로젝트 통합 기준”을 보장
* Logging은 “다음 개선(프롬프트/정책/DB)”을 가능하게 함

---

## 15.7 이 장의 결론

MVP1 파이프라인은 “모델에게 코딩을 맡긴다”가 아니라:

* 모델은 후보를 만들고,
* 시스템은 그 후보를 단계별로 검증하며,
* 실패 원인을 수리 루프로 되먹임하여,
* 결국 테스트 통과 산출물로 수렴시키는

FineDev 최소 공정의 구현입니다.

# 16장. MVP1에서 실제로 관측된 고정점 사례들

이 장은 MVP1(특히 slugify 실험)에서 실제로 반복 관측된 “고정점(stuck loop)”을 FineDev 관점으로 분해해 정리합니다. 고정점이란 단순 실패가 아니라:

* **attempt를 늘려도 같은 유형의 실패가 반복**되거나,
* 수정 지시가 들어가도 **같은 방향의 오해/반항이 유지**되거나,
* 출력이 엉뚱한 방식으로 “규칙을 만족하는 척”하며 **수렴이 멈추는 상태**

를 말합니다.
이번 MVP1은 이 고정점들이 “모델이 못한다”의 증거라기보다, **Output Fine Tuning 정책(라우팅/승격/리라이트/스펙 보강)의 필요성을 증명**해준 사례였습니다.

---

## 16.1 고정점이 중요한 이유: “시도 횟수”가 아니라 “정책 전환”이 필요하다는 신호

MVP1에서 attempts를 3→5로 늘려도 결과가 거의 변하지 않는 케이스가 나타났습니다. 이는 우연 변동(랜덤성) 문제가 아니라:

* 모델이 특정 레시피/습관에 고착되었거나
* 지시를 특정 방식으로 해석하는 경향이 고정되었거나
* 정책(제약/예시/수리 지시)이 오히려 잘못된 방향으로 학습 신호를 주고 있거나

를 뜻합니다. 즉 **“더 돌리면 된다”가 아니라 “다른 조치가 필요하다”**는 신호입니다.

---

## 16.2 고정점 사례 #1 — 구분자(hyphen) “영속적 누락”: `helloworld` 반복

### 관측

* 기대: `"Hello, World!" → "hello-world"`
* 실제 반복 출력: `"helloworld"` (구분자 제거)
* attempts를 늘려도 계속 같은 형태로 나옴

### FineDev 해석(실패 시그니처)

* `example_missing_separators`
* “단어 경계(whitespace/punct)를 구분자로 변환” 규칙이 모델 내부에서 제대로 고정되지 않음

### 왜 고정점이 되었나(가능한 원인 구조)

* 모델이 slugify를 “모든 비문자 제거 + 소문자 + concat”으로 단순화한 레시피를 선호
* 구두점 제거는 맞췄지만, **경계 정보를 유지해야 한다**는 요구를 놓침
* Repair 지시가 “하이픈 넣어라” 수준이면 모델이 계속 무시하거나 다른 곳에서 과잉보정으로 튐

### 이 고정점이 주는 시사점

* “구분자 규칙”은 말로 길게 설명하는 것보다

  * examples를 강화하거나
  * repair directive를 아주 짧고 강하게(토큰 단위) 주는 쪽이 효과적
* 여기서 attempts를 늘리는 것은 거의 의미가 없고,

  * **정책 전환(지시 강화/patch mode/승격)**이 필요

---

## 16.3 고정점 사례 #2 — 구분자 “과잉 만족”: `h-e-l-l-o- -w-o-r-l-d`

### 관측

* 기대: `"hello-world"`
* 실제: `"h-e-l-l-o- -w-o-r-l-d"`
  또는 `"a- - - -b"`

이 출력은 사용자가 말한 것처럼 “인간 유머”처럼 보일 정도로 이상하지만, FineDev 관점에서는 매우 전형적인 고정점 형태입니다.

### FineDev 해석(실패 시그니처)

* `example_over_separators` 또는 `example_char_level_join`

### 왜 이런 현상이 생기나(핵심 구조)

* “하이픈을 넣어라”라는 요구를 모델이 가장 단순한 단위(문자)로 만족시켜버림
* 즉 “단어 경계에 넣어라”를 “문자 사이에 넣어라”로 오해
* 특히 규칙이 길어지거나, 모델이 혼란스러워질 때 “가장 기계적인 만족”으로 도망가는 경향이 있음

### 이 고정점이 주는 시사점

* 이런 과잉 보정은 **설명을 더 늘릴수록** 오히려 강화될 수 있음
* 효과적인 해법은:

  * “문자 사이 하이픈 금지”라는 **반례 한 줄**
  * examples에 “문자 분해 출력은 실패”를 강하게 넣는 것
  * patch mode로 “토큰 단위 split/join”만 요구하는 것

---

## 16.4 고정점 사례 #3 — “부분만 살짝 맞추기”: `hello,-world!`

### 관측(최근 결과)

* 기대: `"hello-world"`
* 실제: `"hello,-world!"`
* 즉:

  * 소문자화는 함
  * 공백을 하이픈으로 바꾸는 것도 어느 정도 함
  * 그런데 구두점 제거가 안 됨(콤마/느낌표 잔존)

### FineDev 해석(실패 시그니처)

* `example_punct_not_removed`

### 의미

이 케이스는 “개선의 조짐”이 맞습니다. 이유는:

* 이전 고정점(하이픈 누락/문자 분해)보다 훨씬 “정상 근처”
* 즉 수렴이 실패하는 게 아니라, **마지막 1% 정제 규칙**이 남은 상태

이 유형은 OFT가 잘 먹히는 영역입니다.

* 짧은 repair 지시
* 또는 결정론적 리라이트(구두점 제거 같은)로 빠르게 수렴 가능

---

## 16.5 고정점 사례 #4 — 비ASCII(한글) 보존: `안녕-hello-123`

### 관측

* 기대: `"안녕 hello 123" → "hello-123"`
* 실제: `"안녕-hello-123"`

즉, 한글을 제거하지 않고 토큰으로 유지함.

### FineDev 해석(실패 시그니처)

* `example_non_ascii_not_removed`

### 왜 고정점이 되나

* 모델은 “문자 제거”에 대해 기본적으로 보수적일 수 있음
  (특히 다국어 입력에서 “유니코드도 문자니까 남겨야 하나?”로 해석)
* “ASCII만 유지” 같은 규칙이 명시되지 않으면, 모델의 선택이 분산됨

### 이 고정점이 주는 시사점

* 이건 “모델 반항”이라기보다 “요구 해석의 자유도” 문제에 가깝습니다.
* 해결은:

  * examples에 비ASCII 제거를 명시하거나
  * constraints로 출력 문자 집합을 고정(`[a-z0-9-]`)하는 것

즉, “계약을 무한히 늘리지 말자” 원칙과 충돌하는 게 아니라,

* **필요한 곳에만 최소 계약을 넣는 전형적인 자리**입니다.

---

## 16.6 고정점 사례 #5 — 제약 반항(import 금지 위반): `import re`

### 관측

* `ConstraintViolation: import not allowed (line 1): import re`

이는 attempt를 늘려도 반복될 수 있는 유형입니다.

### FineDev 해석(실패 시그니처)

* `constraint_import_violation`

### 왜 이게 “모델이 반항”처럼 보이나

* slugify 류 문제에서 모델은 정규식(re)을 ‘정답 레시피’로 강하게 연상합니다.
* 그래서 import 금지를 말로 주더라도 “습관적 해결”로 회귀합니다.

### 그런데 이것은 단순 반항이 아니다(중요)

* 모델이 re에 의존해 구현했으면,

  * import 줄만 제거하면 코드가 무의미해질 수 있습니다.
* 따라서 이 문제는:

  * “규칙을 더 강하게 말해라”가 아니라,
  * **제약 준수 가능한 설계로 유도하거나**
  * **역할/승격/패치 모드로 전환**
    해야 합니다.

### FineDev식 대응 원칙

* import 발견 시:

  1. AST로 import 심볼 사용 여부 탐지
  2. 미사용이면 결정론적 제거 가능
  3. 사용 중이면 제거 금지 → 재구현(Repair)로 라우팅
* 같은 violation이 2회 반복되면:

  * Planner(상위 모델 권장) 또는 승격 트리거로 보는 게 합리적

---

## 16.7 고정점 사례 #6 — “attempt 증가가 무효”: 3회→5회에도 동일 결과

### 관측

* attempts=3에서 `helloworld`
* attempts=5에서도 `helloworld`

### FineDev 해석

* 랜덤성 기반 개선이 아니라 “정책/프롬프트/모델 습관” 문제
* 즉 **Retry(무지성 재시도) 전략이 무효**라는 것을 확인한 셈입니다.

### 시사점

* 이런 경우부터는 시도 횟수보다:

  * Repair prompt 설계 변경
  * failure signature 기반 라우팅
  * patch mode
  * 교차 모델/승격
    같은 “정책 전환”이 필요합니다.

---

## 16.8 이번 MVP1 고정점들이 보여준 ‘공정적 결론’

MVP1에서 관측된 고정점은 종류가 여러 개였지만, 공통 결론은 하나로 수렴합니다.

### 결론 1) “모델이 코딩을 못 한다”가 아니라 “수렴 정책이 아직 약하다”

* 후보 생성은 된다.
* 마지막 1% 규칙(구분자/구두점/비ASCII)에서 흔들린다.
* 고정점은 attempts로 해결되지 않는다.

### 결론 2) 고정점은 ‘수리 정보의 품질’ 문제로 많이 귀결된다

* 실패 메시지는 있는데,
* 그걸 어떤 edit directives로 바꿔 넣느냐가 성패를 좌우한다.

### 결론 3) Planner/승격은 ‘고정점 탈출’에 특화된 기능이다

* producer=4b는 반복 실수를 할 수 있다.
* planner/fixer를 12b로 올리면 고정점 탈출이 쉬워질 가능성이 크다.
* 교차 모델(gemma↔llama)도 이 지점에서만 제한적으로 쓰면 실험 가치가 있다.

### 결론 4) 계약을 무한히 늘리지 말되, “딱 필요한 최소 계약”은 효율적이다

* 예: 출력 문자 집합을 `[a-z0-9-]`로 고정하면,

  * 비ASCII/구두점 문제를 한 방에 정리할 수 있음
* 이는 “계약 지옥”이 아니라 “최소 수렴 장치”에 해당합니다.

---

## 16.9 이 장의 요약(짧게)

MVP1 slugify에서 관측된 고정점은 크게 4종으로 정리됩니다.

1. **구분자 누락**(helloworld)
2. **구분자 과잉**(h-e-l-l-o…)
3. **구두점/비ASCII 잔존**(hello,-world!, 안녕-hello-123)
4. **정책 위반 반복**(import re)

이 고정점들은 단순 시도 횟수 증가로 해결되지 않았고,
FineDev가 강조하는 **라우팅/패치 모드/승격/경험치 DB** 같은 OFT 기술이 “왜 필요한지”를 실증했습니다.

# 17장. MVP1 개선 패치 히스토리(핵심 변경점)

이 장은 MVP1을 실행하면서 “무엇을 어떻게 고쳤고, 그 변경이 어떤 문제를 겨냥했는지”를 FineDev 관점에서 정리한 **핵심 패치 히스토리**입니다.
중요한 점은, MVP1의 패치들은 기능 추가라기보다 **실험 공정의 관측 가능성/결정론성/수렴성**을 높이기 위한 변화였다는 것입니다.

> MVP1 패치의 본질 = “모델을 더 똑똑하게”가 아니라 “공정을 더 정확하게”
> (측정 가능하게 만들고, 실패를 분해하고, 수리 루프가 작동하게)

아래는 이 세션에서 실제로 진행된 흐름을 기준으로 “핵심 변경점”을 정리한 것입니다.

## 17.1 패치 #0 (초기 MVP1): 더미(Dry-run)로 파이프라인 뼈대 검증

### 배경

* 처음부터 로컬 Ollama를 붙이면 시스템/서빙 이슈와 모델 이슈가 섞여서 원인 분석이 어렵습니다.
* 그래서 MVP1은 **--dry-run(더미 provider)** 로 “파이프라인이 돌아가는지”부터 확인하도록 설계됐습니다.

### 핵심 의미

* “모델이 잘하냐”가 아니라:

  * spec → 파일 생성
  * 테스트/예시 검증
  * 로그 기록
    이 공정 자체가 살아있는지 확인한 단계

### 관측 결과(의미)

* dry-run에서는 “OK: wrote file”까지 갔다는 것은,

  * 최소한 러너/파일 기록/경로는 정상이었음을 의미합니다.
* 이후 실제 모델로 넘어갈 준비가 됐습니다.

---

## 17.2 패치 #1 (환경/패키징 문제 노출): editable install 요구(`pip install -e ".[dev]"`)

### 배경(실제 오류)

* pytest가 `ModuleNotFoundError: No module named 'mypkg'`로 터짐
* 이건 모델이 만든 코드와 무관하게 “환경이 실패하도록” 되어 있었던 상태

### 핵심 변경점(의미)

* 프로젝트를 editable install로 설치해야

  * `src/` 아래 패키지가 pytest에서 import 됩니다.
* `python -m pip install -e ".[dev]"`를 수행하면,

  * 로컬 개발 상태에서 소스가 바로 import 경로에 잡힘

### FineDev 관점 시사점

* 이런 문제가 있으면 attempts를 아무리 늘려도 의미가 없습니다.
* 즉 이 패치는 “모델 평가가 가능하도록 시스템을 정상화”한 필수 선결 조건입니다.

---

## 17.3 패치 #2 (Ollama provider 연결): 실제 로컬 SLM 호출로 전환

### 배경

* dry-run을 통과한 뒤에, 실제 `--provider ollama`로 전환했습니다.

### 핵심 변경점

* CLI가 spec을 읽고 Ollama로 프롬프트를 보내 실제 코드 후보를 받음
* attempts(3~5)를 통해 pass@k 수렴을 시도

### 관측된 효과

* 이제부터 발생하는 failures는

  * 시스템 문제(서빙/요청)
  * 모델 출력/수렴 문제
    로 분리해서 볼 수 있게 됩니다.

---

## 17.4 패치 #3 (Examples gate 강화): pytest 대신 “예시 불일치”를 우선 노출

### 배경(실제 관측)

* pytest로 가기 전에 이미 slugify가 요구를 못 맞추는 경우가 많았습니다.
* pytest는 로그가 길고, 실패가 직관적이지 않을 때가 있습니다.

### 핵심 변경점(의미)

* “examples mismatch”를 명확히 표시하는 게이트를 전면에 둠
* 실패 메시지가:

  * input / expected / got
    형태로 직접적으로 나오게 함

### 왜 중요한가

* 작은 모델(4b)은 긴 pytest 로그를 보면 더 흔들립니다.
* examples gate는 수리 프롬프트를 짧게 유지할 수 있습니다.
* 즉 이 패치는 “수렴성”을 높이는 변화입니다.

---

## 17.5 패치 #4 (반복 실패 대응): attempts 증가가 무의미한 고정점 발견

### 배경

* attempts=3에서 `helloworld`
* attempts=5에서도 `helloworld`
* 즉 재시도만으로는 해결되지 않는 고정점이 드러남

### 의미(패치라기보다 ‘발견’)

* pass@k를 높이는 전략이 “단순 retry”만으로는 부족함이 확인됨
* 이후 패치들은 “라우팅/플래너/로그”로 방향이 바뀝니다.

---

## 17.6 패치 #5 (Planner 도입 + 라우팅): “AI가 수정 방법을 찾게 하자” 실험

### 배경

* 사용자가 제안한 아이디어:

  * “AI가 잘못된 결과를 낸 경우 수정방법을 AI가 찾도록 하고 그것을 수정 작업에 넣자”
* 이게 효과가 있으려면:

  * 무조건이 아니라, “유효할 때만” 적용되어야 함

### 핵심 변경점(의미)

* Planner 단계(옵션)를 추가:

  * 실패 로그를 보고 **수정 지시(edit directives)** 를 생성
* Routing을 추가:

  * 어떤 실패에서는 planner를 호출하고,
  * 어떤 실패에서는 바로 repair로 가는 정책을 둠
* (설계 의도) 결정론적 판정 후 “휴리스틱은 옵션”으로 분리

### 관측된 한계

* planner 모델도 4b라서 고정점 탈출력이 제한적
* 하지만 구조적으로는 중요한 진전:

  * “수리 정책”을 공정 안에 넣는 첫 단계

---

## 17.7 패치 #6 (제약 위반/반항 문제 노출): import 금지 위반(`import re`)을 정식 시그널로 처리

### 배경(실제 오류)

* `ConstraintViolation: import not allowed (line 1): import re`
* 모델이 습관적으로 re로 회귀

### 핵심 변경점(개념적)

* “import 금지 위반”을 단순 테스트 실패가 아니라

  * 정책 위반 시그널로 분리해서 다루게 됨
* 또한 “import를 지워도 될까?”라는 중요한 논의가 촉발됨

  * 사용 중이면 제거하면 코드가 망가짐
  * 따라서 안전 제거는 AST 기반 판정이 필요

이 시점부터 FineDev의 원칙이 강화됩니다.

* “규칙을 말로 설득”보다 “정책을 게이트로 강제 + 라우팅”

---

## 17.8 패치 #7 (프롬프트 전문 로깅 추가): ‘프롬프트를 직접 튜닝’ 가능한 상태로 전환

### 배경

* 사용자가 요구:

  * “각 단계별 실제 사용되는 prompt를 log로 남겨 달라”
  * 직접 수정해 보고 싶다

### 핵심 변경점

* runs.jsonl에 다음이 저장되도록 개선:

  * gen prompt
  * repair prompt
  * planner prompt(사용 시)
* 뿐만 아니라:

  * 어떤 단계에서 어떤 프롬프트가 쓰였는지 “단계 라벨”도 필요(운영상)

### FineDev 관점 의미

이 패치는 MVP1에서 가장 큰 구조적 진전 중 하나입니다.

* 이제 실패를 단순히 “모델이 반항했다”로 끝내지 않고,
* **어떤 문장이 모델을 흔들었는지**를 실험적으로 검증할 수 있습니다.
* 즉, Output Fine Tuning의 1차 대상이:

  * 코드만이 아니라
  * 프롬프트/수리 지시라는 것이 확정됩니다.

---

## 17.9 패치 #8 (개선 조짐 관측): 고정점이 “다른 형태”로 이동

### 배경(관측 결과)

* 이전: `helloworld` (구분자 누락), `h-e-l-l-o` (과잉)
* 이후: `hello,-world!`, `안녕-hello-123` (구두점/비ASCII 잔존)

### 의미

이건 “완전 성공”은 아니지만, 중요한 개선 신호입니다.

* 하이픈 처리 자체는 어느 정도 맞추기 시작함
* 남는 실패는:

  * 구두점 제거
  * 비ASCII 제거
    처럼 “마지막 1% 정제 규칙”에 가까워짐

즉, 공정이 “정답 근처로 수렴하는 방향”을 보였고,
이 단계부터는:

* 최소 계약(출력 문자 집합 제한) 또는
* 결정론적 리라이트(안전한 정제)
  로 빠르게 마무리할 수 있는 가능성이 커집니다.

---

## 17.10 MVP1 패치 히스토리의 종합 결론

MVP1에서의 개선은 “모델 튜닝”이 아니라 아래 순서로 진행됐습니다.

1. **환경 정상화**(import/설치) → 모델을 오판하지 않게 함
2. **게이트 강화**(examples 중심) → 실패를 수리 가능하게 만듦
3. **수리 정책 실험**(planner/라우팅) → 고정점 대응의 시작
4. **관측 가능성 확보**(프롬프트 로깅) → 이후 개선이 데이터 기반으로 가능
5. **수렴 방향 관측**(실패 형태 변화) → OFT/최소 계약/리라이트의 적용 지점 확인

즉 MVP1은 “정답을 얻는 실험”이 아니라,

* FineDev의 최소 공정을 만들고,
* 그 공정이 어디에서 수렴을 잃는지(고정점)
* 개선의 레버가 어디에 있는지
  를 찾아낸 단계였습니다.

# 18장. 측정 지표 정의

FineDev는 “모델이 좋다/나쁘다”가 아니라 **공정이 수렴하느냐**를 측정합니다. 그래서 지표도 모델 벤치마크(pass@1)만으로는 부족하고, **단계별 실패/수리 비용/고정점/승격/시스템 안정성**까지 포함해야 합니다. 이 장은 MVP1~MVP5(대형 프로젝트)까지 공통으로 쓸 수 있는 측정 지표 체계를 정의합니다.

---

## 18.1 지표 설계 원칙 6가지

1. **단계별(Stage-level)로 쪼갠다**

   * “실패” 하나로 뭉치면 모델을 오판한다.

2. **결정론적 판정 지표와 휴리스틱 지표를 분리한다**

   * 게이트 기반(pass/fail, mismatch count 등)는 결정론적
   * Audit(품질/리스크)은 별도 채널

3. **성공률 + 비용(시간/시도/토큰)을 함께 본다**

   * pass@k가 올라가도 비용이 폭발하면 실용이 아니다.

4. **고정점(반복 실패)을 반드시 계량화한다**

   * attempts를 늘렸는데 동일 실패가 반복되면 정책 전환 신호

5. **시스템 실패(서빙/런타임)를 별도 KPI로 둔다**

   * 시스템 실패율이 높으면 측정 자체가 무너진다.

6. **집계 단위(unit)를 명확히 한다**

   * 함수 1개 단위 / 실행 1회 단위 / 프로젝트 1회 단위
   * 단위가 섞이면 비교가 안 된다.

---

## 18.2 측정 단위와 데이터 스키마(권장)

### 기본 측정 단위 3종

* **Attempt 단위**: 한 번의 생성/수리 시도
* **Function 단위**: 한 함수가 최종 통과할 때까지의 기록 묶음
* **Run/Project 단위**: 여러 함수(또는 전체 스펙 집합) 실행 결과

### Attempt 단위에 기록해야 할 최소 필드

* `function_id` / `spec_path`
* `attempt_no`
* `provider`, `model`
* `stage_results`: 각 게이트 pass/fail
* `failure_signature` (실패 시)
* `error_message` (요약 + 원문)
* `latency_ms` (모델 호출/전체)
* (가능) `prompt_chars`/`prompt_tokens`, `output_chars`/`output_tokens`

> MVP1에서 프롬프트 전문 로깅을 추가한 이유가 바로 이 “측정 가능성” 확보입니다.

---

## 18.3 핵심 KPI 1: 성공률 계열(pass@1, pass@k, completion rate)

### 18.3.1 pass@1

* 정의: 첫 시도(Attempt 1)에서 최종 게이트(pytest 또는 examples+pytest)를 통과한 비율
* 의미: “기본 생산력”

### 18.3.2 pass@k

* 정의: 최대 k번 시도 내에 통과한 비율
* MVP1 기준 k=3~5가 현실적
* 의미: “수리 루프 포함 실용성”

### 18.3.3 Completion Rate(완결성)

* 정의: 코드 추출(extract) 및 문법(syntax)까지 통과한 비율
* 의미: “실행 가능한 후보를 만드는 능력”
* 특히 500~1000라인에서는 completion rate가 급락할 가능성이 큼

---

## 18.4 핵심 KPI 2: 단계별 게이트 실패율(Stage Failure Rate)

FineDev는 실패를 단계별로 측정해야 합니다.

### 정의

* `FailureRate(stage X) = X에서 실패한 attempt 수 / 전체 attempt 수`

### 권장 stage 집합

1. `extract_fail_rate`
2. `syntax_fail_rate`
3. `constraint_fail_rate`
4. `examples_fail_rate`
5. `pytest_fail_rate`
6. `system_fail_rate` (서빙/HTTP/timeout)

### 해석 예시

* extract_fail이 높다 → 출력 형식이 흔들림(프롬프트/출력 처리 개선)
* syntax_fail이 높다 → 완결성/문법 안정성 문제(짧은 단위/후처리 필요)
* constraint_fail이 높다 → 정책 반항/습관 회귀(라우팅/승격 필요)
* examples_fail이 높다 → 요구 해석/로직 미스(예시/수리 지시 품질 개선)
* pytest_fail이 높다 → 통합/환경/엣지케이스(테스트/패키징/설계 점검)
* system_fail이 높다 → 모델이 아니라 시스템 문제(측정 자체 불가)

---

## 18.5 핵심 KPI 3: 실패 시그니처 분포(Failure Signature Distribution)

### 정의

* 전체 실패를 failure_signature로 분류하여 비율로 집계

### 목적

* 어떤 종류의 실패가 지배적인지 한눈에 파악
* 라우팅 정책/리라이트 룰 우선순위 결정
* 경험치 DB 축적의 “카테고리”로 사용

### 예시(슬러그파이)

* `example_missing_separators`
* `example_over_separators`
* `example_punct_not_removed`
* `example_non_ascii_not_removed`
* `constraint_import_violation`

---

## 18.6 핵심 KPI 4: 고정점 지표(Stuckness Metrics)

MVP1에서 확인한 가장 중요한 지표 영역입니다.

### 18.6.1 Repeat Signature Rate(반복 시그니처율)

* 정의: 동일 function에서 동일 signature가 연속으로 반복되는 비율
* 해석:

  * 높으면 “attempt 증가”가 무효 → 정책 전환 필요

### 18.6.2 Stuck Length(고정점 길이)

* 정의: 동일 signature가 몇 회 연속 반복됐는지 평균/분포
* 예: 3회 연속 `missing_separators` → 매우 강한 고정점

### 18.6.3 Fix Efficacy(수리 효율)

* 정의: 특정 signature에서 repair 후 다음 attempt에서 개선(다른 signature로 이동 또는 통과)한 비율
* 의미:

  * 수리 프롬프트/플래너가 효과가 있는지 측정

---

## 18.7 핵심 KPI 5: 비용 지표(Cost & Latency)

### 18.7.1 Attempt당 비용

* 정의(현실적): 호출 시간, 토큰(가능 시), CPU/GPU 점유
* 최소로는 `latency_ms`만으로도 운영 판단 가능

### 18.7.2 Function-to-Pass 비용

* 정의: 한 함수가 통과할 때까지 걸린

  * 총 attempt 수
  * 총 시간(모델 호출 시간 + 게이트 시간)
* 실무 KPI로 매우 중요:

  * “전기세 공장”이 되려면 평균 비용이 예측 가능해야 함

### 18.7.3 Gate Time Share(게이트 비용 비중)

* 정의: 총 시간 중 게이트/pytest가 차지하는 비율
* 의미:

  * 모델이 빨라도 pytest가 느리면 전체가 느려짐
  * 대규모 프로젝트(MVP5)에서는 테스트 전략 최적화 필요

---

## 18.8 핵심 KPI 6: 승격/라우팅 지표(Escalation & Routing Metrics)

### 18.8.1 Escalation Rate(승격률)

* 정의: 전체 함수 중 상위 모델(12b/대형 LLM)로 넘어간 비율
* 의미:

  * 4b 중심 전략의 경제성이 유지되는지 판단

### 18.8.2 Escalation Success Rate(승격 성공률)

* 정의: 승격 후 k회 내 통과 비율
* 의미:

  * 승격 정책이 타당한지
  * 어떤 모델이 “구원투수” 역할을 하는지

### 18.8.3 Planner Invocation Rate(플래너 호출률)

* 정의: 고정점/특정 시그니처에서 planner가 호출된 비율
* 의미:

  * planner가 과도하게 호출되면 비용 증가
  * 너무 안 호출되면 고정점 탈출 실패

---

## 18.9 핵심 KPI 7: 시스템 안정성 지표(System Reliability)

이건 “모델 성능”과 별개이며, 측정이 무너지지 않게 하는 필수 KPI입니다.

### 18.9.1 System Error Rate

* 정의: HTTP 500, timeout, OOM, 연결 실패 등 시스템 계층 오류 비율
* 해석:

  * 이 값이 높으면 실험 결과는 신뢰할 수 없음(모델 오판 위험)

### 18.9.2 Error Observability Score(관측 가능성 점수)

* 정의(실무적): 시스템 오류 발생 시

  * 요청/응답 전문(특히 error body)이 로그에 남아있는 비율
* MVP1에서 “프롬프트 로깅”은 여기와 같은 축에 있습니다.
* 관측 가능성이 낮으면, 개선이 불가능합니다.

---

## 18.10 품질 지표(Audit Metrics)는 별도 트랙으로 둔다

휴리스틱 분리 원칙 때문에, Audit 지표는 게이트 성공률과 섞지 않습니다.

### Audit 지표 예

* audit finding 수(함수당 평균)
* severity 분포(info/warn/high)
* 카테고리 분포(security/perf/style/maintainability)
* audit 기반 패치 제안 수, 수용률(사람 승인률)

이 지표는 “품질 개선”을 측정하지만, “빌드 성공”과 섞으면 공정이 불안정해질 수 있습니다.

---

## 18.11 지표를 어떻게 리포트로 묶을 것인가(권장 리포트 형태)

실험 결과를 한 장으로 보려면 아래 묶음이 가장 효과적입니다.

1. **Overall Success**

* pass@1, pass@5
* 평균 attempts-to-pass
* 평균 time-to-pass

2. **Stage Failure Breakdown**

* extract/syntax/constraint/examples/pytest/system 실패율 막대

3. **Failure Signature Top-N**

* 상위 5개 시그니처 + 비율 + 평균 stuck length

4. **Routing/Escalation**

* 승격률, 승격 성공률, planner 호출률

5. **Reliability/Observability**

* system error rate
* error body 로깅 비율

---

## 18.12 MVP 단계별로 특히 중요해지는 지표

### MVP1(단일 함수)

* examples_fail_rate
* constraint_fail_rate
* stuck metrics(반복 signature)
* 프롬프트 길이/로깅 품질

### MVP2~MVP3(함수 다수 + deps 증가)

* pass@k
* stage breakdown
* topo 빌드 병목 노드(자주 실패하는 핵심 함수)
* 평균 time-to-pass

### MVP4~MVP5(함수 1000개 이상 대형)

* 시스템 안정성(system error rate)
* 테스트 비용(게이트/pytest time share)
* 승격률(비용 통제)
* 경험치 DB 효과(반복 실패 감소율)
* 전체 완료 시간(throughput: functions/hour)

---

## 18.13 이 장의 결론

FineDev의 측정 지표는 “모델이 잘한다”를 말하기 위한 것이 아니라,

* **공정이 수렴하는지**
* **수렴 비용이 예측 가능한지**
* **고정점을 얼마나 빨리 탈출하는지**
* **시스템이 측정을 오염시키지 않는지**

를 계량화하기 위한 것입니다.

# 19장. 실험 로그 기반 정량 리포트(템플릿)

이 장은 FineDev 실험 결과를 **runs.jsonl 같은 로그만으로 자동 생성**할 수 있는 “정량 리포트 템플릿”을 제시합니다. 목표는 두 가지입니다.

1. **모델 성능 vs 시스템/프롬프트/운영 이슈**를 분리해서 보여준다
2. pass@k 같은 성공률뿐 아니라, **어디에서 왜 막히는지(병목/고정점/승격 비용)**를 한눈에 드러낸다

이 템플릿은 MVP1(단일 함수)부터 MVP5(함수 1000개)까지 그대로 확장 가능하도록 설계합니다.

---

## 19.1 리포트 기본 구성(권장 목차)

1. **실험 메타데이터**
2. **요약 대시보드(1페이지)**
3. **성공률/비용 지표**
4. **단계별(Stage) 실패 분해**
5. **실패 시그니처 Top-N 및 고정점 분석**
6. **재작업/수리 효과 분석(Repair Efficacy)**
7. **승격/라우팅 분석(Planner/Escalation)**
8. **시스템 안정성/관측 가능성**
9. **케이스 스터디(대표 실패 패턴 3~5개)**
10. **개선 권고(다음 실험 액션 아이템)**

---

## 19.2 (1) 실험 메타데이터 섹션 템플릿

### 19.2.1 실험 ID 및 환경

* Experiment ID: `YYYYMMDD-HHMM-<tag>`
* Host OS / Python version
* Provider: `ollama | openai | dummy`
* Model(s): `producer_model`, `planner_model` (있다면)
* Git commit / version tag
* 실행 명령(재현 가능하게)

  * 예: `python -m tools.cli run ... --attempts 5 --provider ollama`

### 19.2.2 입력 스펙 범위

* Spec count: N
* Spec list(요약): slugify.yml 외 N개
* 평균/최대 expected LOC(예상 생성 길이)
* deps/graph 사용 여부(topological build on/off)

### 19.2.3 정책 플래그

* ENABLE_PLANNER on/off
* constraints set(예: no-import)
* deterministic rewrites on/off
* audit on/off

> 이 메타데이터는 결과 해석에서 “조건이 달라서 비교 불가” 문제를 줄입니다.

---

## 19.3 (2) 요약 대시보드(1페이지) 템플릿

한 페이지에 아래 10개 수치가 들어가면 “운영 판단”이 가능합니다.

### 핵심 지표 10종(예시)

1. pass@1
2. pass@k (k=3 또는 5)
3. 평균 attempts-to-pass
4. median attempts-to-pass
5. 평균 time-to-pass(초)
6. Stage failure breakdown(막대 1개로 요약: 가장 큰 실패 stage)
7. Top failure signature 1개(예: missing_separators)
8. stuck rate(동일 signature 2회 이상 반복 비율)
9. escalation rate(승격 사용 비율)
10. system error rate(500/timeout 비율)

> 이 페이지를 보면 “모델을 바꿔야 하는지 vs 공정을 고쳐야 하는지”가 거의 결정됩니다.

---

## 19.4 (3) 성공률/비용 섹션 템플릿

### 19.4.1 Success metrics

* pass@1, pass@3, pass@5
* completion rate(extract+syntax 통과율)
* function coverage(전체 스펙 중 몇 개가 최종 통과했나)

### 19.4.2 Cost metrics

* 평균 attempt latency(모델 호출 시간)
* 평균 gate latency(테스트/예시 실행 시간)
* 전체 time-to-pass 분포(평균/중앙/95p)
* 함수당 평균 호출 횟수(=attempts)

### 19.4.3 Efficiency metrics

* “통과한 함수 1개당 평균 소요 시간”
* “통과한 함수 1개당 평균 모델 호출 수”
* (가능하면) 토큰/문자 기준 비용

---

## 19.5 (4) 단계별(Stage) 실패 분해 섹션 템플릿

### 19.5.1 Stage failure rates(표)

* extract_fail_rate
* syntax_fail_rate
* constraint_fail_rate
* examples_fail_rate
* pytest_fail_rate
* system_fail_rate

### 19.5.2 Stage transition funnel(퍼널)

* total attempts
  → extract pass
  → syntax pass
  → constraints pass
  → examples pass
  → pytest pass(최종)

**이 퍼널이 중요한 이유**

* “어디서 가장 많이 죽는지”를 한눈에 보여줌
* 예: constraint에서 40% 죽으면 프롬프트가 아니라 정책/라우팅 문제일 가능성

---

## 19.6 (5) 실패 시그니처 Top-N 및 고정점 분석 템플릿

### 19.6.1 Failure signature Top-N

* Top 5~10 signature 목록
* 각 signature별:

  * 발생 비율
  * 평균 stuck length(연속 반복 횟수)
  * 해결 성공률(이 signature에서 시작했을 때 최종 통과로 간 비율)

### 19.6.2 고정점 분석(핵심)

* stuck rate: 동일 signature가 연속 2회 이상 반복된 function 비율
* stuck@k: k회 내 동일 signature 반복 후에도 탈출 못한 비율
* signature별 stuck propensity(고정점 유발력)

  * 예: `constraint_import_violation`은 stuck propensity가 높을 수 있음

### 19.6.3 고정점 사례 샘플(짧게)

* function_id, attempts, signature sequence

  * 예: `[missing_separators, missing_separators, missing_separators, ...]`

---

## 19.7 (6) 재작업/수리 효과 분석(Repair Efficacy) 템플릿

이 섹션은 “시도 횟수 증가가 의미가 있었나?”를 정량화합니다.

### 19.7.1 Attempt improvement rate

* Attempt n → n+1에서

  * stage가 개선되었는지(예: syntax_fail → examples_fail로 이동)
  * signature가 변화했는지(고정점 탈출 여부)
  * 최종 통과했는지

### 19.7.2 Repair success curve(수렴 곡선)

* x축: attempt 번호
* y축: 누적 성공률(pass by attempt n)

예:

* attempt 1에서 40% 통과
* attempt 3에서 70% 통과
* attempt 5에서 75% 통과
  → “attempt 3 이후는 비용 대비 효과가 낮다” 같은 결론 도출 가능

### 19.7.3 Repair directive effectiveness(프롬프트 기반)

* repair prompt에 포함된 directive 종류별 성공률

  * 예: “token boundary에만 '-'” 지시가 들어갔을 때 개선율

(이건 프롬프트 전문 로깅이 있을 때 매우 강력한 분석이 됩니다.)

---

## 19.8 (7) 승격/라우팅 분석 템플릿

### 19.8.1 Planner 사용 분석

* planner 호출률
* planner 호출 후 1~2 attempt 내 개선율
* planner 호출이 오히려 실패를 늘린 케이스 비율(부작용)

### 19.8.2 Model escalation 분석

* escalation rate(몇 %가 상위 모델로 갔나)
* escalation success rate(갔을 때 몇 %가 해결됐나)
* escalation cost(추가 시간/토큰)

### 19.8.3 Routing policy 평가

* signature별 권장 라우팅 vs 실제 라우팅 비교
* “잘못 라우팅”된 케이스 샘플(예: system error인데 repair로 돌린 경우)

---

## 19.9 (8) 시스템 안정성/관측 가능성 섹션 템플릿

### 19.9.1 System error breakdown

* HTTP 500
* timeout
* OOM
* connection error
* schema/format error

### 19.9.2 Observability score

* system error 발생 시 error body가 로그에 남은 비율
* prompt/response 전문이 남은 비율(프라이버시/보안 정책 내에서)

### 19.9.3 실험 신뢰도 판단

* system_fail_rate가 X% 이상이면 “모델 비교 결론을 내리지 않는다”
* 관측 가능성이 낮으면 “원인 분석 불가 → 개선 실험 우선”

---

## 19.10 (9) 케이스 스터디 섹션 템플릿(대표 3~5개)

각 케이스는 “로그 기반으로 재현 가능한 이야기”가 되어야 합니다.

### 케이스 템플릿

* Function/spec: `slugify.yml`
* Attempt sequence(요약):

  * A1: signature / stage
  * A2: signature / stage
  * ...
* 최종 결과: pass / fail
* 핵심 원인: (예: 구분자 누락 고정점)
* 효과적이었던 조치: (예: directive 변경, 승격)
* 다음 액션: (예: examples 1개 추가, constraint 최소 추가 등)

---

## 19.11 (10) 개선 권고 섹션 템플릿(다음 실험 액션 아이템)

정량 리포트의 목적은 “보기 좋게”가 아니라 **다음 액션을 자동으로 뽑는 것**입니다.

### 권고 작성 원칙

* 각 권고는 “어떤 지표가 왜 문제인지”와 연결되어야 함
* 우선순위는:

  1. system 안정성
  2. stage 병목
  3. 고정점
  4. 비용
  5. 품질(Audit)

### 권고 템플릿 예시

* 관측: `constraint_fail_rate=35%` + `constraint_import_violation` top1
  → 권고: import 의존 탐지(AST) 후 라우팅/승격 정책 강화
* 관측: `examples_fail_rate=50%` + `missing_separators` stuck length 높음
  → 권고: repair directive에 “token boundary only” 반례 고정 삽입 + examples 보강
* 관측: `system_fail_rate=10%` + error body 로깅 20%
  → 권고: 요청/응답 전문 로깅을 필수화(모델 성능 판단 보류)

---

## 19.12 MVP1 slugify 같은 단일 함수에도 이 템플릿이 유효한가?

유효합니다. 단, 범위를 축소해 쓰면 됩니다.

* pass@k / stuck rate / signature 분포가 핵심
* stage breakdown은 대개 examples/constraint 중심으로 나타남
* 케이스 스터디는 오히려 단일 함수가 가장 명확함

그리고 함수가 10개, 100개, 1000개로 늘어나면 이 템플릿이 그대로 “대시보드”가 됩니다.

---

## 19.13 이 장의 결론

runs.jsonl 같은 로그는 단순 기록이 아니라 FineDev의 자산입니다.
정량 리포트 템플릿을 표준화하면:

* 모델을 오판하지 않고,
* 병목을 빠르게 찾고,
* 고정점 탈출 정책을 개선하고,
* 경험치 DB로 연결해
* 결국 “전기세 공장”의 생산성을 계속 올릴 수 있습니다.

# 20장. MVP 단계별 확장 설계

이 장은 FineDev를 **MVP1 → MVP2 → MVP3 → MVP4 → MVP5**로 확장하는 설계를 “복잡도를 쉽게 증가”시키는 관점에서 정리합니다. 핵심은 단순합니다.

* MVP1은 **공정이 성립하는지**를 확인하는 최소 단위(단일 함수)
* 이후 MVP들은

  * 함수 수(스케일)
  * 의존성(그래프)
  * 수렴 정책(고정점 탈출)
  * 품질 옵션(Audit)
  * 운영 안정성(대규모 실행/리포팅)
    을 단계적으로 추가합니다.

> 사용자가 정한 목표에 맞춰 “CLI 기반”으로 MVP1~MVP4를 구성하고,
> “함수 1000개 규모(대형 프로젝트)”를 MVP5로 둡니다.

---

## 20.1 전체 로드맵 한눈에 보기

### MVP1 — 단일 함수 공정 성립

* 입력: spec 1개
* 출력: 구현 1개 + 테스트 통과
* 목적: 스펙→생성→게이트→수리→로그가 돌아간다

### MVP2 — 고정점 탈출 자동화(라우팅/패치/리라이트)

* 입력: spec 1~10개
* 목적: attempts만 늘려도 안 풀리는 문제를 “정책 전환”으로 해결

### MVP3 — 의존성 그래프/카탈로그 주입 + 다함수 생산

* 입력: spec 10~100개
* 목적: topo 순서로 조립되는 Micro Orchestration을 실제로 돌린다

### MVP4 — 운영/데이터화(리포트/DB/회귀 방지)

* 입력: spec 100~300개(권장)
* 목적: 경험치 DB와 정량 리포트로 “공정이 스스로 개선”되게 만든다

### MVP5 — 함수 1000개 대형 프로젝트(전기세 공장)

* 입력: spec 1000개(+ deps)
* 목적: 실패 격리, 재시작, 병렬 실행, 승격 정책까지 포함한 산업형 운영

---

## 20.2 MVP1 (Baseline) — “공정 최소 단위” 고정

### 목표

* 단일 함수가 pass@k로 수렴 가능한지 확인
* 시스템/서빙 이슈를 분리할 수 있는지 확인

### 구성 요소

* Spec parser
* Provider(dummy/ollama)
* Gate chain: extract → syntax → constraints → examples → pytest
* Runs logging(runs.jsonl)

### MVP1에서 ‘하지 않는 것’

* 복잡한 라우팅
* AST 기반 정적 분석
* 의존성 그래프
* 경험치 DB
* Audit

### MVP1의 성공 정의

* 실패가 “원인 분해 + 로그”로 남고,
* 적어도 일부 케이스는 attempts 내 수렴한다.

---

## 20.3 MVP2 — 고정점 대응 엔진(Policy Upgrade)

MVP2는 “모델이 못하는 게 아니라 **고정점이 풀리지 않는 문제**”를 해결하기 위한 단계입니다. 즉 Output Fine Tuning이 본격적으로 들어옵니다.

### MVP2의 목표

* 동일 signature 반복을 감지하고, 자동으로 정책을 바꿔서 수렴시키기
* “휴리스틱”을 계약에 섞지 않으면서도 수리력을 올리기

### 추가되는 기능(핵심)

1. **Failure Signature 표준화**

* 모든 실패를 signature로 분류
* stuck length / stuck rate 계산

2. **Routing 정책 테이블**

* signature → action 매핑

  * 예: `constraint_import_violation` → “import 사용 여부 AST 검사” → 재구현 지시 또는 승격
  * 예: `example_missing_separators` → token-boundary 지시 + 반례 삽입

3. **Patch Mode(최소 수정 강제)**

* “전체 재작성” 대신
* 기존 코드 유지 + 필요한 부분만 수정하도록 프롬프트를 전환

4. **Deterministic Rewrite 룰셋(안전 범위)**

* 로직을 바꾸지 않는 안전 정규화
* AST 기반으로 “미사용 import 제거” 같은 안전 리라이트

5. **Planner(옵션) 강화**

* planner가 생성하는 것은 “설명”이 아니라 **짧은 edit directives**
* planner는 고정점에서만 호출(비용 통제)

### MVP2 성공 기준

* MVP1에서 고정점이었던 케이스 일부가

  * attempts 증가 없이(또는 적은 증가로)
  * 정책 전환으로 해결됨
* stuck rate가 감소

---

## 20.4 MVP3 — Micro Orchestration 확장(그래프/카탈로그/다함수)

MVP3부터 “함수 단위 개발”이 실제로 스케일하기 시작합니다.

### MVP3의 목표

* 10~100개 함수가 **의존성 순서**로 자동 생산/조립되는지 확인
* 카탈로그 주입이 프롬프트 길이를 통제하면서도 효과적인지 검증

### 추가되는 기능(핵심)

1. **Dependency Graph + Topo Build**

* spec에 deps를 명시
* topo sort로 build order 결정
* 실패 노드 격리(전체 중단 방지)

2. **Catalog Injection**

* 전체 카탈로그를 넣지 않고 deps에 해당하는 항목만 선택 주입
* 모듈 단위 카탈로그 분리

3. **API Export 자동화**

* `__init__.py`에서 공개 함수 자동 export
* import 규칙 통일(테스트에서 항상 같은 방식으로 호출)

4. **Per-function isolated retries**

* 실패 함수만 재시도
* 성공 함수는 캐시/잠금(lock) 처리

### MVP3 성공 기준

* 다함수 프로젝트에서 “일부 실패가 전체를 막지 않는다”
* 재실행 시 이미 성공한 함수는 재생성하지 않고 이어서 진행 가능
* pass@k와 time-to-pass가 스케일에 따라 예측 가능하게 유지

---

## 20.5 MVP4 — 운영/데이터화(리포트, 회귀 방지, 경험치 DB)

MVP4는 “기술 데모”에서 “운영 가능한 공정”으로 전환하는 단계입니다.

### MVP4 목표

* 로그 기반 정량 리포트 자동 생성(19장 템플릿)
* 경험치 DB로 반복 실패 비용 감소
* 회귀(regression) 방지 체계 구축

### 추가되는 기능(핵심)

1. **Report Generator**

* runs.jsonl → KPI 산출(pass@k, stage breakdown, signature topN, stuck metrics)
* 실험 간 비교(모델/프롬프트/정책 변경 효과)

2. **Experience DB(실패 시그니처 처방전)**

* signature별 “검증된 edit directive” 저장
* 특정 케이스(스펙 fingerprint)별 성공 패치 저장
* 다음 실행에서 자동 주입

3. **Regression Suite**

* 이전에 통과했던 함수는 “항상 통과해야 한다”
* 정책 변경 시 회귀가 생기면 즉시 탐지

4. **Quality 옵션 채널(Audit AI)**

* 기본은 report-only
* 품질 권고를 지표로만 관리(계약 오염 방지)

### MVP4 성공 기준

* 동일 스펙 세트 재실행 시 pass@k 및 비용이 개선/안정
* 반복 실패(signature)가 줄어듦(경험치 DB 효과)
* 회귀가 잡힘

---

## 20.6 MVP5 — 함수 1000개 대형 프로젝트(산업형 운영)

MVP5는 사용자가 말한 “1000개든 10000개든 똑같이 적용”되는 단계입니다. 이 단계부터는 모델보다 **운영 시스템**이 핵심 경쟁력입니다.

### MVP5 목표

* 1000개 함수의 대규모 빌드/수리/승격을 “중단 없이” 처리
* 병렬 실행과 재시작/체크포인트로 “전기세 공장” 구현

### MVP5에서 반드시 필요한 기능(핵심)

1. **Work Queue + 병렬 워커**

* 독립 함수는 병렬 생성/검증 가능
* deps가 있는 함수는 topo 단계별로 워커 배치

2. **Checkpoint/Resume**

* 중간에 멈춰도 다음 실행에서 이어서 진행
* 성공 결과 캐시/아티팩트 고정

3. **Hotspot 관리**

* 자주 실패하는 핵심 유틸(병목 노드)을 우선적으로 강화

  * 스펙 보강
  * 승격 기본 적용
  * 경험치 DB 처방 강화

4. **Escalation Budgeting(승격 예산)**

* 상위 모델 호출은 비용이 크므로 예산을 둠
* 예: “전체 함수의 5%까지만 12b/클라우드 승격 허용”
* 나머지는 retry/patch/리라이트/스펙 보강으로 해결

5. **Test Strategy Scaling**

* pytest 전체를 매번 돌리면 비용 폭발
* 계층화:

  * examples(빠름) → 유닛 테스트(중간) → 통합 테스트(무거움)
* 변경 영향 범위 기반 테스트 선택(가능하면)

6. **Observability/Alerting**

* system error rate 상승 시 자동 중지/재시도 정책
* error body/프롬프트/결과 샘플링 저장

### MVP5 성공 기준

* 함수 1000개 빌드 완료율, 총 시간, 비용이 “예측 가능”
* 실패가 격리되고 전체 공정이 붕괴하지 않음
* 경험치 DB 때문에 재실행 시 점점 빨라짐
* 승격 예산 내에서 목표 품질 달성

---

## 20.7 단계별 “복잡도 증가”가 쉬운 이유(설계 철학)

이 로드맵이 자연스럽게 확장되는 이유는, 각 MVP가 아래를 “새로 발명”하는 게 아니라 **기존 구조에 레이어를 얹는 방식**이기 때문입니다.

* MVP1: 파이프라인(단일 유닛)
* MVP2: 라우팅/수리 정책(유닛 수렴 강화)
* MVP3: 그래프/조립(유닛 확장)
* MVP4: 데이터화/회귀 방지(운영화)
* MVP5: 병렬/예산/관측(산업화)

즉, 코어는 항상 동일합니다.

* spec → generate → gate → repair → log

---

## 20.8 이 장의 결론

FineDev의 MVP 확장은 “모델을 키운다”가 아니라:

* **공정을 강화하고**
* **고정점을 정책으로 깨고**
* **함수 수를 늘려도 붕괴하지 않게 운영하며**
* **로그/DB로 점점 더 결정론적으로 만든다**

는 방향으로 진행됩니다.

# 21장. UI/Web 프로젝트로의 확장

UI/Web 프로젝트는 FineDev 관점에서 “코드 난이도”보다 **취향/일관성/산출물 다양성** 때문에 실패가 늘어나는 영역입니다. 즉 백엔드/유틸 함수처럼 “정답이 하나”인 문제가 아니고, 팀/브랜드/사용자 맥락에 따라 정답이 달라집니다. 그래서 기업형 개발에서 UI를 AI에 맡기는 걸 배제해 왔던 건 합리적이었습니다.

그런데 당신이 말한 것처럼, **UI/UX를 설계(템플릿)로 빼버리면** 상황이 바뀝니다. FineDev는 “정답 불확실성”을 **설계와 템플릿으로 결정론화**하고, 남는 부분을 함수 단위/컴포넌트 단위로 생산하는 방식으로 UI/Web까지 확장할 수 있습니다.

---

## 21.1 UI/Web에서 실패가 늘어나는 근본 원인(왜 ‘모델 실수’가 아니라 ‘문제 구조’인가)

UI/Web은 아래 특성이 있습니다.

### 1) 정답이 고정되지 않는다(취향/브랜드/컨텍스트)

* 버튼 모양, 간격, 색, 카피 문구 등은 테스트로 고정하기 어렵습니다.
* 따라서 “프롬프트를 늘리면” 오히려 모델이 혼란해집니다.

### 2) 산출물이 다중 파일/다중 레이어다

* component, page, route, api client, state, styles, assets…
* 작은 실수(경로/이름/import)가 전체를 깨뜨립니다.

### 3) 빌드/런타임 환경 의존이 크다

* bundler(vite/webpack), tsconfig, eslint, prettier, next config…
* 모델이 코드만 맞추면 되는 게 아니라 “환경 규칙”을 맞춰야 합니다.

### 4) 회귀가 쉽게 생긴다

* UI는 “동작은 되는데 망가진” 상태가 많습니다.
* 즉 컴파일/테스트 통과만으로 품질 보장이 안 됩니다.

그래서 UI/Web 확장에서는 FineDev의 두 원칙이 더 중요해집니다.

* **Micro Orchestration**(작은 단위로 쪼개기)
* **휴리스틱 분리(Audit)**(품질은 옵션 레이어로)

---

## 21.2 UI/Web 확장의 핵심 전략: “UI를 코드로 생성하지 말고, UI 규격을 먼저 고정한다”

당신이 말한 결론을 FineDev식으로 정리하면 이렇습니다.

> UI/UX가 전체 작업의 90%를 차지한다면,
> 그 90%를 “설계/템플릿”으로 빼서 고정하고,
> AI는 나머지 10%(반복 구현)만 하게 만들어야 한다.

FineDev는 이를 **Design-as-Spec(설계=스펙)**로 부릅니다.

### Design-as-Spec에 포함되는 것(권장)

* 디자인 시스템(색, 타이포, 간격, 컴포넌트)
* 레이아웃 템플릿(페이지 그리드/네비/폼)
* 컴포넌트 카탈로그(사용 가능한 UI 블록 목록)
* 라우팅 규칙(폴더 구조, import path 규칙)
* 상태 관리 규칙(예: React Query만 사용, Zustand만 사용 등)
* API 호출 규칙(예: openapi client 사용, fetch wrapper 사용 등)

이걸 고정하면, 모델은 “창작”이 아니라 “조립”을 하게 됩니다.

---

## 21.3 UI/Web에서의 Micro Orchestration 단위: Function → Component → Page

백엔드에서는 function=file이 기본이었다면, UI에서는 단위가 바뀝니다.

### 권장 단위 계층

1. **UI atom/molecule component** (Button, Input, Badge 등)
2. **feature component** (UserCard, SearchPanel 등)
3. **page** (Route 단위)
4. **layout** (App shell, Dashboard layout)
5. **integration** (API client, state wiring)

FineDev 운영 관점에서는 다음 규칙이 좋습니다.

* component 1개 = 파일 1개(원칙 유지)
* page 1개 = 파일 1개
* layout은 템플릿 고정(가능하면 AI가 건드리지 않게)

---

## 21.4 UI/Web용 Spec 템플릿(계약을 최소화하면서도 수렴시키는 방식)

UI/Web 스펙은 “예시 입력→예시 출력”이 백엔드처럼 단순하지 않습니다. 대신 “결정론적 검사 가능한 것”만 계약으로 둡니다.

### UI component spec 예시(필드)

* `name`: UserCard
* `type`: component
* `props`: `{ user: User }`
* `behaviors` (결정론적 가능):

  * 클릭 시 onSelect 호출
  * user.name 표시
* `constraints`:

  * 금지 라이브러리/허용 라이브러리
  * import path 규칙
  * styling 방식(Tailwind만, CSS module 금지 등)
* `files`:

  * 생성 경로 고정
* `tests`:

  * RTL(React Testing Library) 스냅샷/쿼리 테스트(최소)
* `notes`:

  * 디자인 시스템 링크/토큰

### UI에서 examples 대신 중요한 것

* “컴포넌트가 어떤 DOM을 가져야 한다”를 테스트로 고정

  * 예: `getByRole('button', {name: 'Save'})`
* “상태 변화”를 이벤트 기반 테스트로 고정

  * click → callback called

즉 UI에서도 **결정론적 게이트**를 만들 수 있습니다. 다만 “픽셀 완벽” 대신 “행동/접근성/구조”로 고정하는 것이 현실적입니다.

---

## 21.5 결정론적 게이트(UI/Web 버전): 무엇을 강제할 것인가

UI/Web 확장에서 가장 중요한 건 게이트 설계입니다. 권장 게이트는 아래 순서입니다.

1. **format/extract**: 파일 생성 형태 정리
2. **lint/typecheck**: eslint + tsc(또는 next build)
3. **unit tests**: jest/vitest + RTL
4. **build**: `npm run build` (또는 `next build`)
5. **smoke e2e(선택)**: playwright/cypress 최소 시나리오

### 핵심 포인트

* UI는 pytest 하나로 끝나지 않습니다.
* 대신 gate를 “싸게→비싸게” 계층화해야 합니다.

  * lint/typecheck가 가장 싸고 효과적
  * build/e2e는 비용이 크니 제한적으로

---

## 21.6 Output Fine Tuning(UI/Web 버전): 고정점 패턴과 탈출법

UI/Web에서도 고정점은 생깁니다. 다만 유형이 다릅니다.

### 대표 고정점 패턴

* import 경로 반복 오류(alias, 상대경로)
* 타입 에러 반복(Props mismatch, any 남발)
* 상태 관리 패턴 위반(규칙 무시하고 useState 난사)
* 디자인 시스템 무시(임의 className, 인라인 스타일)
* “빌드 통과를 위해 이상한 우회” (ts-ignore, disable lint)

### FineDev식 탈출 정책

* 실패 시그니처를 UI에 맞게 정의

  * `ts_prop_mismatch`
  * `import_path_violation`
  * `lint_rule_violation`
  * `forbidden_style_usage`
  * `ts_ignore_added`
* signature별 라우팅

  * path 오류 → 결정론적 rewrite(경로 자동 교정) 가능
  * props mismatch → patch mode로 최소 수정
  * ts-ignore 남발 → 강제 금지 constraint(결정론) + 재구현 지시
* 고정점이면 승격(특히 planner/fixer 승격이 효과 큼)

---

## 21.7 UI/UX “휴리스틱”은 어떻게 다루나: Audit AI의 진짜 무대

UI에서 휴리스틱은 훨씬 크기 때문에 Audit AI가 특히 중요합니다.

### UI Audit가 할 수 있는 것

* 접근성(a11y) 권고: aria, role, contrast(일부는 도구화 가능)
* 디자인 시스템 준수 체크(토큰 사용 여부)
* 레이아웃 일관성 권고(간격/그리드)
* 카피/문구 톤 권고(브랜드 가이드)

### 분리 원칙 적용

* Audit 결과로 빌드를 실패시키지 않음(report-only 기본)
* 다만 “정책 위반”은 계약으로 둘 수 있음

  * 예: 인라인 스타일 금지, 임의 색상 금지 등(정규식/AST로 판정 가능하면)

---

## 21.8 “템플릿이 필수”를 FineDev로 구현하는 방법: Scaffold Locking

UI/Web 프로젝트에서 가장 중요한 설계는 “AI가 건드리면 안 되는 영역”을 고정하는 것입니다.

### Scaffold Locking 전략

* 폴더 구조/라우팅/빌드 설정은 템플릿으로 고정
* AI가 수정 가능한 영역을 제한

  * 예: `src/components/**`, `src/pages/**`만 생성/수정 허용
* 금지 파일 목록:

  * package.json, tsconfig, vite.config, next.config 등
* 변경이 필요하면 “별도 승인 흐름”으로 분리

이렇게 하면 모델이 “무한 자유 소설쓰기”로 빠질 가능성이 급감합니다.

---

## 21.9 UI/Web 확장 MVP 로드맵(이전 MVP와 연결)

기존 MVP(클리 기반) 위에 UI 확장을 얹는 방식은 아래처럼 자연스럽습니다.

### UI-MVP1(= 기존 MVP1 변형)

* 컴포넌트 1개 생성
* lint/typecheck + RTL 테스트 통과
* 템플릿 고정 + 생성 영역 제한

### UI-MVP2

* 고정점 라우팅(경로/타입/스타일 위반)
* patch mode 강화
* planner/fixer 역할 분리

### UI-MVP3

* feature 단위(컴포넌트 10~50개)
* 카탈로그 주입(디자인 시스템 컴포넌트 목록)
* topo(컴포넌트 deps) 조립

### UI-MVP4

* 정량 리포트(빌드/린트/타입 실패 분해)
* 경험치 DB(경로/타입 오류 처방전)
* 회귀 방지(스냅샷/스토리북 기반 가능)

### UI-MVP5

* 대형 UI 프로젝트(페이지/컴포넌트 1000개도 가능)
* 병렬 워커 + 체크포인트
* e2e 최소화 + 변경 범위 기반 테스트 선택
* Audit 채널로 지속적 UI 품질 관리

---

## 21.10 이 장의 결론

UI/Web 프로젝트 확장은 “AI가 UI를 잘 그리게 만들자”가 아니라:

1. UI/UX의 90%를 **설계/템플릿으로 고정**하고
2. AI가 수정 가능한 영역을 **좁혀서 조립 작업으로 바꾸고**
3. 결정론적 게이트를 **lint/typecheck/build/test**로 계층화하고
4. 품질/취향은 **Audit로 분리**해 운영하는 방식으로

FineDev의 철학(공정 기반 개발)을 그대로 적용하는 것입니다.

# 22장. FineDev의 핵심 결론

이 장은 FineDev가 여러 실험(이전 세션의 4b↔12b, 대형 LLM 관찰, 그리고 이번 세션 MVP1 slugify 실험)에서 도출한 결론을 “한 장의 원칙”으로 정리합니다. 결론은 기술적 디테일보다 **개발 패러다임의 전환**에 가깝습니다.

> FineDev의 결론:
> **“모델이 개발을 한다”가 아니라 “공정이 개발을 한다.”**
> 모델은 공정의 부품이며, 개발의 신뢰성은 공정이 만든다.

아래는 이를 구성하는 핵심 결론들입니다.

---

## 22.1 결론 1 — 모델은 언제나 실수한다(크기와 무관)

### 관측된 사실

* gemma3:4b는 출력 안정성(형식/문법)에서 흔들림이 컸고
* gemma3:12b는 함수 단위에서는 실용권으로 들어왔지만
* 대형 LLM(qwen3-coder:480b-cloud 포함)도 “사소하지만 치명적인” 실수를 했다

### 의미

* “큰 모델이면 안전”이라는 가정은 운영에서 위험하다
* 개발은 99%가 아니라 **100% 실행 가능**이 목표이므로,
* 1% 실수는 치명적이다

따라서 모델 크기 경쟁만으로는 개발 자동화를 완성할 수 없습니다.

---

## 22.2 결론 2 — 코딩은 모델 단독으로 불가능하다. Orchestrator(공정)가 필수다

### FineDev가 말하는 Orchestrator(공정)

* 틀을 잡는다(스펙/환경/정책)
* 모델이 틀 안에서 일하게 한다(짧고 최소한의 지시)
* 결과를 검증/수리/승격으로 완성한다(수렴)

즉 “API 한 번 호출”은 개발이 아니라 “초안 생성”에 불과합니다.
개발을 하려면 **검증과 수리의 반복**이 필요합니다.

---

## 22.3 결론 3 — 실패의 대부분은 ‘모델’이 아니라 ‘시스템/서빙/러너’에서 생긴다

### 대표 사례

* HTTP 500의 원인이 서버 다운이 아니라 요청 포맷 오류였던 사례
* PAD_END만 나오는 현상이 모델 문제가 아니라 런타임/서빙 문제 가능성이 컸던 사례
* import 경로/패키징 문제로 코드가 맞아도 pytest가 실패한 사례

### 의미

* 원인 분해/로깅이 없으면 모델을 쉽게 오판한다
* 그래서 FineDev는 “관측 가능성(Observability)”을 최우선으로 둔다

---

## 22.4 결론 4 — 성공률을 올리는 가장 큰 레버는 “프롬프트”가 아니라 “게이트”다

모델을 설득하는 긴 프롬프트는 한계가 있습니다(특히 SLM).
반면 FineDev는 다음을 확인했습니다.

* 문법은 compile/ast로 100% 잡을 수 있다
* 예시는 즉시 실행/비교할 수 있다
* 테스트는 최종 판정이다

즉, **결정론적 게이트 체인**이 모델의 불안정성을 흡수하며 “수렴”을 만든다.

---

## 22.5 결론 5 — 프롬프트는 최소·명료 + 예시 중심이 가장 강하다

실험에서 강하게 지지된 가설:

* 규칙/형식/장황한 지시는 작은 모델을 흔들게 만들고,
* 오히려 실패를 늘린다
* 반면 examples(입출력) 몇 개는 모델을 강하게 고정한다

따라서 FineDev의 프롬프트 철학은:

* **짧게**
* **예시로**
* **필수 제약만**
  입니다.

---

## 22.6 결론 6 — “길이 축”은 별도 난이도 축이다(200라인 vs 500~1000라인)

이전 실험에서 확인된 것처럼:

* 12b도 500~1000라인 단일 파일은 완결성/문법/시간에서 불안정
* 컨텍스트/출력 길이를 늘리면 지연·실패·서버 불안정이 급증

결론:

* 로컬 SLM에서 “긴 파일 1회 생성”은 구조적으로 불리하다
* 따라서 **함수 단위/조각 생산**이 정답에 가깝다

---

## 22.7 결론 7 — Micro Orchestration(함수 단위 개발)은 SLM을 ‘실용화’하는 핵심 전략이다

함수 단위로 자르면:

* 출력 길이 감소 → 문법/완결성 안정
* 실패 격리 → 재작업 비용 감소
* deps/topo 조립 → 대규모 프로젝트도 운영 가능

또한 파이썬은 `__init__.py`/모듈 구조 덕분에 함수 단위 생산이 자연스럽습니다.

---

## 22.8 결론 8 — Output Fine Tuning(99%→100%)이 실제 자동화의 본질이다

사람이 보기엔 “사소한 버그”가,
운영에서는 “항상 발생하는 1%”입니다.

* 구분자 누락/과잉
* 구두점 잔존
* 비ASCII 처리
* import 정책 위반

이 1%를 잡는 것이 곧 경쟁력이며,
FineDev는 이를:

* failure signature
* stuck(고정점) 감지
* 라우팅/패치/승격
* 경험치 DB

로 해결하는 체계를 “Output Fine Tuning”이라 부릅니다.

---

## 22.9 결론 9 — 계약(결정론)과 휴리스틱(품질)은 반드시 분리해야 한다

계약을 늘리면 품질은 올라가지만,
동시에 공정이 복잡해져 모델 환각/실패가 늘 수 있습니다.

따라서 FineDev는:

* 결정론적으로 판정 가능한 것만 계약/게이트로
* 나머지는 Audit AI(옵션)로 분리

이 원칙으로

* 수렴 엔진은 안정적으로 유지하고
* 품질은 별도 레이어로 확장합니다.

---

## 22.10 결론 10 — “경험치 DB”가 있으면 SLM도 점점 결정론적으로 쓸 수 있다

반복되는 실패는 반복됩니다(특히 작은 모델).
FineDev는 이를 “모델의 한계”로 끝내지 않고:

* 실패 시그니처 + 성공한 처방(지시/패치)을 DB화하여
* 다음 실행에서 자동 주입/라우팅한다

즉,

* 시간이 갈수록 pass@k가 올라가고
* 비용이 내려가며
* 운영이 안정화됩니다.

이는 사용자가 말한 “전기세만 늘어나는 체계”로 수렴하는 핵심 장치입니다.

---

## 22.11 결론 11 — UI/Web도 배제할 필요가 없다(설계/템플릿 고정이 전제)

UI는 취향/일관성 때문에 AI가 어려워하지만,
그 어려움은 모델이 아니라 **문제 정의의 자유도**에서 옵니다.

* UI/UX를 디자인 시스템/템플릿으로 고정
* AI가 건드릴 수 있는 영역을 제한(scaffold locking)
* 게이트를 lint/typecheck/build/test로 계층화
* 품질은 Audit로 분리

이렇게 하면 UI/Web도 FineDev 공정에 포함시킬 수 있습니다.

---

## 22.12 FineDev의 한 문장 정리(브랜드 메시지)

당신이 브랜드화하려는 용어까지 포함해서 FineDev를 한 문장으로 요약하면:

> **FineDev = Micro Orchestration(작게 쪼개 생산) + Output Fine Tuning(마지막 1% 수렴)으로,
> 작은 모델도 실무 개발 공정으로 만드는 방법론**

---

## 22.13 최종 결론: 앞으로의 경쟁은 “모델”이 아니라 “공정”에서 난다

* 대형 모델은 누구나 쉽게 만들 수 없는 영역으로 수렴하고
* 반대로 FineDev 같은 공정 기술은

  * 저렴한 모델을 실용화하고
  * 기업 개발을 자동화하며
  * 새로운 비즈니스를 만드는 영역이 됩니다.

즉 FineDev는 “모델을 이기는 전략”이 아니라,
**모델을 부품화하여 개발을 산업화하는 전략**입니다.

# 23장. 실무 적용 가이드

이 장은 FineDev를 “실험”이 아니라 **실제 조직/프로젝트에 적용**할 때의 가이드입니다. 핵심은 기술 스택보다 **적용 순서와 운영 규칙**입니다. FineDev는 모델을 바꾸는 프로젝트가 아니라, **개발 공정을 재설계하는 프로젝트**이기 때문입니다.

---

## 23.1 어디에 먼저 적용할 것인가(적용 대상 선정)

FineDev는 모든 개발에 바로 동일 효과를 내지 않습니다. “수렴이 잘 되는 유형”부터 시작해야 조직이 빨리 이득을 봅니다.

### 1순위(가장 잘 맞음)

* **함수/유틸 중심**: 문자열 처리, 파서, 데이터 변환, 계산 로직
* **테스트가 명확**: 입출력 예시/단위테스트로 요구 고정 가능
* **의존성이 낮음**: 외부 API/DB 없이도 검증 가능

### 2순위

* 백엔드 서비스의 **핵심 로직 모듈**
* 내부 도구의 서버/배치 작업
* ETL/데이터 파이프라인의 변환 단계

### 3순위(조건부)

* UI/Web (템플릿/디자인 시스템이 이미 고정되어 있을 때)
* 복잡한 서비스 통합(외부 시스템 의존이 강한 경우)

### 피해야 할 시작점(초기에는)

* 500~1000라인 단일 파일 대규모 생성
* 요구가 자주 바뀌고 테스트가 없는 프로젝트
* 서빙/인프라가 불안정한 환경(측정이 무너짐)

---

## 23.2 도입 전 준비물: “모델”이 아니라 “공정 자산”을 만든다

실무 적용에서 가장 중요한 준비물은 다음 4가지입니다.

1. **스펙 포맷 표준**

* YAML/JSON 등 어떤 형식이든 상관없지만 “팀 표준”이 있어야 함
* 최소: signature, purpose, examples, constraints(필수만), deps(있으면)

2. **결정론적 게이트 체인**

* syntax → constraints → examples → tests
* “싸게 실패시키는 순서”로 고정

3. **로깅/재현성**

* 프롬프트 전문(또는 재구성 가능한 수준)
* 모델 응답 원문
* stage별 결과/실패 메시지
* 이게 없으면 개선이 불가능합니다.

4. **운영 정책**

* attempts 기본값
* 고정점 감지 기준
* 승격 조건/예산
* audit on/off 기준

---

## 23.3 실무 적용의 표준 운영 플로우(권장)

### Step A. 설계(=템플릿) 확정

* “무엇을 만들지”를 스펙과 테스트로 고정
* 함수 단위로 쪼개고 deps를 명시
* 공개 API는 `__init__.py` 같은 곳에 정리

### Step B. 생산(생성/수리/수렴)

* Producer 모델로 후보 생성
* 게이트로 실패 원인 분해
* Repair 루프로 pass@k 수렴
* 고정점이면 라우팅/승격

### Step C. 통합/회귀 방지

* 통과한 산출물은 “아티팩트”로 고정
* 재실행 시 같은 스펙은 재생성하지 않거나 캐시
* 정책 변경 시 회귀 테스트로 안전장치

### Step D. 경험치 DB 축적

* 실패 시그니처별 처방(지시문/패치)을 축적
* 반복 실패 비용을 점점 줄임

---

## 23.4 역할 분담: “개발자 역할이 사라지는 게 아니라 바뀐다”

FineDev가 들어오면 개발자는 코드를 많이 치는 사람이 아니라, 아래 역할이 강해집니다.

### 1) 설계자(스펙/테스트 디자이너)

* 요구를 예시와 테스트로 고정하는 능력
* deps를 잘 설계해서 “함수 단위 생산”이 가능하게 함

### 2) 공정 엔지니어(Orchestrator)

* 게이트 순서/실패 메시지 설계
* 라우팅/승격/리라이트 정책 설계
* 시스템 안정성/관측 가능성 관리

### 3) 품질 감독(Audit/리뷰)

* 휴리스틱 품질을 분리해서 점진적으로 개선
* 보안/성능/유지보수성 리스크를 통제

---

## 23.5 “계약을 무한히 늘리지 않는” 실무 규칙

당신이 지적한 핵심 문제(계약을 넣기 시작하면 끝이 없다)를 해결하는 실무 규칙입니다.

### 규칙 1) 계약에는 “판정 가능한 것”만 넣는다

* 컴파일/AST/정규식/테스트로 판정 가능한 것만

### 규칙 2) 계약은 “실패를 줄이는 최소치”까지만

* 예: slugify에서 출력 문자 집합을 `[a-z0-9-]`로 제한
  → 이건 품질 취향이 아니라 “요구 정의”에 해당하므로 가치가 큼
* 반면 스타일/리팩터링은 audit로 보냄

### 규칙 3) 휴리스틱은 무조건 Audit 채널로 분리

* 보고서로 남기고, 필요할 때만 반영
* 빌드 실패로 연결하지 않는다(초기에는 특히)

---

## 23.6 “모델 반항”과 고정점에 대한 운영 가이드

실무에서 가장 체감되는 문제는 “왜 자꾸 말을 안 듣냐”입니다. FineDev는 이를 감정이 아니라 **운영 신호**로 봅니다.

### 23.6.1 반항처럼 보이는 현상의 실체 3종

1. 요구가 애매해서 모델이 합리적 선택을 한 것
2. 모델의 습관적 레시피(정규식, 특정 패턴)로 회귀한 것
3. 프롬프트/수리 지시가 과잉 또는 모순이라 “가장 단순한 만족”으로 도망간 것

### 23.6.2 고정점 탈출의 표준 정책(권장)

* 동일 signature 2회 반복 → **정책 전환 트리거**

  1. repair directive를 “반례 1줄”로 강화
  2. patch mode 전환(최소 수정)
  3. examples 1개 추가(고정점 직접 타격)
  4. planner/fixer 승격 또는 교차 모델
  5. (가능하면) 결정론적 리라이트

“attempts를 더 준다”는 가장 마지막 선택이 되도록 합니다.

---

## 23.7 모델 구성 실무 팁: “Producer는 작게, Fixer는 강하게”

비용 대비 효과가 좋은 운영 패턴입니다.

### 권장 역할 분리

* Producer: 4b~12b (대량 생산)
* Fixer/Planner: 12b 또는 상위 모델(고정점 탈출 담당)

이렇게 하면:

* 대부분은 저렴하게 해결하고
* 어려운 5~10%만 비싼 모델로 처리할 수 있습니다.

즉 “저렴한 모델로 고성능 모델과 경쟁”의 실전 형태가 됩니다.

---

## 23.8 팀 도입 절차(현실적인 단계)

### 1주차: MVP1 수준(단일 함수)

* 스펙 포맷 확정
* 게이트 체인 확정
* 로그/리포트 1차 생성

### 2~3주차: MVP2 수준(고정점 대응)

* failure signature 정의
* 라우팅 정책 테이블 도입
* patch mode / 최소 리라이트 적용

### 1~2개월: MVP3~4 수준(확장/운영화)

* deps/topo build
* 경험치 DB(처방전)
* 회귀 방지(Regression Suite)
* 정량 리포트 자동화

### 이후: MVP5 수준(1000 함수 공장)

* 워커/병렬
* 체크포인트/재시작
* 승격 예산
* 테스트 계층화

---

## 23.9 UI/Web 실무 적용 가이드(요약)

UI는 “AI가 디자인”하면 망하기 쉽지만, FineDev는 방향을 바꿉니다.

* 디자인 시스템/컴포넌트 템플릿을 고정
* AI가 수정 가능한 영역을 제한(scaffold locking)
* lint/typecheck/build/test로 게이트를 계층화
* 픽셀은 audit, 기능은 테스트로

즉 UI도 “창작”이 아니라 “조립”으로 바꿔서 운영합니다.

## 23.10 실무에서 흔한 실패 원인과 처방(체크리스트)

### 실패 원인

* [ ] 패키징/경로 문제로 import가 깨짐
* [ ] 로깅이 부족해 실패 원인을 모름
* [ ] 프롬프트가 길어져 SLM이 흔들림
* [ ] attempts만 늘리고 정책 전환이 없음
* [ ] 휴리스틱을 계약에 넣어 공정이 복잡해짐
* [ ] 시스템 에러(500/timeout)를 모델 실패로 오판

### 처방

* [ ] editable install/프로젝트 스캐폴딩 고정
* [ ] stage별 게이트 결과 + 프롬프트/응답 전문 로깅
* [ ] examples 중심 + 최소 제약
* [ ] 고정점 트리거(2회 반복) → 라우팅/승격
* [ ] Audit 분리(Report-only)
* [ ] 시스템 안정성 KPI로 별도 관리

## 23.11 이 장의 결론

FineDev를 실무에 적용하는 핵심은 기술 선택이 아니라 운영 원칙입니다.

1. **설계(스펙/테스트)가 곧 템플릿**이다
2. **함수/컴포넌트 단위로 쪼개** 생산한다
3. **결정론적 게이트**로 실패를 분해하고
4. **Output Fine Tuning**으로 1% 오류를 수렴시키며
5. **휴리스틱은 Audit로 분리**하고
6. **경험치 DB + 리포트**로 공정이 점점 결정론화된다

결국 “모델로 개발”이 아니라 “공정으로 개발”이 실무 자동화의 정답이라는 결론으로 수렴합니다.
