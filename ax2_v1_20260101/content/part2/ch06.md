 
## 6장. 프롬프트 엔지니어링: “잘 말하기”가 아니라 “요구사항·제약·검증”으로 설계하기

### 1) 개요: 프롬프트는 UI가 아니라 ‘프로그램(명세)’이다

프롬프트는 그냥 질문을 잘 던지는 요령이 아닙니다. 실무에서 프롬프트는 사실상 **요구사항 명세서 + 실행 정책 + 출력 계약**입니다.
같은 모델도 프롬프트 설계에 따라 품질, 재현성, 비용이 크게 갈립니다.

* PoC 단계: 프롬프트가 “대화”처럼 동작해도 괜찮음
* 제품 단계: 프롬프트가 **반복 실행**돼도 결과가 안정적이어야 함
  → 그래서 **구조화 출력(7장), 툴 호출(8장), RAG(9~10장), 평가(22장)**로 연결됩니다.

이 장은 “프롬프트를 코드처럼 다루는 방법”을 중심으로, **패턴(templates), 디버깅(실패 분석), 테스트(회귀), 운영(버전관리)**까지 한 번에 잡습니다.

---

### 2) 학습 목표

1. 좋은 프롬프트를 “말빨”이 아니라 **구성 요소(역할·입력·제약·출력·검증)**로 설명
2. 실패 유형(환각/탈선/형식 깨짐/과장/정책 위반)을 원인별로 분해하고 수정
3. 프롬프트 템플릿과 버전관리를 통해 재현 가능한 개선 루프를 구성
4. 모델 파라미터(temperature/top-p)와 프롬프트의 역할 분담을 이해
5. 프롬프트 테스트(리그레션)와 평가를 붙여 “제품형”으로 만들기

---

## 3) 프롬프트의 기본 구조(실무 표준 구성)

프롬프트를 아래 5개 파트로 나눠 설계하면, 대부분의 문제가 줄어듭니다.

### 3.1 역할(Role) / 목표(Goal)

* “너는 무엇을 하는 존재인가”를 역할로 고정
* 목표는 “무엇을 산출해야 하는가”를 한 문장으로 명확히

**예**: “너는 사내 IT 헬프데스크 상담원이다. 사용자의 질문에 대해 내부 정책 문서 근거를 인용해 답한다.”

### 3.2 입력(Input) / 컨텍스트(Context)

* 모델에 필요한 정보만 주기(필요 이상으로 길면 성능이 떨어질 수 있음)
* 컨텍스트는 출처/권한/시간을 포함하면 품질이 올라갑니다.

### 3.3 제약(Constraints)

* 반드시 해야 할 것 / 하지 말아야 할 것
* 금칙어, 정책 위반 금지, 추측 금지(근거 없으면 모른다), 길이 제한 등

### 3.4 출력 형식(Output Format)

* 자연어로 “그럴듯하게” 말하게 두지 말고, **형식을 강제**하는 방향이 유리
* 7장의 구조화 출력(JSON Schema)로 이어짐

### 3.5 검증/자기점검(Verification)

* 모델에게 스스로 체크하도록 지시하거나(“근거가 없으면 ‘모른다’”),
* 외부에서 결과를 검증하고 실패 시 재시도하도록 설계

---

## 4) 핵심 원리: 프롬프트 품질은 “정보·제약·검증”의 균형이다

### 4.1 정보가 부족하면: 환각/추측

* 모델은 “모른다”를 기본값으로 갖지 않음 → 빈칸을 그럴듯하게 채움
* 대응: RAG/툴 호출/근거 요구/불확실성 표현

### 4.2 정보가 너무 많으면: 주의 분산/탈선

* 긴 컨텍스트는 비용뿐 아니라 **정확도**도 떨어뜨릴 수 있음(관련 정보가 묻힘)
* 대응: 요약/필터링/“필요한 부분만 제공(RAG)” 전략

### 4.3 제약이 약하면: 장황/형식 깨짐/정책 위반

* 대응: 출력 계약(형식), 금지 규칙, stop 조건, 구조화 출력

### 4.4 제약이 과하면: 답변 회피/품질 저하

* “절대 하지 마”가 너무 많으면 모델이 소극적으로 변함
* 대응: 필수/선택 제약을 구분하고, 우선순위를 명시

---

## 5) 프롬프트 패턴 라이브러리(현업에서 바로 쓰는 것들)

### 5.1 지시형 패턴(Instruction-first)

* 핵심 지시 → 입력 → 출력 형식 → 제약 순으로 구성
* 간결하고 유지보수 쉬움

### 5.2 예시 기반 패턴(Few-shot)

* “좋은 입력-출력 예시”를 1~3개 제공해 행동을 유도
* 분류/추출/톤 맞추기에 효과적
* 단, 예시가 길면 비용↑, 오래되면 오염(원치 않는 습관 학습) 가능

### 5.3 역할 기반 패턴(Role + rubric)

* 역할과 함께 평가 기준(루브릭)을 넣어 품질을 끌어올림
* 예: “정확성>간결성>친절함 우선순위로 답하라”

### 5.4 단계적 작업 패턴(Plan → Execute)

* 먼저 계획(혹은 체크리스트)을 만들고, 그 계획대로 실행
* 복잡한 업무(문서 분석, 정책 적용)에서 누락이 줄어듦
* 비용이 늘 수 있어 중요한 작업에 선택 적용

### 5.5 Draft → Critique → Final(자기검토)

* 초안 작성 → 기준에 따라 비판/수정 → 최종 출력
* 품질은 올라가지만 호출 수가 늘어 비용/지연이 증가

### 5.6 Citation-first(근거 우선)

* 먼저 근거 문장/출처를 선택하게 하고, 그 근거로 답을 쓰게 함
* RAG와 결합하면 환각 방지에 매우 강력

## 6) 실패 유형별 디버깅(가장 실용적인 파트)

프롬프트 디버깅은 “한 줄 수정”이 아니라 **원인 분해**가 핵심입니다.

### 6.1 환각이 많다

* 원인: 근거 부족, temperature 과다, “모르면 모른다” 정책 부재
* 처방:

  1. 근거 제공(RAG) 또는 툴 조회
  2. “근거 없으면 모른다/추측 금지” 규칙
  3. 인용 형식 강제
  4. temperature 낮추기

### 6.2 형식이 깨진다(JSON 파싱 실패 등)

* 원인: 자연어가 섞임, 필드 누락, 지시 충돌
* 처방:

  1. 출력 형식 섹션을 맨 아래에 명확히
  2. 불필요한 장식/설명 금지
  3. 7장 구조화 출력(JSON Schema)로 전환
  4. 검증 실패 시 자동 재시도(repair loop)

### 6.3 답이 장황하다

* 원인: 목표 불명확, 길이 제약 부재, 사용자 수준 미지정
* 처방:

  1. 길이 제한(불릿 5개 이하 등)
  2. “먼저 결론, 다음 근거” 구조 강제
  3. max tokens/stop 조건 설정

### 6.4 지시를 무시한다(탈선)

* 원인: 지시가 약하거나 서로 충돌, 입력이 잡음으로 가득
* 처방:

  1. 우선순위 명시(“다음 규칙이 최상위”)
  2. 입력 정리(필요한 컨텍스트만)
  3. 작업 단계를 분리(요약→판단→작성)

### 6.5 정책/보안 위반 위험

* 원인: 권한 없는 문서 인용, 민감정보 노출, 인젝션
* 처방:

  1. 시스템 레벨 정책(가드레일) + 프롬프트 정책(금지)
  2. 권한 필터/ACL 기반 RAG
  3. PII 마스킹, 툴 allowlist

## 7) “프롬프트를 코드처럼” 운영하는 방법(제품화 핵심)

### 7.1 템플릿화(Template)

프롬프트는 문자열이 아니라 **파라미터가 있는 템플릿**이어야 합니다.

* 입력: 사용자 질문, 문서 근거, 정책, 출력 스키마 등
* 장점: 재사용/테스트/버전관리 가능

**솔루션**

* **LangChain Prompt Templates**: 변수/부분 프롬프트 조합으로 템플릿 구성
* **Jinja2**: 일반 템플릿 엔진으로도 충분히 구현 가능

### 7.2 버전관리(Versioning)와 변경관리

* 프롬프트 변경은 곧 제품 변경입니다.
* 변경 시 “어떤 케이스에서 좋아지고/나빠졌는지”가 남아야 합니다.

**실무 패턴**

* 프롬프트에 버전 태그 부여
* 변경마다 골든셋 평가(회귀테스트)
* 운영 중 모니터링 지표 변화 추적

### 7.3 프롬프트 테스트(Regression Testing)

**“어제 잘 되던 게 오늘 안 된다”**를 막는 장치입니다.

**솔루션**

* **promptfoo**: 프롬프트/모델/파라미터 조합을 비교하고 테스트 자동화
* (LLM 관측) **Langfuse / LangSmith**: 프롬프트 버전과 실행 로그를 묶어 추적

---

## 8) 프롬프트와 모델 파라미터의 역할 분담(중요한 실무 감각)

* 프롬프트: **무엇을 해야 하는지(명세/제약/형식)**를 고정
* 파라미터(temperature/top-p): **얼마나 다양하게/보수적으로 생성할지**를 조정
* 구조화 출력/검증: **실패를 시스템적으로 줄이는 장치**

즉, “프롬프트로 모든 걸 해결”하려고 하지 말고:

* 형식 문제 → 스키마(7장)
* 최신/사내 지식 → RAG(9~10장)
* 사실/계산 → 툴 호출(8장)
* 품질 유지 → 평가/관측(22~23장)
  로 역할을 나누면 성공 확률이 크게 올라갑니다.

---

## 9) 관련 기술·솔루션(각 1~2줄, 실무 연결)

* **LangChain**: 프롬프트 템플릿/체인/툴 연동으로 LLM 앱 조립을 지원.
* **LlamaIndex**: 데이터 연결(RAG) 중심이지만 프롬프트 구성/라우팅과 결합하기 좋음.
* **promptfoo**: 프롬프트 회귀 테스트, 모델 비교, 실험 자동화에 적합.
* **DSPy**: 프롬프트를 데이터 기반으로 최적화하는 접근(정형 태스크에 유용).
* **Langfuse / LangSmith**: 프롬프트 버전+트레이싱+평가 루프를 운영에 연결.

## 10) 권장 실습(이 장의 산출물은 ‘프롬프트 스타일 가이드’)

### 실습 A: 프롬프트 스타일 가이드 만들기(팀 표준)

* 역할/목표/제약/형식/검증의 템플릿을 만들고
* 좋은 예/나쁜 예를 3개씩 작성
* “금지 규칙/우선순위/길이 정책”을 문서화

### 실습 B: 실패 유형별 디버깅 챌린지

* 일부러 실패하는 프롬프트를 제공(환각/형식 깨짐/장황/탈선)
* 원인 분해 후 수정안 제시
* 수정 전/후를 promptfoo로 비교 테스트

### 실습 C: 파라미터 프리셋 만들기

* 업무 유형별 기본 프리셋(Q&A/요약/아이디어/추출/리포트)을 정의
* temperature/top-p/max tokens/stop 규칙을 표준화

## 11) 이 장의 결론(다음 장과 연결)

* 프롬프트는 “대화 스킬”이 아니라 **명세/제약/검증이 있는 엔지니어링 산출물**입니다.
* 제품형 LLM에서는 “프롬프트만”으로는 한계가 빨리 오므로,

  * 7장 **구조화 출력**으로 형식 신뢰성을 확보하고
  * 8장 **툴 호출**로 사실/업무 실행을 붙이며
  * 9~10장 **RAG**로 근거/최신성을 보강하는 흐름으로 확장합니다.
