
## 22장. AI 품질 평가·테스트·회귀(LLM Eval / RAG Eval / Agent Eval): “좋아 보이는 데모”를 “안정적인 제품”으로 바꾸는 체계

### 1) 개요: AI 제품의 품질은 “한 번 잘 됨”이 아니라 **항상 잘 됨**이다

AI 시스템은 프롬프트/모델/데이터/RAG 인덱스/도구/정책이 조금만 바뀌어도 결과가 흔들립니다. 그래서 제품 단계에서는 개발 방식이 바뀝니다.

* 기능 개발(Feature)만큼 **평가(Eval)와 회귀(Regression)** 가 중요
* “정확도”만이 아니라 **근거성(groundedness), 안전성, 도구 호출 정확성, 비용/지연**까지 함께 봐야 함
* 오프라인 평가(골든셋) + 온라인 모니터링(실사용 지표) + 레드팀(악성 입력) 3종 세트를 돌려야 운영이 됩니다

---

### 2) 학습 목표

1. AI 평가를 **오프라인/온라인/레드팀**으로 나누고 각각의 목적을 설명
2. LLM/RAG/Agent의 품질을 **측정 가능한 지표**로 정의
3. 골든셋(Dataset)과 루브릭(Rubric)을 만들고 회귀 테스트 파이프라인을 구성
4. 자동 평가(메트릭/LLM-as-judge)와 인간 평가(HITL)의 역할 분담
5. 대표 솔루션(OpenAI Evals/Evals API, promptfoo, RAGAS, Phoenix 등)을 어디에 쓰는지 판단

---

## 3) 핵심 개념: 평가를 5층으로 쪼개면 설계가 쉬워진다

### (1) 정답성(Accuracy / Task Success)

* 사용자 의도에 맞게 답했는가(업무 성공률)

### (2) 근거성(Groundedness / Faithfulness)

* **RAG 근거 안에서만** 답했는가, 인용/출처가 맞는가

### (3) 형식/계약(Structured Output Validity)

* JSON Schema/필수 필드/타입/enum 준수(7장 연계)

### (4) 도구/행동 정확성(Tool-use Correctness)

* 적절한 툴을 선택했는가, 파라미터가 맞는가, 실행 결과를 올바르게 반영했는가(8·11장 연계)

### (5) 안전/정책(Safety / Compliance)

* PII 유출, 금지 콘텐츠, 정책 위반, 프롬프트 인젝션 내성(18장 연계)

> 제품 평가의 본질은 “모델 점수”가 아니라 **실패를 유형별로 분해하고 줄이는 루프**입니다.

---

## 4) 평가 체계의 표준 구조: 오프라인 + 온라인 + 레드팀

### 4.1 오프라인 평가(Offline Evals) = 개발/릴리즈의 기준선

* 골든셋(질문/정답/근거/기대 행동)을 고정해 놓고
* 모델/프롬프트/인덱스 변경 시마다 자동 실행
* 결과가 떨어지면 배포를 막거나(게이트), 원인 분석 후 수정

**OpenAI의 오픈소스 Evals**는 LLM 또는 LLM 기반 시스템 평가 프레임워크와 eval 레지스트리를 제공한다고 설명합니다. ([GitHub][1])
또한 OpenAI는 API 문서에서 “eval을 정의하고 실행한 뒤 결과를 분석하며 반복 개선”하는 흐름을 안내합니다. ([OpenAI 플랫폼][2])

### 4.2 온라인 평가(Online Monitoring) = 실제 사용자 품질 감시

* 오프라인에서 좋다고 실서비스에서 좋다는 보장은 없습니다.
* 온라인에서는 다음이 핵심:

  * 실패율(파싱 실패/툴 실패/빈 검색)
  * 사용자 피드백(👍/👎, 재질문률)
  * 비용/지연(P95, 토큰, 툴 호출 횟수)
  * 안전 이벤트(PII 탐지, 정책 차단)

### 4.3 레드팀/공격 테스트(Red Teaming) = “악성 입력”에 대한 내성

* 프롬프트 인젝션, 데이터 유출 유도, 도구 오남용 유도, 비즈니스 룰 위반 유도 등을 체계적으로 테스트
* promptfoo는 “LLM evals & red teaming”을 표방하며 인젝션/PII 유출/도구 오용 등 다양한 테스트 범주를 제공한다고 안내합니다. ([GitHub][3])

---

## 5) 골든셋 설계: “정답 텍스트”보다 “근거·기대 행동”이 중요

### 5.1 골든셋의 최소 구성(권장)

* 질문(현업에서 실제 나오는 형태)
* 컨텍스트(해당 케이스의 RAG 문서/툴 결과가 필요하면 함께 고정)
* 기대 결과:

  * **정답 또는 허용 가능한 답 범위**
  * **근거(문서 ID/섹션/문단)** 또는 “근거 없으면 모른다”
  * (에이전트면) 어떤 툴을 호출해야 하는지, 또는 호출하면 안 되는지

### 5.2 질문군을 유형별로 나눠야 성능이 오른다

* FAQ형(짧고 확정)
* 규정/정책형(근거 필수)
* 계산/변환형(툴 권장)
* 요약/리포트형(형식/길이 계약 중요)
* 위험/민감형(안전 규칙 중요)
* 멀티모달형(문서/이미지/오디오 입력 포함)

## 6) RAG 평가: “검색이 문제인지, 생성이 문제인지”를 분리하라

RAG의 실패는 크게 3종입니다.

1. 정답 근거가 Top-K에 없음(Recall 문제)
2. 근거는 있는데 아래쪽에 있음(Ranking 문제)
3. 근거가 있는데 답이 근거와 다름(Generation/grounding 문제)

**RAGAS**는 RAG 및 에이전트 워크플로우에 대한 평가 메트릭 세트를 제공한다고 문서에서 설명합니다. ([docs.ragas.io][4])
또한 RAGAS는 “RAG 파이프라인의 reference-free 평가” 프레임워크로 논문에서 소개됩니다. ([arXiv][5])

**실무 지표(권장)**

* Retrieval: Recall@K, MRR/NDCG, 중복률(다양성)
* Context: 관련성, 잡음률(불필요한 문장 비율)
* Generation: groundedness/faithfulness, 인용 누락률, “근거 밖 주장” 비율

---

## 7) 에이전트/툴 평가: “답변”이 아니라 “행동”을 테스트해야 한다

### 7.1 에이전트 평가 항목

* Tool selection: 어떤 툴을 골랐는가(올바른가/불필요한가)
* Arguments validity: 파라미터가 스키마/범위/권한에 맞는가
* Execution success: 호출 성공률, 재시도 횟수, 타임아웃률
* Post-processing: 툴 결과를 답에 정확히 반영했는가
* Safety: 금지 액션을 실행하려 하지 않는가(18장 연계)

### 7.2 실무 팁: “상태(state) 로그”가 평가 데이터가 된다

11장처럼 단계별 상태를 구조화로 저장하면,

* 어디서 실패했는지 자동 분류가 가능하고
* 회귀 테스트도 “단계별”로 쪼개서 할 수 있습니다.

---

## 8) 자동 평가 vs 인간 평가: 역할 분담이 답이다

### 8.1 자동 평가가 강한 영역

* 스키마 준수(JSON 파싱/필드 누락)
* 금칙어/PII 탐지(정규식+모델)
* RAG 인용 존재 여부, 근거 매칭(규칙/메트릭)
* 툴 호출 성공/실패 같은 시스템 지표

### 8.2 인간 평가가 필요한 영역

* “업무적으로 유용한가” 같은 품질(문장/설득/전문성)
* 애매한 질문에 대한 적절한 추가 질문 능력
* 미묘한 정책/윤리 판단(오탐/미탐 비용이 큰 영역)

### 8.3 LLM-as-judge(보조 심사자) 사용 원칙

* 루브릭을 명확히(예: 정확성>근거성>간결성)
* 동일 루브릭으로 반복 가능하게
* 중요한 릴리즈는 샘플링 인간 검수로 캘리브레이션

## 9) 운영/관측 기반 평가: “이상 징후”를 자동으로 잡아내기

Phoenix는 “오픈소스 LLM 트레이싱 & 평가 플랫폼”을 표방합니다. ([Phoenix][6])
또한 Arize는 OpenTelemetry 기반의 LLM 관측을 강조합니다. ([Arize AI][7])

**운영에서 바로 쓰는 경보 예시**

* 파싱 실패율이 1%→5%로 급증(스키마/프롬프트 변경 문제)
* RAG 인용 누락률 급증(프롬프트/컨텍스트 주입 문제)
* 특정 팀 문서에서만 오답률 증가(인덱스/ACL/문서 개정 문제)
* 툴 호출 횟수 폭주(에이전트 루프/인젝션 가능성)
* P95 지연 상승(서빙/배치/검색 병목)

## 10) 관련 기술·솔루션(실무에서 자주 쓰는 조합)

* **OpenAI Evals(오픈소스)**: 커스텀 eval 작성/실행을 위한 프레임워크와 레지스트리 제공. ([GitHub][1])
* **OpenAI Evals API 가이드**: eval 정의→실행→분석의 개발 루프를 문서로 안내. ([OpenAI 플랫폼][2])
* **promptfoo**: 로컬/CI 친화적 테스트와 레드팀(인젝션/PII/도구 오용 등) 범주를 제공. ([GitHub][3])
* **RAGAS**: RAG/에이전트 평가 메트릭을 제공하는 프레임워크 및 문서. ([docs.ragas.io][4])
* **Phoenix(Arize)**: 트레이싱·평가·디버깅을 위한 오픈소스 플랫폼, OpenTelemetry 기반 관측을 강조. ([Phoenix][6])

## 11) 권장 실습(현업형): “릴리즈 게이트” 만들기

### 실습 A: 오프라인 회귀 테스트 게이트

1. 질문 100개 골든셋 구성(질문군 5종으로 분류)
2. 각 케이스에:

   * 정답/허용 답 범위
   * 근거(문서/섹션)
   * 스키마(JSON) 기대 형태
3. promptfoo 또는 OpenAI Evals로 CI에서 자동 실행
4. 기준 미달 시 배포 차단(예: 인용 누락률 > 3%면 실패)

### 실습 B: RAG 평가 분해 리포트

* Recall@K(검색) vs groundedness(생성) 지표를 분리해
* “검색 개선이 필요한지 / 프롬프트·압축이 필요한지” 자동으로 결론이 나오게 설계

### 실습 C: 레드팀 최소 세트

* 인젝션(직/간접), PII 유출 유도, 금지 툴 호출 유도 케이스를 30개 만들고
* 차단률(=안전성)과 오탐률(=정상 요청을 막는 비율)을 함께 측정

## 12) 이 장의 결론(다음 장 연결)

* AI 품질은 “정답을 잘 맞추는 능력”만이 아니라 **근거·형식·행동·안전·운영**을 함께 만족해야 합니다.
* 오프라인(골든셋) + 온라인(관측) + 레드팀(공격) 3종 세트를 갖추면, 모델/프롬프트/데이터가 바뀌어도 품질을 유지할 수 있습니다.
* 다음 20장에서는 이 평가 체계를 기반으로, **데이터/지식베이스/피드백 루프(학습·튜닝·지식 업데이트)**를 어떻게 굴릴지(지속 개선 운영)로 자연스럽게 이어갈 수 있습니다.
