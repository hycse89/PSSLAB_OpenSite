 
## 7장. 구조화 출력(Structured Outputs)과 신뢰성: LLM을 “대화”에서 “업무 시스템”으로 바꾸는 핵심 기술

### 1) 개요: 왜 현업에서는 “좋은 글”보다 “파싱 가능한 결과”가 더 중요할까

현업에서 LLM 결과물은 대개 **다음 단계 자동화**로 이어집니다.

* Jira 티켓 생성, 테스트케이스 등록, 요구사항 문서화
* 고객 문의 분류/태깅, 리스크 체크, 정책 위반 탐지
* 폼/테이블/리포트 생성, DB 업데이트, 워크플로우 트리거

이때 자연어 답변은 보기엔 좋지만, **기계가 안정적으로 처리하기 어렵습니다.**
그래서 제품형 AI에서는 출력에 대해 다음을 요구합니다.

1. **형식이 항상 일정**해야 하고
2. **필수 필드가 누락되지 않아야** 하며
3. 값의 타입/범위가 맞아야 하고
4. 실패하면 자동으로 복구(repair)할 수 있어야 합니다.

이를 가능하게 하는 것이 **구조화 출력(Structured Outputs)** 입니다. 핵심은:

> “LLM에게 JSON을 ‘잘 쓰게’ 부탁하지 말고, **스키마(JSON Schema)로 출력 계약을 강제**하라.”

---

### 2) 학습 목표

1. 구조화 출력이 필요한 이유(신뢰성/자동화/운영)를 설명
2. JSON Schema를 이용해 출력 계약(Contract)을 정의할 수 있음
3. “프롬프트 기반 JSON” vs “스키마 강제”의 차이를 이해
4. 검증/재시도/폴백을 포함한 **출력 신뢰성 파이프라인**을 설계
5. 구조화 출력이 RAG/툴 호출/에이전트와 결합될 때의 아키텍처를 설명

---

## 3) 핵심 개념: 출력 계약(Output Contract)

구조화 출력은 “형식만 예쁘게” 만드는 기술이 아니라 **계약 기반 인터페이스**입니다.

* 입력: 사용자 요청 + 컨텍스트(RAG 결과, 툴 결과 등)
* 출력: 계약된 스키마를 만족하는 JSON
* 후속: 검증 통과 시에만 DB/업무시스템 반영

즉, LLM을 **불안정한 텍스트 생성기**가 아니라, **타입이 있는 함수**처럼 다루게 해줍니다.

---

## 4) 핵심 원리: JSON Schema로 강제하면 무엇이 달라지나

### 4.1 “프롬프트로 JSON 써줘”의 한계

프롬프트만으로 JSON을 유도하면 흔히 발생하는 문제:

* 따옴표 누락, trailing comma, 주석 삽입 → 파싱 실패
* 필수 필드 누락/이름 오타
* 타입 불일치(숫자여야 하는데 문자열, 배열이어야 하는데 객체)
* 자연어 설명이 섞여서 JSON 밖 텍스트가 튀어나옴

모델이 아무리 좋아도 “가끔” 이런 일이 생기면 **운영 시스템은 멈춥니다.**

### 4.2 스키마 강제(Structured Outputs)의 효과

스키마 강제는 출력 공간을 제한합니다.

* 필수 필드가 빠지기 어려워짐
* 타입/enum/패턴 제약을 만족시키도록 생성
* 파싱 실패율이 급감 → 자동화 신뢰성 상승

> 한 마디로, LLM 출력의 “확률적 흔들림”을 **형식 레벨에서 흡수**합니다.

---

## 5) 설계 방법: 스키마를 어떻게 잡아야 실무에서 실패가 줄어드나

### 5.1 스키마 설계 원칙(실무 체크리스트)

1. **필수 필드 최소화**: 꼭 필요한 것만 required로 (너무 많으면 실패/빈값 증가)
2. **값의 선택지를 좁히기**: enum/const로 범위를 제한
3. **중첩을 과하게 하지 않기**: 지나친 depth는 오류/누락을 부름
4. **자연어는 별도 필드로 분리**: `notes`, `rationale` 같은 텍스트 필드를 따로 두기
5. **ID/날짜/이메일 등은 패턴으로 제한**: regex pattern 활용
6. **확장성 고려**: 추후 필드 추가 가능하게 `additionalProperties` 정책 결정

### 5.2 “업무 자동화”에 적합한 전형 스키마 패턴

* **분류/태깅**: `category(enum)`, `confidence(0~1)`, `reason`
* **요구사항 추출**: `requirements[]` 각 항목에 `id`, `priority`, `acceptance_criteria`
* **티켓 생성**: `title`, `description`, `severity(enum)`, `component(enum)`, `steps_to_reproduce[]`
* **검토/감사**: `risks[]`, `policy_violations[]`, `recommended_actions[]`

## 6) 신뢰성 파이프라인: “검증 + 복구”를 기본으로 깔기

구조화 출력은 스키마만 던진다고 끝나지 않습니다. **검증 실패 시 복구 루프**가 핵심입니다.

### 6.1 표준 파이프라인(권장)

1. **생성**: 모델이 스키마에 맞게 JSON 생성
2. **검증**: JSON Schema / 타입 검증(Pydantic 등)
3. 실패 시:

   * (A) 자동 재시도: “어느 필드가 왜 틀렸는지” 오류 메시지를 컨텍스트로 넣고 재생성
   * (B) 폴백: 더 보수적 모델/파라미터로 재시도
   * (C) 인간 검토(HITL): 고위험 영역이면 승인 절차로 넘김
4. 통과 시:

   * DB 반영/티켓 생성/후속 툴 실행

### 6.2 검증 전략(현업 팁)

* “모든 걸 스키마로”는 불가능합니다.
  → **형식/필수 필드/타입/enum**은 스키마로 강제하고,
  → 의미적 검증(예: 우선순위가 맞는지)은 **후처리 룰**로 체크합니다.
* 신뢰도(confidence) 필드를 넣고 낮으면 “추가 질문”으로 전환하는 것도 실무적입니다.

## 7) 구조화 출력과 다른 구성요소의 결합(아키텍처 패턴)

### 7.1 RAG + Structured Outputs

* RAG로 근거를 가져오고, 구조화 출력으로 “근거+결론”을 포맷 고정
* 예: `citations[]` 필드에 문서ID/구간을 담아 근거 추적 가능

### 7.2 Tool calling + Structured Outputs

* 모델이 DB/검색 툴을 호출한 결과를 받아, 최종 산출물을 JSON으로 정리
* “툴 결과는 사실”, “모델은 정리/조합” 역할 분담이 쉬워짐

### 7.3 에이전트/워크플로우 + Structured Outputs

* 각 단계 결과를 구조화해 **상태(state)**로 저장하면, 디버깅/재시작/분기 처리가 쉬워집니다.
* LangGraph 같은 그래프 워크플로우에서 특히 큰 효과

## 8) 기술(Techniques): 실무에서 자주 쓰는 고급 포인트

### 8.1 부분 스키마(Progressive structuring)

복잡한 결과를 한 번에 뽑지 말고:

1. 1차: 핵심 필드만 구조화
2. 2차: 상세 필드 확장
   으로 나누면 실패율이 줄어듭니다.

### 8.2 “자연어 설명”을 별도 필드로 격리

* JSON을 깨뜨리는 주범은 모델의 친절한 설명입니다.
* 설명은 `rationale` 같은 필드로 몰아넣고, 바깥 텍스트를 금지합니다.

### 8.3 스키마 버전 관리

스키마는 API 계약이므로 버전이 필요합니다.

* `schema_version` 필드 포함
* 구버전/신버전 파서 호환 전략 마련

### 8.4 데이터 정규화(Normalization)

* 문자열 트림, 날짜 포맷 통일(ISO8601), enum 매핑(동의어 처리)
* 모델이 만든 값을 후처리로 안정화하면 운영이 편해집니다.

---

## 9) 관련 기술·솔루션(실무 기준, 1~2줄 설명)

### 9.1 스키마/검증

* **JSON Schema**: 구조화 출력 계약을 정의하는 표준(필수/타입/enum/패턴).
* **Pydantic**: 파이썬에서 JSON을 타입으로 검증/파싱하고 오류를 구조적으로 반환.
* **jsonschema(파이썬 라이브러리)**: JSON Schema 검증 구현에 널리 사용.

### 9.2 구조화 출력 지원(플랫폼 기능)

* **OpenAI Structured Outputs**: JSON Schema에 맞춘 응답 생성을 지원해 파싱 실패를 줄임.
* **Azure OpenAI Structured outputs**: Azure OpenAI에서도 유사한 구조화 응답 기능 제공.

### 9.3 출력 검증/가드레일 프레임워크

* **Guardrails AI**: 출력 검증, 재시도, 정책 적용을 묶어주는 프레임워크 계열.
* **NeMo Guardrails**: 정책/대화 흐름/안전 제약을 구성하는 가드레일 프레임워크(조직 적용에 유용).

### 9.4 평가/테스트

* **promptfoo**: 스키마 준수율, 필드 누락률 같은 회귀 테스트를 자동화.
* **Langfuse/LangSmith**: 구조화 출력 결과를 트레이스로 남기고 실패 원인을 분석.

## 10) 권장 실습(이 장을 확실히 ‘제품 감각’으로)

### 실습 A: “티켓 생성기” 구조화 출력 만들기

* 입력: 장애 설명(자연어), 로그 일부, 사용자 환경
* 출력 스키마:

  * `title`, `severity(enum)`, `component(enum)`, `steps_to_reproduce[]`, `expected`, `actual`, `suggested_owner`
* 검증 실패 시 자동 재시도(오류 메시지 포함)

**평가 지표**

* 파싱 성공률, 필수 필드 누락률, enum 오분류율, 평균 재시도 횟수, 지연/비용

### 실습 B: RAG + citations 구조화

* 입력: 정책 질문 + 검색된 근거 문단
* 출력:

  * `answer`
  * `citations[]: {doc_id, section, quote}` (짧은 인용)
* 근거 없으면 `answer = "insufficient_evidence"` 같은 정책값을 반환

## 11) 이 장의 결론(다음 장과 연결)

* 구조화 출력은 LLM을 “글쓰기 도구”에서 **업무 자동화 엔진**으로 바꾸는 핵심 기술입니다.
* 스키마 강제 + 검증/복구 루프가 있어야 운영에서 멈추지 않습니다.
* 다음 8장에서는 이 구조화 출력을 바탕으로, 모델이 **외부 시스템(검색/DB/Jira 등)을 직접 호출**하도록 만드는 Tool/Function Calling으로 확장합니다.
