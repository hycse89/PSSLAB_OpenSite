
## 10장. RAG 고도화: Hybrid · Rerank · Query Routing으로 “정답률”을 끌어올리는 실전 기술

### 1) 개요: 기본 RAG가 ‘70점’이라면, 고도화는 70→90을 만드는 작업

9장에서 만든 기본 RAG는 대개 다음 한계에 부딪힙니다.

* 검색은 되는데 **정답 근거가 Top-K 상단에 안 뜸**(순위 문제)
* 전문 용어/에러코드/제품명처럼 **키워드 매칭이 중요한 질문**에서 약함
* 질문이 짧거나 애매하면 **잘못된 문서로 끌려감**
* 문서가 많아지면 비슷한 문서가 섞이고 **잡음이 증가**
* 정답 문서는 찾았는데 LLM이 **근거를 제대로 못 씀**(근거 선택/압축 문제)

10장은 이걸 해결하는 “현업 표준 업그레이드”를 다룹니다.
핵심 메시지는 하나입니다.

> RAG 고도화의 대부분은 “더 좋은 모델”이 아니라
> **검색 전략(하이브리드/재정렬/라우팅/압축)과 평가 루프**로 해결된다.

---

### 2) 학습 목표

1. RAG 성능을 **Recall 문제 vs Ranking 문제 vs Context 문제**로 분해
2. 하이브리드 검색(BM25+Vector)을 설계하고 적용할 수 있음
3. Reranking으로 Top-K 품질을 올리는 방법(후보→재정렬)을 이해
4. Query rewriting/expansion, Query routing(컬렉션 라우팅)을 적용
5. 중복 제거/컨텍스트 압축/근거 우선 생성으로 환각을 줄이는 방법을 설계
6. 고도화 전/후를 평가 지표로 비교해 개선을 증명

---

## 3) 고도화의 진단 프레임: “어디서 깨지는지” 먼저 분해하라

RAG 성능 이슈는 보통 아래 3층 중 하나(혹은 복합)입니다.

### 3.1 Recall 문제(정답 문서를 못 찾음)

* Top-K에 정답 근거가 아예 없음
  → 임베딩/청킹/메타데이터/하이브리드가 필요

### 3.2 Ranking 문제(정답은 있는데 아래에 있음)

* Top-20 안에는 있지만 Top-5에는 없음
  → rerank가 정답률을 크게 올릴 수 있는 전형적 신호

### 3.3 Context/Generation 문제(근거는 있는데 활용을 못함)

* 근거가 여러 개로 분산되거나 잡음이 많아 모델이 헷갈림
  → 컨텍스트 압축/근거 우선/중복 제거/구조화 출력이 필요

---

## 4) 핵심 기술 1: 하이브리드 검색(Hybrid Search)

### 4.1 왜 하이브리드가 필요하나

벡터 검색은 의미를 잘 잡지만, 다음에서는 약해지기 쉽습니다.

* 에러코드, 로그 문자열, API 이름, 버전 번호, 제품명
* 약어/철자 변형이 많은 도메인
* “정확한 키워드가 정답”인 질문

이럴 때는 **BM25(키워드)**가 강합니다.

하이브리드는 다음을 결합합니다.

* **Sparse(키워드, BM25)**: 정확한 문자열 매칭에 강함
* **Dense(임베딩 벡터)**: 의미/문맥 유사도에 강함

### 4.2 결합 방식(실무에서 자주 쓰는 패턴)

* **Score fusion**: BM25 점수와 벡터 점수를 가중 합/정규화 후 합치기
* **Candidate union**: BM25 Top-K + Vector Top-K 후보를 합친 뒤 rerank
* **Field weighting**: 제목/헤딩/태그는 키워드 가중을 높게

### 4.3 운영 팁

* 도메인에 따라 가중치를 튜닝해야 함(코드/로그 많은 조직은 sparse 비중↑)
* 멀티언어(한/영 혼재)라면 토크나이징과 analyzer 설정도 성능에 크게 영향

---

## 5) 핵심 기술 2: Reranking(재정렬)

### 5.1 Rerank가 무엇인가

1차 검색은 “후보 회수(recall)”가 목표라 빠르게 많이 가져옵니다.
그 다음, 더 무겁지만 정확한 모델로 **후보를 정밀하게 재정렬**합니다.

* 1차: 벡터DB/BM25로 Top-50 후보
* 2차: reranker로 Top-5로 정렬
* 3차: 상위 근거만 LLM에 전달

### 5.2 왜 효과가 큰가

RAG에서 “정답률이 안 나오는” 원인의 상당 부분이 **순위 문제**입니다.
rerank는 이 병목을 정면으로 해결합니다.

### 5.3 Reranker 유형

* **Cross-encoder reranker**: 질문-문서를 함께 넣고 관련도를 직접 평가(정확하지만 비용↑)
* **LLM rerank / LLM-as-judge**: LLM로 관련성/근거성을 평가(유연하지만 편향/비용 고려)
* **도메인 특화 reranker**: 특정 분야(코드/법률 등)에 맞춘 모델이 더 강함

### 5.4 실무 팁

* rerank는 Top-K 후보 수가 핵심: 너무 적으면 효과가 없고, 너무 많으면 비용↑
* “정답 근거가 Top-20에는 들어오는데 최종 답이 틀리다”면 rerank가 1순위 후보

---

## 6) 핵심 기술 3: Query rewriting / expansion(질문 개선)

### 6.1 왜 필요한가

사용자 질문은 종종:

* 너무 짧고
* 맥락이 없고
* 조직 내부 용어를 섞고
* 철자/약어가 흔들립니다.

이 상태로 검색하면 “좋은 답”이 나오기 어렵습니다.

### 6.2 대표 기법

* **Query rewriting**: 질문을 더 명확하고 검색 친화적으로 재작성
* **Query expansion**: 동의어/약어/관련 키워드를 추가(제품명, 약어 사전 활용)
* **Multi-query retrieval**: 질문을 여러 버전으로 생성해 각각 검색 후 합치기

### 6.3 주의점

* 재작성 과정이 질문의 의미를 바꾸면 위험(특히 정책/법무)
* 원질문을 보존하고, rewriting은 “검색용”으로만 사용하며 로그로 남기는 게 좋음

---

## 7) 핵심 기술 4: Query Routing(컬렉션/인덱스 라우팅)

### 7.1 필요성

문서가 커지면 한 인덱스에 다 넣는 것보다,

* 정책 문서
* 기술 문서
* 운영 매뉴얼
* 티켓/장애 기록
  같이 “컬렉션”을 나눠야 품질과 속도가 좋아집니다.

### 7.2 Routing 방식

* **규칙 기반**: 키워드/태그/부서로 라우팅(가장 안정적)
* **분류기 기반**: 질문을 분류 모델/LLM로 카테고리 분류 후 라우팅
* **학습 기반**: 라우터 모델이 여러 인덱스의 힌트를 보고 선택(고급)

### 7.3 실무 팁

* 초반에는 규칙 기반이 운영이 쉽고, 점차 분류기/LLM 라우팅으로 확장
* 라우팅은 “틀려도 복구”가 중요 → 1차 실패 시 전체 인덱스로 폴백 검색

---

## 8) 컨텍스트 품질 기술: 중복 제거·압축·근거 우선

검색이 잘 돼도 컨텍스트가 나쁘면 LLM이 망합니다.

### 8.1 중복 제거(Deduplication)

* 비슷한 문단/중복 청크가 상위로 몰리면 다양성이 떨어지고 정보가 편향
* near-duplicate 제거(해시/유사도 기반)

### 8.2 컨텍스트 압축(Context Compression)

* Top-K 청크를 그대로 넣지 말고, 필요한 문장만 추려서 압축
* 예: 문단 전체 대신 “질문과 직접 관련 문장 2~4개”만 포함
* 비용/정확도 모두 개선되는 경우가 많음

### 8.3 근거 우선 생성(Citation-first)

* 먼저 근거 리스트를 고르고, 그 근거만으로 답을 작성하게 하면 환각이 줄어듭니다.
* 7장의 구조화 출력과 결합하면 “답+근거”를 강제 가능

---

## 9) 평가/실험 설계: 고도화는 “전/후 개선을 증명”해야 한다

고도화는 조합이 많아 감으로 하면 끝이 없습니다.

### 9.1 최소 지표 세트(권장)

* Retrieval: Recall@K, MRR/NDCG, 정답근거 Top-1 비율
* Generation: groundedness(근거 일치), citation coverage(인용 누락률), 정답률
* Ops: 지연, 비용, 실패율(검색 실패/파싱 실패)

### 9.2 A/B 비교

* 기본 RAG vs (하이브리드) vs (rerank) vs (rewriting) 조합을 단계적으로 비교
* “어떤 질문군에서 좋아졌나/나빠졌나”를 유형별로 분석

---

## 10) 관련 기술·솔루션(실무 대표, 1~2줄 설명)

### 10.1 하이브리드 검색/벡터DB

* **Weaviate**: BM25+Vector 하이브리드와 스키마 기반 구성이 편함.
* **Pinecone**: 관리형 벡터DB로 하이브리드/필터/스케일 운영이 강점.
* **Elasticsearch/OpenSearch**: 키워드 강점 + 벡터 결합으로 하이브리드 구현에 유리.

### 10.2 Rerank

* **Cohere Rerank**: 상용 rerank API로 적용이 쉽고 정밀도 개선 효과가 큰 편.
* **bge-reranker**: 오픈소스 reranker로 자체 호스팅/비용 최적화 가능.
* **ColBERT 계열**: late interaction으로 정밀도를 높이는 접근(대규모 검색에서 연구/적용 사례).

### 10.3 Query rewriting / routing 구현

* **LangChain / LlamaIndex**: 멀티쿼리, 라우팅, 압축 등 RAG 고도화 컴포넌트를 조립하기 좋음.
* **LangGraph**: “라우팅→검색→재검색→압축→생성” 같은 흐름을 상태 기반으로 안정화.

## 11) 권장 실습(현업형): 고도화 3단계 실험

### 실습 A: “기본 RAG” 기준선 만들기

* 골든셋 50문항에서 Recall@5, 정답률, 인용 누락률 측정

### 실습 B: 하이브리드 적용

* 코드/에러코드/제품명 질문군에서 성능 변화 분석(특히 Recall@5)

### 실습 C: rerank + 압축 적용

* Top-50 후보 → rerank Top-5 → 컨텍스트 압축 후 답변
* 정답근거 Top-1 비율과 groundedness가 얼마나 오르는지 측정

산출물: “질문 유형별 개선 지도(heatmap 느낌의 표)” + 비용/지연 트레이드오프 보고서

## 12) 이 장의 결론(다음 장과 연결)

* RAG 고도화는 결국 **검색 전략(하이브리드/재정렬/라우팅) + 컨텍스트 품질(압축/중복제거) + 평가 루프**입니다.
* 모델을 바꾸기 전에, 이 레이어를 다듬는 것이 비용 대비 효과가 훨씬 큽니다.
* 다음 11장에서는 이렇게 복잡해진 RAG/툴/검증 과정을 **워크플로우/에이전트**로 설계해, 실패 복구와 운영 통제를 갖춘 “제품형 자동화”로 완성합니다.
