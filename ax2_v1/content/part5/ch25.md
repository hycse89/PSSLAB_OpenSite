
## 25장. 드리프트·모니터링·재학습 자동화: “모델이 망가지는 순간”을 잡고 다시 살리는 운영 시스템

### 1) 개요: 모델은 시간이 지나면 ‘반드시’ 틀어진다

AI를 운영하면 언젠가 이런 일이 생깁니다.

* 어제까지 잘 맞던 예측이 갑자기 빗나감
* RAG 답변이 최신 정책을 반영 못함
* 추천이 클릭은 오르는데 구매/리텐션이 떨어짐
* 비전 모델이 조명/카메라 변경 후 오탐 폭발
* 음성 인식이 특정 지점(잡음/마이크)에서 급락

이건 “모델이 나빠서”가 아니라 **환경이 바뀌기 때문**입니다.
그래서 운영에서 중요한 건 “최고 성능”보다:

> **언제, 왜 망가졌는지 빨리 알아차리고**
> **어떤 조치를 자동으로 할지(또는 사람이 할지) 체계화**하는 것

---

### 2) 학습 목표

1. 데이터 드리프트/컨셉 드리프트/라벨 드리프트를 구분
2. 온라인 모니터링 지표(품질/데이터/운영)를 설계하고 경보 기준을 정함
3. “드리프트 감지 → 원인 분해 → 완화(폴백/제한) → 재학습/재인덱싱” 자동화 흐름 설계
4. 비 LLM(예측/추천/비전)과 LLM(RAG/툴/에이전트)의 모니터링 차이를 이해
5. 재학습을 ‘자동’으로 하되, 안전/검증/승인 게이트를 포함

---

## 3) 핵심 개념: 드리프트 3종(그리고 많은 조직이 1종만 본다)

### 3.1 데이터 드리프트(Data drift)

* 입력 분포가 바뀜
  예: 트래픽 패턴 변화, 센서 교체, 카메라 각도 변경, 사용자층 변화

**징후**

* 입력 통계(평균/분산/범주 비율)가 달라짐
* 임베딩 분포가 달라짐(텍스트/이미지)

### 3.2 컨셉 드리프트(Concept drift)

* “입력→정답” 관계가 바뀜
  예: 사기 패턴이 진화, 추천에서 취향 트렌드 변화, 정책 변경으로 라벨 기준 변경

**징후**

* 입력 분포는 비슷한데 성능이 떨어짐(정답률/리콜 하락)

### 3.3 라벨 드리프트(Label drift)

* 라벨링 기준/검수자/정책이 바뀜
  예: 불량 기준이 강화됨, 콜센터 분류 정의가 바뀜

**징후**

* 동일 데이터라도 라벨 분포가 바뀜
* 휴먼 리뷰에서 “예전엔 정답이던 게 이제 오답”이 됨

---

## 4) 모니터링을 3층으로: 운영/데이터/품질

### 4.1 운영(Ops) 지표

* P95/P99 지연, 실패율, 타임아웃, 비용, GPU 사용률
* 툴 호출 성공률/재시도 횟수
* RAG 검색 지연/벡터DB 오류

### 4.2 데이터(Data) 지표

* 수치형: 평균/분산/분포(PSI, KS-test)
* 범주형: 카테고리 비율 변화(chi-square)
* 텍스트/이미지: 임베딩 분포 변화(코사인/클러스터 분포)

### 4.3 품질(Quality) 지표

* 예측/추천: MAE, AUC, CTR/구매 전환 등
* 비전: 오탐/미탐(샘플링 라벨), mAP 변화
* LLM/RAG: 인용 누락률, groundedness, 파싱 실패율
* 안전: PII 누출률(0 목표), 정책 차단률/오탐률

> 실무 핵심: “품질 라벨이 늦게 들어오는 영역”은 **프록시 지표**가 필요합니다.
> 예: 추천은 구매 라벨이 늦음 → 초기에는 CTR/체류시간 + 샘플링 리뷰

---

## 5) LLM/RAG/Agent의 드리프트는 ‘데이터’보다 ‘지식/정책/프롬프트’가 많다

### 5.1 RAG 드리프트

* 문서가 바뀌었는데 인덱스가 갱신되지 않음
* 권한/ACL 변경이 반영 안 됨
* 리랭크/라우팅 변경으로 Recall@K 하락

**모니터링 포인트**

* Recall@K(골든셋/리플레이), 인용 누락률, 문서 버전 불일치율
* “근거 없는 답” 비율

### 5.2 프롬프트 드리프트

* 프롬프트 템플릿 변경으로 톤/형식/근거 사용이 변함
* 스키마 변경으로 파싱 실패 증가

**모니터링 포인트**

* 파싱 실패율, 필드 누락률, 답변 길이 분포 변화

### 5.3 에이전트 드리프트

* 툴/API 변화로 실패율 증가
* 루프/재시도 폭주(비용 급증)

**모니터링 포인트**

* 툴 호출 횟수/턴, 실패 코드 분포, 서킷 브레이커 발동률

---

## 6) 드리프트 대응: “완화(즉시) → 수정(중기) → 개선(장기)” 3단 전략

### 6.1 즉시 완화(Mitigation)

* 임계값 조정(오탐 폭증 시)
* 폴백 모델/보수 모드(temperature↓, tool 제한)
* RAG: K 증가 + rerank 강화, 또는 “근거 부족” 응답으로 전환
* 위험 기능 일시 제한(고위험 툴 비활성화)

### 6.2 중기 수정(Remediation)

* 데이터 수집 확대(새 환경 샘플)
* 라벨링/룰 업데이트
* 인덱스 재구성(청킹/메타데이터/ACL 수정)
* 프롬프트/스키마 회귀 테스트 후 수정(19장)

### 6.3 장기 개선(Improvement)

* 자동 재학습 파이프라인 정착
* 드리프트에 강한 모델/피처 설계(정규화, 도메인 적응)
* 실험(AB)과 데이터 루프 자동화(20장)

---

## 7) 재학습 자동화: “자동”이라고 무조건 자동 배포는 아니다

재학습은 두 가지를 분리해야 합니다.

* **자동 학습(Automation)**: 주기적으로 학습/튜닝 수행
* **자동 배포(Autodeploy)**: 검증을 통과하면 자동으로 프로덕션 반영

고위험 시스템은 보통:

* 학습은 자동화하되
* 배포는 게이트(평가+승인)를 거쳐 단계 배포하는 게 안전합니다.

### 7.1 재학습 트리거(대표)

* 시간 기반: 매주/매월
* 이벤트 기반: 드리프트 감지, 성능 KPI 하락
* 데이터 기반: 새 데이터 N건 누적

### 7.2 필수 게이트(19장 연계)

* 오프라인 골든셋 성능 유지/개선
* 안전 테스트(PII/정책/인젝션) 통과
* 비용/지연 예산 통과
* 카나리/롤백 준비

---

## 8) 비전/음성/시계열/추천별 모니터링 체크리스트(요약)

### 8.1 Vision

* 입력 통계: 조명/노이즈/해상도, 카메라별 분포
* 품질: 오탐/미탐 샘플링 라벨, 클래스별 mAP 추세
* 운영: FPS/프레임 드랍/온도/전력(엣지)

### 8.2 Speech

* 환경별 WER(잡음/채널/마이크), 도메인 엔티티 오류율
* 스트리밍 지연(턴 지연), barge-in 성공률

### 8.3 시계열 예측/이상탐지

* 입력 분포(계절성 변화), 잔차 분포, 임계값 초과율
* 경보 오탐률(시간당), 탐지 지연

### 8.4 추천/랭킹

* CTR/전환/리텐션의 “장단기 분리”
* 다양성/신규성 지표(편향 감지)
* 탐색률(Explore)과 성능의 균형

## 9) 관련 기술·솔루션(모니터링/드리프트/재학습)

* **Evidently AI**: 데이터/모델 드리프트와 성능 모니터링 리포트/대시보드에 많이 사용.
* **WhyLabs**: 대규모 데이터/모델 모니터링을 제품화한 서비스 계열.
* **Arize / Phoenix(오픈소스)**: LLM 트레이싱/평가/관측(19장)과 연결.
* **OpenTelemetry + Prometheus/Grafana**: 지표·트레이스 표준(17~19장 연계).
* **Airflow / Prefect / Dagster**: 재학습/재인덱싱 워크플로우 오케스트레이션.
* **MLflow**: 실험/모델 레지스트리/배포 워크플로우 관리.
* **Great Expectations**: 데이터 품질 검증(스키마/범위/결측) 게이트로 활용.

## 10) 권장 실습(현업형): “드리프트 대응 런북 + 자동 파이프라인” 만들기

### 실습 A: 드리프트 경보 설계

1. 입력 분포 지표(PSI/KS) + 운영 지표(P95 지연) + 품질 프록시(재질문률/파싱 실패율) 선정
2. 경보 임계값과 알림 정책(쿨다운/우선순위) 정의
3. 경보 발생 시 자동으로 실행할 완화 조치 정의(폴백/제한)

### 실습 B: 재학습 파이프라인(게이트 포함)

* 데이터 수집→정제→학습→오프라인 eval→카나리 배포→모니터링→롤백
* “성능 악화 시 자동 롤백”까지 넣으면 운영 난이도가 확 내려갑니다.
