
## 20장. 배포·서빙·운영(MLOps/LLMOps): AI를 “데모”에서 “서비스”로 만드는 인퍼런스/관측/비용 통제

### 1) 개요: 제품화의 승부처는 ‘모델’이 아니라 **서빙 품질(지연·비용·안정성·감사)**

학습이 끝난 모델은 “완성”이 아니라 “시작”입니다. 실제 서비스에서는 아래가 더 중요합니다.

* **지연(latency)**: 첫 토큰/첫 음성까지의 시간, P95/P99
* **처리량(throughput)**: 동시 사용자 증가 시 TPS 유지
* **비용(cost)**: GPU 시간, 토큰, 캐시 효율, 배치 전략
* **안정성(reliability)**: 타임아웃/재시도/서킷브레이커/롤백
* **관측(observability)**: 어디서 느려졌는지, 왜 실패했는지 추적
* **안전/거버넌스**: 권한/PII/감사로그/정책 준수

이 장은 “LLM 포함 모든 AI”의 서빙을 **아키텍처/최적화 레버/운영 체계**로 정리합니다.

---

## 2) 핵심 개념: 서빙 품질을 4층으로 쪼개서 최적화하라

### (1) 모델 레벨

* 양자화(Quantization), 지연 최적화 커널, KV-cache, 디코딩 최적화(5장) 등

### (2) 런타임/서버 레벨

* 배치(inflight batching), 동시성, 스케줄러, 스트리밍, 메모리 관리

### (3) 플랫폼 레벨

* GPU/노드 오토스케일, 라우팅, 캐시, 큐(백프레셔), 장애 격리

### (4) 운영 레벨

* 트레이싱/로그/지표, 회귀 평가, 안전 필터, 롤백/버전관리

---

## 3) 핵심 원리: LLM 서빙의 병목은 대부분 **KV-cache + 배치 + 스케줄링**

LLM 서빙은 “한 번에 한 요청”이 아니라 **동시 요청을 어떻게 섞어 굴리느냐**가 성능을 좌우합니다.

* **KV cache**: 긴 컨텍스트/다중 요청에서 메모리 사용량이 폭증 → 메모리 관리가 곧 비용/처리량
* **Inflight batching**: 생성 중인 요청들을 묶어 GPU 효율을 올림
* **스케줄링**: 짧은 요청/긴 요청을 섞을 때 공정성(대기시간)과 처리량 균형

대표 엔진:

* **vLLM**: 고처리량·메모리 효율 LLM 서빙 엔진으로 소개(고성능 서빙 엔진 포지션). ([vLLM][1])
* **TensorRT-LLM**: NVIDIA GPU에서 LLM 추론 최적화를 위한 오픈소스 라이브러리(커스텀 커널, inflight batching, paged KV cache, 다양한 양자화 등 최적화 기능을 강조). ([GitHub][2])
* **Hugging Face TGI(Text Generation Inference)**: 오픈소스 LLM을 고성능으로 배포/서빙하기 위한 툴킷(스트리밍 등 기능 제공). ([Hugging Face][3])

## 4) 실무 아키텍처 5종(가장 자주 쓰는 형태)

### 4.1 단일 모델 API(초기 제품)

* API Gateway → Model Server → (옵션) 캐시/로그
* 장점: 단순, 빠른 출시
* 단점: RAG/툴/검증 붙이면 금방 복잡해짐

### 4.2 RAG 서비스(검색+생성)

* Query → Retrieval(벡터DB/하이브리드/리랭크) → Context 압축 → LLM → 답변(+인용)
* 병목: 검색 지연, 컨텍스트 길이, 인용/근거 검증(9~10장)

### 4.3 Tool-augmented 서비스(업무 실행)

* LLM → Tool 호출 → 결과 검증 → 구조화 출력(JSON) → 업무 반영(7~8장)
* 필수: allowlist/권한/감사로그/재시도

### 4.4 멀티모달 파이프라인(문서/비디오/음성)

* 전처리(OCR/ASR/프레임 샘플링) → 분석 모델 → 이벤트/구조화 → 저장/알림
* 병목: 디코딩/전처리, 스트리밍 지연(13~16장)

### 4.5 워크플로우/그래프(복잡 자동화)

* 상태 기반(step/state)로 분기/재시도/승인 포함(11장)
* 장점: 운영 안정성↑, 재현성↑

## 5) 성능 최적화 레버(현업에서 “바로 돈 되는” 것들)

### 5.1 배치/동시성

* **동적 배치(inflight batching)**로 GPU를 놀리지 않기
* 너무 큰 배치 → 지연 증가, 너무 작은 배치 → 비용 증가

### 5.2 컨텍스트/토큰 절감

* RAG 컨텍스트 압축, 중복 제거, Top-K 튜닝(10장)
* 시스템 프롬프트 길이 최소화, 출력 길이 제한, stop sequence

### 5.3 양자화/정밀도

* FP16/BF16 → INT8/INT4(AWQ 등)로 비용/지연 절감(정확도 트레이드오프 관리)
* TensorRT-LLM은 다양한 양자화 옵션을 최적화 기능으로 포함한다고 설명합니다. ([GitHub][2])

### 5.4 캐시

* **프롬프트 캐시**(자주 반복되는 시스템 프롬프트/FAQ)
* **RAG 캐시**(검색 결과/리랭크 결과)
* **결과 캐시**(동일 요청 재사용, 단 개인정보/권한 분리 필수)

### 5.5 스트리밍 UX

* “첫 토큰 시간(TTFT)”을 줄이면 체감이 크게 좋아짐
* TGI는 스트리밍 응답을 지원하는 예를 문서에서 안내합니다. ([Hugging Face][4])

---

## 6) 안정성/운영: 실패는 “반드시” 일어난다(그래서 설계가 중요)

### 6.1 표준 운영 가드레일

* 타임아웃, 재시도(지수 백오프), 레이트리밋
* 서킷 브레이커(연쇄 장애/비용 폭주 방지)
* 폴백(더 작은 모델/더 보수적 파라미터/“추가 질문” 전환)

### 6.2 릴리즈 전략

* 모델/프롬프트/스키마(7장)는 전부 버전 관리
* Canary / A-B 테스트 / 자동 롤백(품질 지표 악화 시)

### 6.3 관측(Observability) 체크리스트

* 요청별: 토큰 수, TTFT, P95/P99 지연, 실패 코드, 툴 호출 횟수
* RAG: Recall@K, 인용 누락률, 근거 일치율
* 비용: GPU 사용률, 배치 효율, 캐시 히트율

## 7) 관련 기술·솔루션(서빙/배포 관점 핵심만)

### LLM 인퍼런스 엔진

* **vLLM**: 고처리량/메모리 효율 LLM 서빙 엔진. ([vLLM][1])
* **TensorRT-LLM**: NVIDIA GPU LLM 추론 최적화 라이브러리(다양한 최적화 포함). ([GitHub][2])
* **Hugging Face TGI**: 오픈소스 LLM 서빙 툴킷(스트리밍 등). ([Hugging Face][3])

### “빠르게 배포” 계열(엔터프라이즈/운영 최적화)

* **NVIDIA NIM**: 다양한 환경(클라우드/데이터센터/엣지)에서 최신 모델을 빠르게 배포하도록 “사전 구축된 최적화 인퍼런스 마이크로서비스”를 표방. ([NVIDIA][5])

(그 외로는 Triton Inference Server, KServe, Ray Serve, BentoML, Seldon 같은 서빙/오케스트레이션 스택이 자주 함께 쓰이지만, 조직 환경에 따라 선택이 갈립니다.)

## 8) 권장 실습(17장 산출물은 “운영 가능한 서비스 스펙”)

### 실습 A: LLM 서빙 벤치마크(비용/지연 최적화)

* vLLM 또는 TGI로 동일 모델을 띄우고
* 동시 요청 수를 늘리며 TTFT/P95/처리량/비용을 측정
* 배치/최대 토큰/컨텍스트 압축/캐시 적용 전후 비교

### 실습 B: RAG 서비스 운영 대시보드

* 검색 품질(Recall@K, 근거 누락률) + 생성 품질(근거 일치율) + 비용(토큰/캐시 히트율) 통합
* “품질이 떨어진 원인이 검색인지 생성인지”를 즉시 구분 가능하게 설계
