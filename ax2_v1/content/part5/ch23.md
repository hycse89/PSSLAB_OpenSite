
## 23장. 지속 개선 루프: 데이터·지식베이스·피드백을 굴려 “품질이 계속 좋아지는” AI 운영 만들기

### 1) 개요: AI 제품의 경쟁력은 ‘처음 성능’이 아니라 **개선 속도**에서 나온다

모델을 한 번 잘 만들었다고 끝이 아닙니다. 실제 서비스에서는 다음이 계속 바뀝니다.

* 사용자 질문 패턴(새 용어/새 제품/새 정책)
* 사내 문서/정책 개정(RAG 지식이 낡아짐)
* 툴/API 변화(파라미터/권한/오류)
* 운영 환경 변화(트래픽, 지연, 비용)
* 안전/규정 요구사항 변화

그래서 “20장”의 핵심은:

> **피드백을 데이터로 만들고 → 우선순위를 정하고 → 자동 평가로 검증하며 → 배포까지 연결**하는 루프를 갖추는 것

이 루프가 있으면, LLM/비전/음성/문서 AI 무엇이든 “운영하면서 더 좋아지는 시스템”이 됩니다.

---

### 2) 학습 목표

1. 지속 개선을 **(관측→수집→라벨→학습/튜닝→평가→배포)** 루프로 설명
2. 실패를 유형별로 분해하고 “어디를 고쳐야 이득이 큰지” 우선순위를 세움
3. RAG 지식 업데이트(증분 인덱싱, 신뢰도, 버전관리)와 평가를 연결
4. 프롬프트/스키마/라우팅/리랭크/모델 교체 등 개선 수단의 선택 기준 이해
5. 사용자 피드백/휴먼리뷰를 안전하게 데이터화(PII 처리 포함)

---

## 3) 핵심 개념: 지속 개선은 3개의 루프가 동시에 돈다

### 3.1 품질 루프(Quality loop)

* 오답/환각/인용 누락/형식 깨짐 같은 품질 문제를 줄이는 루프

### 3.2 지식 루프(Knowledge loop)

* 문서/정책/FAQ/티켓이 바뀌는 것을 반영해 RAG 인덱스를 최신화하는 루프

### 3.3 효율 루프(Efficiency loop)

* 지연/비용(토큰, 검색, 툴 호출)을 줄이는 루프
  (성능이 좋아져도 비용 폭주하면 제품이 안 됩니다)

---

## 4) 루프의 표준 파이프라인(현업 ‘운영형’ 설계)

### 4.1 관측/수집(Observability → Data)

수집해야 하는 최소 데이터:

* 입력(사용자 질문)과 결과(응답)
* RAG: 검색된 문서 ID/섹션, 리랭크 점수, 컨텍스트 길이
* 툴: 어떤 툴을 어떤 인자로 호출했는지, 성공/실패 코드
* 구조화 출력: 파싱 성공/실패, 누락 필드
* 안전: PII 탐지/차단 이벤트, 정책 위반 시도
* 사용자 피드백: 👍/👎, 재질문률, “수정 요청” 내용

**중요**: 원문 로그를 그대로 쌓지 말고

* PII 마스킹
* 최소 보존
* 접근권한 통제(18장)
  가 기본입니다.

---

### 4.2 실패 분류(Triage): “원인별 버킷”이 있어야 개선이 된다

가장 실용적인 실패 버킷 예시:

1. **Retrieval 실패**: 정답 근거가 Top-K에 없음
2. **Ranking 실패**: 근거는 있는데 아래에 있음
3. **Grounding 실패**: 근거와 다른 답(환각)
4. **Formatting 실패**: JSON 파싱/스키마 불일치
5. **Tool 실패**: 잘못된 툴 선택/인자 오류/타임아웃
6. **Policy/Safety 실패**: PII/금지행동/인젝션
7. **UX 실패**: 장황/질문 되묻기 부족/톤 문제

이 버킷으로 분류하면 “고쳐야 할 레버”가 자동으로 결정됩니다.

* Retrieval/Ranking → 10장(하이브리드/리랭크/라우팅)
* Grounding → 9~10장 + 7장(근거 우선/구조화/검증)
* Formatting → 7장(스키마 강제/repair loop)
* Tool → 8장(시그니처/검증/allowlist)
* Safety → 18장(게이트/정책/ACL)
* UX → 6장(프롬프트 가이드) + 모델/템플릿 개선

---

### 4.3 라벨링/휴먼리뷰(HITL): “최소 비용으로 최대 효과”

모든 케이스를 사람이 다 볼 수 없으니, 전략이 필요합니다.

* **샘플링 검수**: 무작위 + 위험/저품질(낮은 신뢰도, 👎, 재질문) 가중 샘플링
* **액티브 러닝**: 모델이 헷갈리는 케이스를 우선 라벨링
* **라벨 스키마**: 정답/근거/실패 유형/개선 제안(짧게) 정도만 표준화해도 큰 효과

라벨링 산출물은 두 갈래로 씁니다.

1. **평가 데이터(골든셋 확장)**
2. **개선 데이터(프롬프트/룰/인덱스/튜닝)**

---

### 4.4 개선 레버 선택(무엇을 먼저 고치나)

현업에서 “효과 대비 비용”이 좋은 순서(일반론):

1. **프롬프트/템플릿/출력 스키마 개선**(6~7장)
2. **RAG 검색/리랭크/라우팅 개선**(10장)
3. **컨텍스트 압축/중복 제거**(10장)
4. **규칙/검증/후처리 강화**(7, 14, 18장)
5. **모델 교체**(더 비싸지거나 운영 복잡도↑)
6. **파인튜닝/지속 학습**(데이터/거버넌스 비용↑, 그러나 장기적으로 강력)

---

## 5) RAG 지식 업데이트 루프(문서가 바뀌는 현실 대응)

### 5.1 증분 인덱싱(Incremental indexing)

* 문서 해시/버전으로 변경 감지
* 변경된 chunk만 재파싱/재임베딩
* 오래된 버전은 “비활성화” 또는 최신 가중치 낮추기

### 5.2 신뢰도/권한/수명 관리

* 문서마다 신뢰 등급(정책/법무 > 개인 메모)
* ACL 메타데이터로 권한 필터 강제
* “만료일/리뷰 필요” 메타데이터로 낡은 지식 노출 억제

### 5.3 지식 품질 평가

* “새 문서가 들어오면” 골든셋에서 Recall@K가 좋아졌는지/나빠졌는지 체크
* 특정 문서가 오답을 유발하면 인덱스에서 격리(블랙리스트/검토 큐)

---

## 6) 피드백을 ‘학습 가능한 데이터’로 만드는 법

### 6.1 사용자 피드백의 구조화

* 👍/👎만으로는 부족 → 최소한 아래를 받으면 효과가 커짐

  * “왜 별로였나?” (근거 없음/틀림/장황/형식 오류/보안)
  * “기대 답” 한 줄(선택)
* 이걸 구조화하면 자동 분류와 우선순위가 쉬워집니다.

### 6.2 리플레이(Replay)로 회귀 자동화

* 운영 트래픽에서 뽑은 대표 요청을 “리플레이 세트”로 만들어
* 모델/프롬프트/인덱스 변경마다 동일 입력을 재실행 → 품질 변화를 자동 비교

---

## 7) 지속 개선을 “배포”까지 연결하는 운영 체계

### 7.1 버전 관리 대상(필수)

* 프롬프트 템플릿
* 스키마(JSON Schema)
* 라우팅 규칙/리랭크 가중치
* 인덱스 버전(문서 스냅샷)
* 정책(허용/금지)
* 모델 버전(자체/외부)

### 7.2 릴리즈 게이트(19장 연계)

* 오프라인 골든셋 통과 + 안전 테스트 통과 + 비용/지연 예산 통과
  → 통과 못 하면 롤백 또는 수정

### 7.3 자동 롤백/알림

* 인용 누락률 급증, 파싱 실패율 급증, 툴 실패율 급증
  → 자동 롤백 또는 기능 제한(서킷 브레이커)

---

## 8) 관련 기술·솔루션(지속 개선에 자주 쓰는 조합)

* **Langfuse / LangSmith / Phoenix**: 트레이싱·관측·리플레이 기반 평가에 유용(운영 데이터에서 개선 포인트 추출).
* **promptfoo / OpenAI Evals**: CI에서 회귀 테스트 게이트 구성.
* **RAGAS / DeepEval**: RAG groundedness/관련성 등 평가 메트릭 구성에 도움.
* **DVC / LakeFS(데이터 버전관리)**: 데이터/라벨/인덱스 스냅샷을 버전으로 관리할 때 유용.
* **Feature Store(Feast 등)**: 온라인/오프라인 피처 일관성을 관리(전통 ML과 결합 시).

---

## 9) 권장 실습(현업형): “개선 루프”를 실제로 돌려보기

### 실습 A: 실패 버킷 대시보드 + 개선 사이클 1회

1. 운영 로그(샘플)에서 실패 케이스 200개 추출
2. 자동 규칙 + LLM 분류로 7개 버킷에 분류
3. 상위 2개 버킷(예: Retrieval, Formatting)에 대해 개선 적용
4. 골든셋/리플레이 세트로 전후 비교(정답률, 인용 누락률, 파싱 실패율, 비용)

### 실습 B: 문서 업데이트가 성능에 미치는 영향 측정

* 정책 문서 개정 전/후 인덱스를 두 버전으로 유지
* 같은 질문 세트로 Recall@K/정답률 비교
* “문서 변경이 오답을 줄였는지, 새 오답을 만들었는지” 리포트

---

## 10) 이 장의 결론(다음 장 연결)

* 지속 개선의 핵심은 **관측 가능한 데이터 → 실패 분류 → 작은 개선 → 자동 평가 → 안전한 배포** 루프입니다.
* 모델만 바꾸는 조직보다, 이 루프를 갖춘 조직이 장기적으로 품질과 비용을 모두 이깁니다.
* 다음 21장에서는 이 운영 루프를 뒷받침하는 **데이터/모델/정책의 거버넌스(조직 체계, 책임, 표준, 문서화)**로 넘어가면 전체 커리큘럼이 “기업형 AI”로 완성됩니다.
