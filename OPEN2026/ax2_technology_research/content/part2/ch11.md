
## 11장. 에이전트와 워크플로우: “자동화”를 안전하고 재현 가능하게 만드는 설계법

### 1) 개요: 에이전트는 만능이 아니라 “복잡한 작업을 분해해 실행하는 운영 방식”이다

요즘 “AI 에이전트”는 과대포장되기 쉽습니다. 현업에서 중요한 건 이름이 아니라 **실제로 업무가 돌아가고, 실패해도 복구되며, 감사/보안/비용 통제가 가능한가**입니다.

* 단순 Q&A/RAG: 한 번 호출로 끝나도 됨
* 업무 자동화(티켓 생성, 정책 체크 후 실행, 다단계 조사, 보고서 작성):
  **여러 단계 + 조건 분기 + 반복 + 상태 저장 + 실패 복구**가 필요
  → 이때 “에이전트/워크플로우”가 필수입니다.

이 장의 핵심 메시지:

> **현업에서는 ‘자유로운 에이전트’보다 ‘통제 가능한 워크플로우’가 먼저다.**
> 그리고 필요한 곳에만 에이전트를 부분적으로 쓴다.

---

### 2) 학습 목표

1. 에이전트(Agent)와 워크플로우(Workflow)의 차이와 장단점을 설명
2. 계획-실행(Planner–Executor), ReAct 같은 대표 패턴을 이해
3. 상태(state) 기반 설계(입력/중간결과/결정/로그)를 할 수 있음
4. 실패 복구(재시도/폴백/서킷브레이커/인간 승인)를 포함한 운영 설계를 할 수 있음
5. LangGraph 같은 그래프 기반 오케스트레이션 도구를 어떤 상황에 쓰는지 판단

---

## 3) 핵심 개념: “한 번의 호출”을 넘어 “작업 수행 시스템”으로

에이전트/워크플로우가 필요한 이유는 작업이 다음 특성을 가질 때입니다.

* **다단계**: 조사 → 비교 → 결정 → 실행 → 기록
* **조건 분기**: 결과가 A면 추가 조사, B면 실행, C면 종료
* **반복 루프**: 정보가 부족하면 추가 질문/추가 검색
* **외부 시스템 연동**: 검색/DB/티켓/알림/승인
* **실패 가능성**: 네트워크 오류, 권한 실패, 빈 결과, 도구 예외
* **감사/추적 필요**: 왜 그렇게 했는지, 어떤 근거로 실행했는지 남겨야 함

---

## 4) Agent vs Workflow: 언제 무엇을 쓰나

### 4.1 워크플로우(통제형)

* 사람이 단계와 규칙을 **미리 정의**
* 장점: 예측 가능, 디버깅 쉬움, 보안/품질 통제 용이
* 단점: 유연성이 낮고, 새로운 케이스에 약할 수 있음

**추천 용도**

* 정책 기반 승인/처리, 티켓 자동화, 정형 업무, 반복 프로세스

### 4.2 에이전트(자율형)

* 모델이 상황에 따라 계획을 세우고 도구를 선택
* 장점: 새로운 케이스 대응, 탐색형 작업에 강함
* 단점: 예측 어려움, 비용 폭주/오동작 위험, 인젝션/도구 오용 위험

**추천 용도**

* 조사/리서치, 복잡한 문제 해결, 여러 소스를 종합해야 하는 작업(단, 안전장치 필수)

### 4.3 실무 결론(가장 중요한 원칙)

* **워크플로우를 기본으로 설계**하고
* “정말 유연성이 필요한 단계”에만 에이전트를 부분 적용(예: 검색 쿼리 생성, 요약/비교, 후보 생성)

## 5) 대표 아키텍처 패턴(현업에서 반복해서 쓰는 설계)

### 5.1 Planner–Executor 패턴

* **Planner**: 작업을 단계로 계획(필요 도구/순서/종료조건)
* **Executor**: 계획대로 도구를 호출하고 결과를 누적
* 장점: 계획과 실행을 분리해 안정화/검증이 쉬움
* 팁: Planner는 짧고 보수적으로, Executor는 스키마/검증을 강하게

### 5.2 ReAct 패턴(Reason + Act)

* 모델이 “생각(추론)”과 “행동(도구 호출)”을 번갈아 수행
* 현업에서는 “생각을 그대로 노출”하기보다, **행동 로그/근거**만 남기고 운영하는 것이 안전합니다.

### 5.3 Map–Reduce(대규모 문서/데이터 처리)

* 문서를 조각별로 요약/추출(Map) → 전체 통합(Reduce)
* 장점: 긴 문서 처리/병렬 처리에 적합
* 단점: 통합 단계에서 모순/중복이 생길 수 있어 검증 필요

### 5.4 Critic/Verifier 패턴(검증자 분리)

* 작성자(Writer)와 검증자(Verifier)를 분리
* “정책 위반/근거 누락/형식 깨짐”을 검증 단계에서 걸러냄
* 비용은 늘지만, 고위험 업무에서 효과가 큼

### 5.5 Human-in-the-loop(승인 단계 포함)

* 고위험 액션(권한 변경, 환불, 배포)에는 반드시 승인 단계 삽입
* “요약/근거/추천 액션”까지만 자동, 실행은 승인 후

## 6) 상태(State) 설계: 자동화 품질의 80%를 좌우

멀티스텝 작업은 “메모리”가 아니라 **상태(state)**로 관리해야 합니다.

### 6.1 상태에 담아야 할 것(권장)

* 입력: 사용자 요청, 요청자 ID/권한, 시간
* 중간 산출물: 검색 결과, 선택된 근거, 계산 결과, 후보안
* 결정 기록: 어떤 규칙/근거로 결정을 내렸는지(감사)
* 실행 결과: 티켓 ID, DB 반영 결과, 실패 코드
* 제약/정책: 금지 규칙, 허용 도구 목록, 예산/시간 제한
* 추적용: trace_id, step_id, 재시도 횟수

### 6.2 “대화 메모리”와 “작업 상태” 분리

* 대화 메모리: 사용자와의 맥락 유지(선호/배경)
* 작업 상태: 지금 수행 중인 프로세스의 사실/결과/결정
  → 섞이면 디버깅도 어렵고 보안도 위험해집니다.

---

## 7) 실패 복구/안전장치: 에이전트를 ‘제품’으로 만드는 요소

### 7.1 가드레일 5종 세트(현업 표준)

1. **도구 allowlist**: 허용된 도구만 제공
2. **파라미터 검증**: JSON Schema/Pydantic 검증 필수
3. **예산/시간 제한**: 최대 호출 수, 최대 토큰, 최대 비용
4. **재시도/폴백**: 오류 유형별 재시도, 다른 도구/모델로 폴백
5. **감사로그/관측**: 어떤 도구를 왜 호출했는지 trace로 남김

### 7.2 서킷 브레이커(Circuit Breaker)

* 실패율이 일정 수준을 넘으면 자동으로 기능을 제한/중단
* 운영에서 “폭주”를 막는 장치(비용/보안/서비스 안정성)

### 7.3 인젝션 대응(특히 에이전트에서 중요)

에이전트는 외부 텍스트(문서/웹)에서 “도구를 이렇게 써라” 같은 악성 지시를 읽기 쉬움.

* 시스템/정책 프롬프트 최상위 고정
* 외부 컨텍스트는 “참고 자료”로 격리
* 도구 호출은 규칙 기반 검증을 통과해야만 실행

---

## 8) 기술(Techniques): “통제 가능한 자동화” 구현 팁

### 8.1 단계별 스키마(Progressive Structuring)

각 단계 출력은 구조화(7장)해 상태에 저장합니다.

* 검색 단계: `{queries[], selected_docs[]}`
* 요약 단계: `{facts[], citations[]}`
* 실행 단계: `{action, parameters, approval_required}`
  이렇게 하면 재시작/분기/감사가 쉬워집니다.

### 8.2 라우팅 + 폴백

* 라우터가 인덱스/도구를 선택하되, 실패하면 전체 검색/다른 도구로 폴백
* “틀릴 수 있다”를 전제로 설계하면 운영 안정성이 올라갑니다.

### 8.3 병렬화

* 독립적인 검색/분석을 병렬로 수행(Map 단계) 후 통합
* 처리량/지연을 최적화하기 좋은 패턴

---

## 9) 관련 기술·솔루션(실무 기준)

### 9.1 그래프/워크플로우 오케스트레이션

* **LangGraph**: 상태/분기/루프/재시도를 그래프 구조로 명확히 표현(LLM 워크플로우에 특히 적합).
* **Temporal**: 장기 실행/재시도/보상 트랜잭션이 강한 엔터프라이즈 워크플로우 엔진(LLM 호출을 안정적으로 감싸기 좋음).
* **Prefect / Dagster**: 데이터/파이프라인 중심 워크플로우에 강하며, AI 작업 파이프라인에도 활용 가능.

### 9.2 멀티 에이전트(선택)

* **AutoGen / CrewAI**: 역할 분리(검색자/작성자/검증자) 같은 멀티 에이전트 패턴을 실험하기 좋음.
* 주의: 운영에서는 통제 장치(예산/허용 도구/검증)가 없으면 폭주하기 쉽습니다.

### 9.3 관측/평가

* **Langfuse / LangSmith / Phoenix**: 각 단계 호출·도구 사용·결과를 트레이스로 남기고, 실패 원인/비용을 분석.
* **RAGAS / DeepEval**: 워크플로우 결과의 품질을 자동 평가(근거율/정확성 등).

## 10) 권장 실습(현업형): “정책 기반 실행 에이전트/워크플로우”

### 과제: “권한 변경 요청 처리”

**요구**

* 사용자가 권한 변경을 요청하면,

  1. 정책 문서를 RAG로 검색
  2. 조건(소속/직무/승인자/기간)을 구조화로 추출
  3. 조건 충족 여부 판단
  4. 충족하면 승인 요청 생성(또는 승인자에게 알림)
  5. 승인 후에만 실제 권한 변경 API 호출(툴)

**필수 설계 요소**

* 단계별 state 저장(요청/근거/판단/승인/실행 결과)
* 실패 복구(권한 부족/정책 문서 누락/툴 오류)
* 감사로그(누가 왜 실행했는지)
* 예산 제한(최대 도구 호출 수, 최대 비용)

**평가**

* 정책 위반 실행률 0% (가장 중요)
* 성공률, 평균 처리 시간, 재시도 횟수, 운영 비용
