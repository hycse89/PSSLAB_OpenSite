 
## 8장. Tool/Function Calling: LLM을 “답변기”에서 “업무 실행 엔진”으로 바꾸기

### 1) 개요: 왜 툴 호출이 LLM 제품화의 분기점인가

LLM만으로도 글은 잘 씁니다. 하지만 현업에서 필요한 건 보통 “글”이 아니라 **행동(action)** 입니다.

* 사내 DB에서 고객 상태 조회
* 이슈 트래커(Jira/GitHub)에 티켓 생성
* 계산/검증(견적, 규정 체크, 포맷 변환)
* 외부 검색/사내 검색 실행 후 요약
* 알림/승인 요청/워크플로우 트리거

LLM이 **외부 도구(함수/API)를 호출**하게 만들면,

* 사실은 시스템에서 가져오고(환각 감소)
* 업무는 자동으로 실행되고(생산성 증가)
* 결과는 구조화 출력으로 정리되어(신뢰성 증가)
  실제로 “제품”이 됩니다.

이 장은 Tool/Function Calling의 핵심 메커니즘과, **안전한 설계(allowlist, 검증, 권한, 감사로그, 재시도)**를 포함한 실무 아키텍처를 상세히 다룹니다.

---

### 2) 학습 목표

1. Tool/Function Calling이 무엇이며, 프롬프트 기반 “도구 흉내”와 무엇이 다른지 설명
2. 툴 호출 플로우(계획→호출→결과→최종 응답)를 설계하고 구현 흐름을 이해
3. 툴 스키마(OpenAPI/JSON Schema)로 파라미터를 정의하고 검증하는 방법을 이해
4. **안전한 툴 설계**(권한/allowlist/파라미터 검증/감사로그/레이트리밋)를 적용
5. RAG/구조화 출력/워크플로우와 결합해 “업무 자동화”를 완성

---

## 3) 핵심 개념: LLM은 ‘의사결정자’, 도구는 ‘사실/행동의 실행자’

Tool Calling을 잘 쓰는 팀은 역할 분리를 명확히 합니다.

* **LLM의 역할**: 어떤 도구를 쓸지 선택, 어떤 파라미터로 호출할지 결정, 결과를 요약/조합
* **도구(시스템)의 역할**: 사실 제공(DB/검색), 계산 수행, 상태 변경(티켓 생성/결제/승인)

> 원칙: **사실(Truth)은 시스템에서**, **표현/조합은 LLM에서**.

이 원칙이 지켜지면 환각이 줄고, 보안/감사도 쉬워집니다.

---

## 4) 핵심 원리: Tool Calling의 기본 실행 흐름

### 4.1 표준 플로우(싱글턴 툴 호출)

1. 사용자 입력 + 컨텍스트(정책/권한 등)
2. 모델이 “툴 호출이 필요하다”고 판단 → `tool_name` + `arguments` 생성
3. 애플리케이션이 툴 실행(실제 API 호출)
4. 툴 결과를 모델에 다시 전달
5. 모델이 최종 답변/구조화 결과를 생성

### 4.2 멀티스텝 플로우(여러 도구 연쇄)

* 조회 → 필터링 → 계산 → 등록 같은 연쇄가 필요할 때
* 이때는 **상태(state)**를 저장하고, 실패 시 재시도/롤백까지 고려해야 합니다(11장/23~25장과 연결).

### 4.3 “툴 호출” vs “에이전트”

* 툴 호출은 기능(메커니즘)
* 에이전트는 “계획/반복/자기 수정”까지 포함한 운영 패턴
  즉, **툴 호출은 최소 단위**, 에이전트는 그 위의 조립 방식입니다.

---

## 5) 설계 핵심: 툴 인터페이스를 ‘계약’으로 만들기

### 5.1 스키마(함수 시그니처) 정의

툴 호출 성공률과 안전성은 “시그니처” 품질에서 결정됩니다.

* 입력 파라미터 타입(문자열/숫자/enum/배열)
* 필수/선택 필드
* 값 범위(예: 1~5), 패턴(예: 티켓 키 형식)
* 설명(모델이 올바른 값을 고르게 하는 힌트)

**실무 원칙**

* 파라미터를 최소화(모델이 채우기 어렵다면 분리)
* enum/const로 선택지 축소
* 사람이 읽는 설명을 잘 달아야 모델 호출 품질이 올라갑니다.

### 5.2 OpenAPI 기반 툴 노출(실전)

사내 REST API가 이미 있다면 OpenAPI(Swagger) 스펙으로 정리해

* “LLM이 호출 가능한 도구 카탈로그”로 만들 수 있습니다.

장점:

* 문서와 실행 계약이 일치
* 파라미터/응답 타입이 표준화
* 권한/버전관리 연동이 쉬움

---

## 6) 안전/보안: 툴 호출에서 반드시 막아야 하는 것들(현업 핵심)

### 6.1 Allowlist(허용 목록) 기반 설계

* 모델에게 “세상의 모든 API”를 주면 위험합니다.
* **정해진 도구만** 주고, 기능을 단계적으로 확장합니다.

### 6.2 파라미터 검증(Validation)과 정규화

* 모델이 만든 arguments는 항상 검증해야 합니다.
* JSON Schema/Pydantic으로 타입·범위·패턴 검증
* 문자열 정규화(공백 제거, 날짜 ISO 포맷 등)

### 6.3 권한(Authorization)과 데이터 접근(ACL)

* “모델이 호출”하더라도 실제 권한은 **사용자/서비스 계정** 기준으로 제한해야 합니다.
* RAG에서처럼 툴 결과도 권한 필터가 적용되어야 합니다.

### 6.4 인젝션(Injection)과 툴 오용 방지

모델이 외부 텍스트(문서/웹)에서 “도구 호출을 유도하는 악성 지시”를 읽을 수 있습니다.
대응 원칙:

* 시스템/툴 프롬프트는 외부 컨텍스트와 분리
* “툴 호출 규칙”을 최상위 정책으로 고정
* 도구 입력은 사용자 입력을 그대로 쓰지 말고 **정규화/필터링**
* 고위험 작업은 “2인 승인/확인 단계”를 넣기(HITL)

### 6.5 감사로그(Audit log) / 레이트리밋 / 비용 통제

* 누가 어떤 툴을 어떤 인자로 호출했는지 기록
* 호출 빈도/비용 상한을 둬 폭주 방지
* 실패율 급증 시 자동 차단(서킷 브레이커)

---

## 7) 품질 전략: 툴 호출이 실패할 때의 복구 설계

툴 호출은 네트워크/권한/데이터 결측 등으로 자주 실패합니다. 제품에서는 반드시 복구 루프가 필요합니다.

### 7.1 실패 유형

* 파라미터 오류(형식/타입/누락)
* 권한 없음(403), 리소스 없음(404)
* 타임아웃/레이트리밋(429)
* 서버 오류(5xx)
* 결과가 비어 있음(검색 실패)

### 7.2 복구 패턴(실무 표준)

1. **파라미터 수정 재시도**: 검증 오류 메시지를 모델에 주고 수정하게 함
2. **대체 툴 사용**: 1차 검색 실패→다른 인덱스/키워드 검색
3. **부분 결과로 진행**: 가능한 정보만으로 “추가 질문” 생성
4. **사람에게 넘기기**: 고위험 작업/반복 실패는 HITL로 전환
5. **폴백 모델/보수 모드**: 더 낮은 temperature, 더 엄격한 스키마

---

## 8) 구조화 출력/ RAG / 워크플로우와 결합 패턴(아키텍처)

### 8.1 Tool → Structured Outputs

* 툴 결과를 받아 최종 결과를 스키마 JSON으로 정리
* 예: “고객 상태 조회” → `{customer_id, status, next_actions[]}`

### 8.2 RAG → Tool

* 문서 근거로 정책을 찾고, 정책에 맞는 툴을 호출(예: 환불 정책 확인 후 환불 API 호출)

### 8.3 Workflow(그래프) 기반 Tool orchestration

* 단계가 많아질수록 단일 프롬프트에 몰아넣지 말고
* 상태 기반 워크플로우(11장 LangGraph 등)로 분해

  * 조회 단계 / 검증 단계 / 실행 단계 / 기록 단계

---

## 9) 관련 기술·솔루션(실무에서 자주 쓰는 것들)

### 9.1 Tool/Function Calling 제공(플랫폼)

* **OpenAI Tool/Function Calling**: 모델이 도구를 선택하고 파라미터를 구조화해 반환하는 표준 기능.
* **OpenAI Responses API**: 텍스트/툴 호출/구조화 응답을 한 흐름으로 구성하기 좋음.

### 9.2 도구 스펙/계약

* **OpenAPI(Swagger)**: 사내 REST API를 “툴 카탈로그”로 만드는 표준 스펙.
* **JSON Schema / Pydantic**: 툴 입력/출력 검증, 정상화, 오류 메시지 구조화에 유용.

### 9.3 오케스트레이션

* **LangChain Tools**: 도구 정의/호출 흐름을 쉽게 구성(빠른 프로토타이핑에 좋음).
* **LangGraph**: 상태/분기/재시도/루프가 필요한 멀티스텝 툴 실행에 적합.
* **Temporal**: 엔터프라이즈 워크플로우 엔진으로 재시도/보상 트랜잭션이 강력(툴 호출을 안정화).

### 9.4 운영/관측/정책

* **Langfuse / LangSmith**: 어떤 툴이 왜 호출됐는지 트레이스 기반으로 분석.
* **NeMo Guardrails / Guardrails AI**: 정책 기반으로 툴 사용/출력 검증을 제한하는 프레임워크 계열.

## 10) 권장 실습(현업형 과제)

### 실습 A: “티켓 자동 생성 + 상태 조회” 봇

1. 도구 2개 만들기

* `search_incidents(query, time_range)` : 장애 사례 검색
* `create_ticket(title, severity, component, description)` : 티켓 생성

2. 모델은 상황에 따라

* 먼저 검색으로 유사 장애를 찾고
* 그 결과를 근거로 티켓을 생성

3. 최종 출력은 7장의 스키마 JSON으로 고정

**평가 지표**

* 툴 호출 성공률, 파라미터 오류율, 평균 재시도 횟수
* 티켓 품질(필수 필드 누락률, severity 오분류율)
* 비용/지연

### 실습 B: “정책 기반 실행” (안전 설계 포함)

* 환불/권한 변경 같은 “고위험” 액션 툴을 가정
* 정책 문서 RAG로 조건 확인
* 조건을 만족할 때만 실행(아니면 승인 요청 생성)

## 11) 이 장의 결론(다음 장과 연결)

* Tool/Function Calling은 LLM을 **사실 기반**으로 만들고, **업무를 실행**하게 하며, 자동화를 가능하게 합니다.
* 하지만 성공의 핵심은 기능이 아니라 **안전한 설계(allowlist, 검증, 권한, 감사로그, 복구 루프)** 입니다.
* 다음 9장에서는 “정확하고 최신인 근거”를 공급하는 **RAG 기본 공정**을 다뤄, 툴 호출과 함께 환각을 크게 줄이는 제품형 패턴을 완성합니다.
