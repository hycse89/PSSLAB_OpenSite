 
## 5장. 생성(Generation)과 추론 제어: “모델 성능”을 “제품 품질”로 바꾸는 디코딩/제어 기술

### 1) 개요: 같은 모델도 “어떻게 생성하느냐”에 따라 결과가 완전히 달라진다

생성형 AI(텍스트/이미지/음성)는 본질적으로 **확률 분포에서 샘플링**합니다.
즉, 모델은 “정답 한 개”를 내는 기계가 아니라, “가능한 다음 결과들의 확률”을 내고 우리는 그걸 **어떤 규칙으로 선택/샘플링**할지 결정합니다.

그래서 실무에서 자주 보는 현상:

* 모델은 좋은데 답이 **장황/중복/탈선/환각**한다
* 어떤 요청은 잘 되는데, 어떤 요청은 **너무 딱딱/너무 창의적/형식이 깨짐**
* 같은 프롬프트도 매번 결과가 달라서 **재현성이 부족**

이 장은 “생성의 원리”를 잡고, **디코딩(Decoding) 전략 + 제어 파라미터 + 구조화/검증/재시도**까지 묶어 **품질을 엔지니어링하는 방법**을 다룹니다.

---

### 2) 학습 목표

1. 생성이 “다음 토큰 확률”을 반복 샘플링하는 과정임을 설명
2. Greedy/Beam/Sampling의 차이와 장단점을 이해
3. Temperature/Top-p/Top-k의 의미를 품질 관점에서 설명하고 튜닝 가능
4. 반복/탈선/환각 같은 실패 패턴의 원인을 분해하고 대응책을 적용
5. 구조화 출력(JSON Schema), stop 조건, 재시도/폴백 등 **제품형 제어 전략**을 설계

---

## 3) 핵심 개념: 생성은 “확률 분포에서의 선택”이다

### 3.1 Logits → 확률(Softmax)

모델은 다음 토큰 후보들에 대해 **logits(점수)**를 출력합니다.
이를 softmax로 바꾸면 확률 분포가 됩니다.

* logits가 한 후보에 몰리면: 결과가 결정적(일관성↑, 창의성↓)
* logits가 퍼지면: 선택지가 다양(창의성↑, 일관성↓)

### 3.2 Autoregressive generation(자기회귀 생성)

LLM(대부분의 생성 모델)은 다음 과정을 반복합니다.

1. 지금까지의 토큰을 입력
2. 다음 토큰의 확률 분포 계산
3. 디코딩 규칙으로 다음 토큰 선택
4. 선택된 토큰을 입력에 붙이고 반복

이 반복 과정에서 **작은 실수/왜곡이 누적**될 수 있어, 초반 제어(프롬프트/형식/근거)가 중요합니다.

---

## 4) 핵심 원리: 디코딩(Decoding) 전략 3종

### 4.1 Greedy decoding

* 매 단계에서 확률이 가장 높은 토큰을 선택
* 장점: 빠르고 재현성이 높음(거의 deterministic)
* 단점: 문장이 뻔해지고, 국소 최적에 갇혀 품질이 떨어질 수 있음(특히 창의적 작업)

**언제 쓰나**: 요약/정형 답변/구조화 출력처럼 일관성이 중요한 경우(혹은 temperature 매우 낮게)

### 4.2 Beam search(개요)

* 여러 후보 시퀀스를 동시에 유지(beam width)하며 최적 후보를 찾음
* 장점: 번역 등에서 특정 품질 향상을 기대
* 단점: 계산량 증가, 최근 LLM 대화/창작에서는 과한 경우도 많음
* 실무에선 텍스트 생성형 LLM에서는 “beam을 강제”하기보다 sampling 제어를 더 많이 씁니다.

### 4.3 Sampling(샘플링)

* 확률 분포에 따라 무작위로 선택(제어 파라미터로 범위를 조절)
* 장점: 다양성/창의성 확보, 문장 자연스러움
* 단점: 재현성 낮아지고, 잘못된 방향으로 탈선 가능

**언제 쓰나**: 브레인스토밍, 초안 다변화, 창작, 다양한 후보 생성 후 rerank/선정하는 워크플로우

## 5) 제어 파라미터(실무에서 가장 많이 만지는 버튼)

### 5.1 Temperature

확률 분포를 “평평하게/뾰족하게” 만드는 파라미터입니다.

* 낮게(0~0.3): 보수적·일관적·재현성↑, 그러나 딱딱/반복 가능
* 높게(0.7~1.2): 다양성↑, 그러나 오류/환각/탈선↑

**현업 팁**

* 업무용 Q&A/정책/보고서: 낮게
* 아이디어 생성/카피/콘텐츠: 중간~높게
* 구조화 출력: 낮게 + 스키마 강제

### 5.2 Top-p (nucleus sampling)

“확률 합이 p가 될 때까지” 상위 후보 집합에서만 샘플링합니다.

* p가 낮으면(0.7~0.9): 안전하고 일관적
* p가 높으면(0.95~0.99): 다양하지만 튐 가능

**현업 팁**

* temperature와 함께 조정하지만, 둘을 동시에 과하게 올리면 품질이 급격히 흔들립니다.

### 5.3 Top-k

상위 k개 후보만 남기고 샘플링합니다.

* k가 작으면 보수적
* k가 크면 다양성 증가

요즘은 top-p가 더 흔하지만, 특정 엔진/서빙에서는 top-k가 직관적이라 쓰기도 합니다.

### 5.4 최대 토큰/길이 제어(Max tokens) + Stop sequences

* 장황함/비용 폭주 방지
* 특정 구분자(예: `\n\n###`)에서 생성 중단

**현업 팁**

* “답변 길이를 지시”만 하지 말고, **하드 리미트**도 함께 둡니다.

### 5.5 Penalties(반복 억제)

* repetition penalty, frequency/presence penalty 등(플랫폼별 옵션)
* “같은 말 반복”을 줄이는 데 도움

## 6) 실패 패턴(현업에서 자주 터지는 문제)과 대응법

### 6.1 반복/루프(같은 문장, 같은 구조 반복)

**원인**

* 낮은 temperature + 특정 패턴 고착
* 프롬프트가 모호하거나, 출력 형식이 너무 자유로움

**대응**

* repetition penalty/penalty 적용
* 출력 형식(섹션 수/불릿 수) 강제
* stop sequence 사용
* “요약→최종” 같은 2단계 생성

---

### 6.2 탈선(요구와 다른 이야기로 샌다)

**원인**

* 지시가 약함, 컨텍스트 과다/잡음
* 질문에 필요한 정보가 없는데도 “뭔가 말하려고” 함

**대응**

* 제약 조건 강화(해야 할 것/하지 말 것)
* 컨텍스트 정리(필요한 근거만)
* “근거 없으면 모른다/추가 질문” 정책

---

### 6.3 환각(Hallucination)

**원인**

* 모델이 모르는 영역에서 그럴듯한 문장 생성
* RAG 검색 실패 또는 근거 부족
* 높은 temperature/과도한 자유도

**대응(우선순위)**

1. **근거 제공(RAG)** + 출처 인용 강제
2. **툴 호출(데이터 조회/계산)**로 사실을 시스템에서 가져오게
3. temperature 낮추기, “추측 금지/근거 없으면 모른다” 정책
4. 후처리 검증(사실 체크 룰, 스키마 검증)

---

### 6.4 형식 깨짐(파싱 불가)

**원인**

* 자연어 출력이 섞이거나, JSON 깨짐, 필드 누락

**대응**

* **Structured Outputs(JSON Schema)**로 출력 형식 자체를 강제
* Pydantic 등으로 검증 후 실패 시 자동 재시도(repair loop)

---

## 7) 제품형 생성 제어 패턴(실무에서 ‘진짜’ 쓰는 것)

### 7.1 후보 생성 후 선택(generate-and-select)

* 한 번에 1개 정답을 기대하지 말고, 후보 N개 생성 → 규칙/모델로 최종 선택
* 마케팅 카피/요약/답변 톤 조절에서 매우 강력

구성 예:

1. 후보 5개 생성(temperature↑)
2. 정책/형식/금칙어 필터
3. rerank(LLM-as-judge 또는 룰 기반)로 1개 선정

### 7.2 2단계 생성: Draft → Critique → Final

* 초안을 만들고, 자기검토(critique) 후 최종 작성
* 장점: 논리/형식/누락이 줄어듦
* 단점: 비용/지연 증가(그래서 중요한 작업에만)

### 7.3 증거 우선 생성(citation-first)

* 먼저 “근거 문장/인용 목록”을 만들고
* 그 근거만으로 답을 쓰게 하면 환각이 크게 줄어듭니다.

### 7.4 구조화 출력 + 후처리 자동화

* JSON으로 “요구사항/테스트케이스/티켓”을 뽑고
* 검증 통과 시에만 시스템에 등록(Jira/DB)

---

## 8) 기술(Techniques) & 구현 포인트

### 8.1 로그 확률/불확실성 활용(가능한 경우)

* 일부 플랫폼은 토큰 logprob를 제공
* 낮은 확률로 생성되는 구간은 “불확실”로 보고 추가 검증/근거 요구를 걸 수 있음

### 8.2 스트리밍(Streaming)

* 사용자 경험을 크게 개선
* 다만 “중간에 잘못된 방향”이 보일 때 중단/수정하는 UX 설계가 중요

### 8.3 캐싱과 재현성

* 같은 입력이면 같은 결과를 얻고 싶다면:

  * temperature 낮추기
  * seed 지원 시 seed 고정
  * 결과 캐싱(특히 반복 요청) 적용

---

## 9) 관련 기술/솔루션(실무에서 바로 연결되는 것들)

### 9.1 생성 제어(플랫폼 파라미터)

* **Temperature / Top-p / Max tokens / Stop sequences**: 거의 모든 LLM API가 제공하는 기본 제어 레버.
* **Frequency/Presence penalty(계열)**: 반복/주제 다양성 제어에 유용(지원 여부는 플랫폼별).

### 9.2 구조화 출력/검증

* **JSON Schema 기반 Structured Outputs**: 출력 형식을 계약으로 강제해 파싱 실패를 크게 줄임.
* **Pydantic**: 스키마/타입 검증 + 실패 시 자동 재시도 루프 구성에 적합.
* **Guardrails AI(프레임워크)**: 출력 검증/재시도/정책 적용을 묶어주는 계열.

### 9.3 평가/선택 워크플로우

* **promptfoo**: 여러 프롬프트/파라미터 조합을 테스트하고 비교(회귀 테스트에 좋음).
* **RAGAS/DeepEval/TruLens**: 생성 결과의 근거/정확성 등을 자동 평가하는 프레임워크(LLM 평가 파트에서 심화).

## 10) 권장 실습(이 장을 확실히 체득하는 과제)

### 실습 A: 디코딩 파라미터 스윕(temperature/top-p)

* 같은 질문에 대해 temperature(0.1, 0.3, 0.7), top-p(0.8, 0.9, 0.95) 조합을 돌려
* **평가 기준**(정확성/일관성/간결성/금칙어 위반/형식 준수)을 점수화
* 결과: “업무 유형별 기본 프리셋” 만들기(예: Q&A=0.2/0.9, 아이디어=0.8/0.95 등)

### 실습 B: 형식 깨짐 방지

* 자연어 출력 → JSON 파싱 실패 사례를 일부러 만들고
* (1) 프롬프트만으로 해결 vs (2) Structured Outputs 적용 비교
* 실패율/재시도율/지연/비용 비교

### 실습 C: 환각 완화 실험

* 동일 질문을

  1. Prompt-only
  2. RAG(근거 제공)
  3. Tool(계산/조회)
     로 비교해서 환각률/근거율을 측정

## 11) 이 장의 결론(다음 장과 연결)

* 생성 품질은 **모델**만큼이나 **디코딩/제어/검증**에 의해 결정됩니다.
* “업무형 AI”는 자유 생성이 아니라, **형식·근거·정책**을 엔지니어링하는 일입니다.
* 다음 2부(LLM 실용)에서는 5장에서 배운 생성 제어를 기반으로,

  * 6장 프롬프트(지시/제약/검증)
  * 7장 구조화 출력
  * 8장 툴 호출
  * 9~10장 RAG
    로 연결해 “제품형 LLM 앱”을 구축하게 됩니다.
